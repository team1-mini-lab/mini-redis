# 실제 Redis와 다른 점

[← README로 돌아가기](../../README.md)

| 항목 | 실제 Redis | mini-redis | 이유 |
| --- | --- | --- | --- |
| 통신 | TCP 위 자체 프로토콜(RESP) | HTTP + JSON | `curl`로 바로 확인, 과제의 "외부에서 사용" |
| 동시성 | 싱글 스레드 | Flask 멀티 스레드 + lock 하나 | Flask가 요청을 스레드로 받음. lock으로 같은 효과 |
| 해시 함수 | SipHash + 무작위 시드 | FNV-1a 고정 | 충돌 재현. 해시 플러딩 방어는 범위 밖 |
| 확장 | 두 테이블로 조금씩 옮김 | 한 번에 2배 | 설명이 단순하고 우리 규모에선 멈춤이 체감되지 않음 |
| 만료 삭제 | 지연 삭제 + 주기적 무작위 검사 | 지연 삭제만 | 조회할 때 지우는 것만으로 "만료된 키는 없는 키"라는 동작은 보장됨. 한 번도 다시 조회되지 않는 만료 키가 메모리에 남는 문제는 과제 필수 범위가 아니라 뒤로 미룸 |
| 원자적 증가 | `INCR`, `DECR` | 없음 | 과제 필수 기능(저장·조회·삭제·만료)에 들어가지 않아 뒤로 미룸 |
| 파일 저장 | RDB, AOF | 없음 | 캐시는 원본(DB)이 따로 있어서, 재시작으로 값이 사라져도 DB에서 다시 채울 수 있음 |

## 통신

실제 Redis는 TCP 연결 위에서 RESP라는 Redis 전용 형식으로 명령을 주고받습니다. 클라이언트는 `SET name mini EX 5`처럼 명령 이름과 인자를 보내고, 서버는 정해진 형식으로 결과를 돌려줍니다. 이 형식을 쓰려면 `redis-cli`나 각 언어의 Redis 클라이언트 라이브러리가 필요합니다.

mini-redis는 HTTP 요청과 JSON으로 통신합니다. 저장은 `POST /set`에 JSON 본문을 보내고, 조회와 삭제는 `GET /get?key=...`, `DELETE /delete?key=...`로 합니다. HTTP를 고른 이유는 따로 클라이언트를 만들지 않아도 `curl`이나 브라우저, 파이썬의 `requests`로 바로 요청을 보내 결과를 확인할 수 있고, 과제 요구사항인 "외부 프로그램에서 저장소를 사용할 수 있어야 한다"를 가장 간단하게 만족하기 때문입니다. 대신 요청마다 HTTP 헤더를 주고받으므로 RESP보다 주고받는 데이터가 많고 느립니다.

## 동시성

실제 Redis는 명령을 실행하는 스레드가 하나입니다. 여러 클라이언트의 요청이 동시에 와도 명령은 하나씩 차례로 실행되므로, 한 명령이 실행되는 도중에 다른 명령이 끼어들 수 없습니다. 그래서 저장소 안에 lock을 둘 필요가 없습니다.

mini-redis는 Flask 서버 위에서 동작하는데, Flask는 요청마다 스레드를 따로 만들어 여러 요청을 동시에 처리합니다. 그대로 두면 두 요청이 같은 해시 테이블을 동시에 고치다가 노드가 사라지는 일이 생길 수 있습니다. 그래서 `store.py`에 lock을 하나 두고 `set`, `get`, `delete`를 모두 그 lock 안에서 실행합니다. 한 번에 한 요청만 저장소를 만지게 되므로, 명령을 하나씩 차례로 실행하는 Redis와 같은 결과를 얻습니다. 요청을 받고 JSON을 해석하는 부분은 여전히 여러 스레드에서 동시에 일어나고, 저장소를 만지는 부분만 차례로 실행됩니다.

## 해시 함수

실제 Redis는 SipHash라는 해시 함수를 쓰고, 서버를 시작할 때마다 무작위로 정한 값(시드)을 함께 넣어 해시 값을 계산합니다. 이렇게 하면 밖에서 시드를 알 수 없으므로, 공격자가 일부러 같은 칸에 몰리는 키를 대량으로 만들어 보내 서버를 느리게 만드는 공격(해시 플러딩)을 막을 수 있습니다.

mini-redis는 FNV-1a를 시드 없이 씁니다. 같은 키는 언제 실행해도 같은 칸에 들어가므로, "두 키가 같은 칸에 들어갔을 때 체인이 제대로 동작하는가"를 테스트에서 매번 똑같이 재현할 수 있습니다. 그 대신 해시 플러딩 공격에는 막혀 있지 않습니다. 이 프로젝트는 외부에 공개해 운영하는 서버가 아니므로 이 방어는 범위에서 뺐습니다.

## 칸 수 확장

실제 Redis는 칸을 늘릴 때 해시 테이블을 두 개 둡니다. 기존 테이블 옆에 두 배 크기의 새 테이블을 만들고, 이후 들어오는 명령을 처리할 때마다 기존 테이블의 칸을 조금씩 새 테이블로 옮깁니다. 옮기는 동안 조회는 두 테이블을 모두 확인합니다. 이렇게 나눠서 옮기기 때문에 키가 수백만 개여도 한 명령이 오래 멈추는 일이 없습니다.

mini-redis는 키 수 ÷ 칸 수가 0.75를 넘는 순간 두 배 크기의 새 배열을 만들고, 모든 노드를 그 자리에서 한 번에 옮깁니다. 그동안 그 요청은 옮기기가 끝날 때까지 기다리고, lock 때문에 다른 요청도 기다립니다. 한 번에 옮기는 방식을 고른 이유는 코드가 단순해서 동작을 설명하고 검증하기 쉽고, 이 프로젝트에서 다루는 키 수(테스트에서 최대 10만 개)에서는 옮기는 시간이 짧아 멈춤이 문제되지 않기 때문입니다.

## 만료 삭제

실제 Redis는 만료된 키를 두 가지 방법으로 지웁니다. 하나는 키를 조회할 때 만료됐는지 확인하고 지우는 지연 삭제입니다. 다른 하나는 1초에 여러 번, 만료 시간이 있는 키 중 일부를 무작위로 골라 만료된 것을 지우는 주기적 삭제입니다. 주기적 삭제 덕분에 아무도 다시 조회하지 않는 만료 키도 결국 메모리에서 사라집니다.

mini-redis는 지연 삭제만 합니다. 조회할 때 만료된 키를 지우고 "없는 키"로 답하므로, 사용자가 보기에는 만료된 키가 항상 없는 것처럼 동작합니다. 하지만 만료된 뒤 한 번도 조회되지 않는 키는 메모리에 계속 남습니다. 저장·조회·삭제·만료라는 과제의 필수 동작은 지연 삭제만으로 만족하므로, 주기적 삭제는 뒤로 미뤘습니다.

## 원자적 증가

실제 Redis에는 `INCR`, `DECR`처럼 저장된 숫자를 1 늘리거나 줄이는 명령이 있습니다. "값을 읽고, 계산하고, 다시 저장한다"는 세 동작을 명령 하나로 처리하고, 명령은 하나씩 차례로 실행되므로 그 사이에 다른 요청이 끼어들 수 없습니다. 여러 서버가 함께 세야 하는 조회수나 남은 수량을 정확하게 다룰 수 있는 이유입니다.

mini-redis에는 이런 명령이 없습니다. 숫자를 바꾸려면 클라이언트가 `get`으로 읽고 계산한 뒤 `set`으로 저장해야 하는데, `get`과 `set`은 서로 다른 요청이라 그 사이에 다른 서버의 요청이 끼어들 수 있습니다. 두 서버가 같은 값 1을 읽고 각자 0을 저장하면, 두 번 뺐는데 한 번만 빠진 결과가 됩니다. 저장소 안의 lock은 요청 하나 안에서만 순서를 지켜 주고, 요청 두 개에 걸친 동작은 지켜 주지 못합니다. 이 명령은 과제의 필수 기능에 들어가지 않아 뒤로 미뤘습니다.

## 파일 저장

실제 Redis는 메모리에 있는 데이터를 파일로도 남길 수 있습니다. RDB는 일정 시간마다 메모리 전체를 파일 하나로 저장하는 방식이고, AOF는 값을 바꾸는 명령이 올 때마다 그 명령을 파일 끝에 기록하는 방식입니다. 서버를 다시 켜면 이 파일을 읽어 데이터를 되살립니다.

mini-redis는 데이터를 메모리에만 둡니다. 서버를 끄면 저장된 키가 모두 사라집니다. 이 프로젝트에서 mini-redis는 캐시로 쓰이고, 원본 데이터는 DB에 따로 있습니다. 캐시가 비어도 다음 조회가 DB에서 값을 가져와 다시 채우므로 데이터를 잃지는 않습니다. 다만 다시 채워지는 동안에는 요청이 DB로 몰리고, 로그인 세션처럼 DB에 원본이 없는 값은 사라져서 사용자가 다시 로그인해야 합니다.
