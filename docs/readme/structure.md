# 구조

[← README로 돌아가기](../../README.md)

```
데모 API (demo/app.py, 웹 서버 여러 대)
   │ HTTP
   ▼
mini_redis/server.py   요청 해석 → 입력 검증 → 저장소 호출 → JSON 응답
   │ set / get / delete
   ▼
mini_redis/store.py    lock 하나 · (값, 만료 시점) 묶음 · 지연 삭제
   │ put / get / remove
   ▼
mini_redis/hashtable.py  FNV-1a 해시 · 체이닝 · 0.75 넘으면 2배 확장
```

각 층은 아래 층의 함수만 알고 내부는 모릅니다. 그래서 3가지 API 요청을 테스트 한 뒤 임시용으로 쓰고 있던 파이썬 `dict`를 직접 만든 해시 테이블로 바꿀 때 `server.py`는 변경하지 않았습니다.

요청과 상관없이 서버 안에서 혼자 도는 스레드(백그라운드 스레드)가 두 개 더 있습니다. 둘 다 위의 `store.py`를 요청 스레드와 함께 쓰므로 같은 lock을 잡습니다.

```
정리 스레드     0.1초마다  만료된 키를 256칸씩 찾아 지움      (주기적 정리)
스냅샷 스레드   30초마다   살아 있는 키 전체를 파일에 적음    (데이터 유지)
```

| 폴더 | 내용 |
| --- | --- |

| `demo/` | 캐시를 쓰는 데모 API, 가짜 DB(SQLite, 3초 지연), 시연 스크립트, 매수 주문을 미니 DBMS에 저장하는 코드 |
| `mini_dbms/` | 팀 미니 DBMS(team1-mini-lab/mini-dbms main) 실행 파일을 고치지 않고 복사한 것 |

## 주기적 정리

### 왜 필요한가

만료된 키는 지연 삭제로 처리합니다. 지연 삭제는 누군가 `get`이나 `delete`로 그 키를 요청했을 때만 지웁니다. 그래서 아무도 다시 요청하지 않는 만료 키는 계속 메모리를 차지하고, 해시 테이블의 전체 키 개수(`len`)를 부풀려 필요 없는 칸 확장(`_grow`)까지 일으킵니다. 주기적 정리는 이런 키를 치우는 보조 장치입니다.

만료된 키를 요청했을 때 값을 돌려주지 않는 것은 여전히 지연 삭제가 맡습니다. `get`과 `delete`는 값을 돌려주기 전에 매번 만료 시각을 직접 확인하므로, 주기적 정리가 늦어도 응답은 틀리지 않습니다.

### 동작

```
정리 스레드: 0.1초 쉬기 → lock 잡기 → cursor부터 256칸 보기 → 만료된 키 지우기 → lock 풀기 → 반복
```

| 순서 | 하는 곳 | 하는 일 |
| --- | --- | --- |
| 1 | `store.py` `cleanup_expired_once()` | lock을 잡고, 지난번에 멈춘 칸 번호(`cursor`)를 꺼냄 |
| 2 | `hashtable.py` `scan(cursor, 256)` | `cursor`번 칸부터 256칸에 든 (키, 값)을 목록으로 돌려주고, 다음에 볼 칸 번호도 돌려줌. 끝 칸까지 봤으면 다음 번호는 0 |
| 3 | `store.py` | 목록의 값마다 만료 시각을 확인하고, 만료된 키는 `remove`로 지움 |
| 4 | `store.py` | 다음 칸 번호를 `cursor`에 적어 두고 lock을 품 |

### 설계 결정

| 결정 | 이유 |
| --- | --- |
| 요청 스레드가 아니라 백그라운드 스레드가 정리 | 요청이 오지 않을 때도 정리하고, 요청 하나가 정리 비용을 떠안지 않음 |
| 스레드는 `Store()`를 만들 때가 아니라 `server.py`에서 서버를 켤 때 한 번만 시작 | 테스트에서 `Store`를 수십 번 만들 때 정리 스레드가 수십 개 생기지 않게 |
| 한 번에 테이블 전체가 아니라 256칸만 보고, 멈춘 칸 번호(`cursor`)를 기억했다가 다음에 이어서 봄 | 키가 아무리 많아도 정리 한 번이 lock을 쥐는 시간이 짧고 일정함. 칸 배열은 `list`라 `cursor`번 칸으로 바로 갈 수 있음 |
| `hashtable.py`는 칸의 (키, 값)을 꺼내 보여 주기만 하고(`scan`), 만료 판단과 지우라는 지시는 `store.py`가 함 | "해시 테이블은 만료를 모른다"는 기존 역할 나누기를 지킴 |
| 0.1초마다, 256칸씩. `Store`의 클래스 상수 `CLEANUP_INTERVAL`, `CLEANUP_BUCKETS`로 한 번만 적어 둠 | 아래 측정에서 요청 응답 시간이 늘지 않은 가장 짧은 간격과 가장 많은 칸 수 |

간격은 정리 스레드가 lock을 얼마나 자주 잡는지를, 칸 수는 한 번 잡을 때 얼마나 오래 쥐는지를 정합니다.

| 간격 (256칸) | 1초에 lock 잡는 횟수 | 요청 p99 (정리 없을 때 0.30~0.35ms) | 판단 |
| --- | --- | --- | --- |
| **0.1초** | 10번 | 0.23~0.32ms | 변화 없음 |
| 0.05초 | 20번 | 0.22~0.42ms | 한 번은 늘고 한 번은 그대로 |
| 0.02초 | 50번 | 0.46~0.49ms | 꾸준히 늘어남 |
| 0.01초 | 100번 | 0.52~0.60ms | 꾸준히 늘어남 |

| 한 번에 보는 칸 | 정리 1회 lock 시간 (키 10만 개, 전부 만료) | 요청 속도 변화 | 테이블 한 바퀴 (키 10만 개 / 1,000개) |
| --- | --- | --- | --- |
| 16 | 0.013ms | 없음 | 27분 / 12.8초 |
| **256** | **0.14ms** | 없음 | **102초 / 0.8초** |
| 512 | 0.30ms | 없음 | 51초 / 0.4초 |
| 1024 | 0.66ms | 처리량 5~10% 감소 | 26초 / 0.2초 |

## 데이터 유지

### 왜 필요한가

`store = Store()`는 서버 프로세스의 메모리 안에 있습니다. 프로세스가 끝나면 운영체제가 그 메모리를 돌려받으므로, 서버를 다시 켜면 빈 저장소로 시작합니다. 데이터 유지는 메모리 내용을 파일에도 적어 두고, 서버를 켤 때 그 파일을 읽어 저장소를 다시 채웁니다. mini-redis를 캐시로만 써도, 재시작 직후 모든 요청이 DB로 몰리는 것을 막을 수 있습니다.

### 동작

```
실행 중:   스냅샷 스레드가 30초마다 (바뀐 게 있을 때만)   저장소 ──▶ data/snapshot.json
끌 때:     Ctrl+C(SIGINT)나 kill(SIGTERM)을 받으면     저장소 ──▶ data/snapshot.json  (마지막 한 번)
켤 때:     요청을 받기 전에                              data/snapshot.json ──▶ 빈 저장소
```

스냅샷 한 번은 두 단계로 나눕니다.

| | 빠른 단계: 목록 만들기 | 느린 단계: 파일에 쓰기 |
| --- | --- | --- |
| 하는 곳 | `store.py` `snapshot_items()` | `snapshot.py` `save_snapshot()` |
| 하는 일 | 테이블을 돌며 만료되지 않은 (키, 값, 만료 시각)을 list에 담기 | list를 JSON으로 바꿔 `snapshot.json.tmp`에 쓰고, `os.replace`로 `snapshot.json`과 바꿔치기 |
| 키 10만 개일 때 | 66ms | 316ms |
| lock | 잡음 | 잡지 않음 |

### 설계 결정

| 결정 | 이유 |
| --- | --- |
| 명령마다 기록하는 로그 대신, 그 순간 살아 있는 키 전체를 파일 하나에 덮어쓰는 스냅샷 | 완료 기준(껐다 켜도 값이 조회됨)을 만족하고 코드가 단순함. 서버가 갑자기 죽으면 마지막 스냅샷 뒤의 변경(최대 30초치)은 잃음 |
| 30초마다, 마지막 스냅샷 뒤에 `set`이나 `delete`가 없었으면 건너뜀. 끌 때 한 번 더 | 갑자기 죽어도 잃는 양이 최대 30초치로 정해지고, 정상 종료는 잃는 것이 없음. 측정한 CPU 사용은 10초 간격 약 4%, 30초 약 1.3% |
| SIGTERM이 오면 `sys.exit(0)`으로 바꿔 Ctrl+C와 같은 마지막 코드(`finally`)를 거치게 함 | SIGTERM의 기본 동작은 그 자리에서 끝나는 것이라 마지막 저장이 실행되지 않음. 배포 환경은 서버를 내릴 때 SIGTERM을 보냄 |
| 끌 때는 스냅샷 스레드에게 멈추라고 알리고, 하던 저장이 끝날 때까지 기다린 뒤 마지막 저장 | 두 곳이 같은 `.tmp` 파일에 동시에 써서 내용이 섞이지 않게 |
| lock 안에서는 목록만 만들고, 파일 쓰기는 lock 밖에서 | 요청이 멈추는 시간은 목록을 만드는 동안뿐이고, 파일에는 한 순간의 내용이 그대로 담김 |
| 파일 형식은 JSON: `{"version": 1, "items": [{"key", "value", "expire"}]}` | 모든 값을 그대로 되돌릴 수 있고(값은 `POST /set`에서 JSON으로 들어옴), 읽을 때 코드가 실행되지 않고, 사람이 열어 볼 수 있고, 표준 라이브러리만 씀. 바이너리 형식보다 크고 느린 것은 감수 |
| 실행 중 만료는 `time.monotonic()`, 파일에 적을 때는 `time.time()` 기준 시각으로 바꿈 | `time.monotonic()`은 컴퓨터 시계를 고쳐도 뒤로 가지 않지만, 기준점이 컴퓨터를 켤 때마다 바뀜. `time.time()`은 재부팅해도 같은 순간을 같은 숫자로 나타내므로, 꺼져 있던 동안 흐른 시간까지 만료에 셀 수 있음 |
| 켤 때 이미 만료 시각이 지난 키는 넣지 않음 | 꺼져 있는 동안 만료된 키 |
| `.tmp`에 끝까지 쓴 뒤 `os.replace`로 바꿔치기 | 쓰는 도중에 죽어도 `snapshot.json`에는 이전 스냅샷이 그대로 남음 |
| 켤 때 파일이 없으면 빈 저장소, 깨졌으면 `.broken`으로 옮기고 경고한 뒤 빈 저장소. `.tmp`는 보지 않음 | 깨진 파일을 남겨 두어야 다음 스냅샷이 원인을 덮어쓰지 않음. `.tmp`는 쓰다 만 파일일 수 있음 |
| 요청을 받기 전에 파일을 읽어 채움 | 채우기 전에 요청을 받으면 "없음"으로 잘못 답하거나, 새로 저장한 값이 파일의 옛 값에 덮임 |
