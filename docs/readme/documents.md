# 결정 기록과 문서 모음

[← README로 돌아가기](../../README.md)

mini-redis를 만들며 따른 요구사항, 팀이 내린 결정, 데모와 측정의 근거를 항목별로 풀어 적었습니다. 각 항목 끝에 원문 문서 링크가 있습니다.

## 요구사항

과제 가이드에서 뽑아 낸 요구사항은 열두 가지입니다.

첫째, 해시 테이블을 직접 구현한 키-값 저장소여야 하고 저장, 조회, 삭제가 동작해야 합니다. 둘째, 그 해시 테이블의 설계 원리와 구현 과정, 주요 함수의 동작을 설명할 수 있어야 합니다. 셋째, 저장소를 다른 프로그램이 쓸 수 있도록 API 형태로 열어야 합니다. 넷째, 여러 요청이 동시에 들어와도 값이 깨지지 않는 구조여야 합니다. 다섯째, 보관 기간이 지난 값을 요청받았을 때 어떻게 할지 정해야 합니다. 여섯째, 저장된 값이 더 이상 맞지 않게 되었을 때 지우는 방법(무효화)이 있어야 합니다.

품질 쪽 요구사항도 있습니다. 저장, 조회, 삭제를 단위 테스트로 확인해야 하고, 간단한 API를 만들어 그 응답을 mini-redis에 저장해 쓰는 기능 테스트를 해야 합니다. 엣지 케이스를 최대한 고려해야 하고, mini-redis를 쓸 때와 쓰지 않을 때의 성능을 비교해야 합니다.

선택 요구사항은 두 가지입니다. 서버가 꺼져도 데이터를 최대한 지키는 방법과, 다른 팀과 차별화되는 기능입니다.

반대로 하지 않기로 한 것도 정했습니다. 문자열 말고 다른 Redis 자료형과 명령, 실제 Redis 클라이언트와의 호환, 여러 서버로 나누거나 복제하는 기능, 인증은 만들지 않습니다.

## 결정 참고사항

설계 문서에는 팀이 확정한 결정과, 각자 구현할 때 참고하도록 제안한 결정이 함께 적혀 있습니다.

팀이 확정한 결정은 세 가지입니다. 사용 언어는 파이썬입니다. 팀 전체가 익숙하고 이어서 만들 미니 DBMS도 같은 언어로 만들기 때문입니다. API 형식은 HTTP입니다. 구현, 테스트, 시연이 모두 쉽기 때문입니다. 진행 방식은 금요일 저녁 8시까지 입력 검증까지 각자 구현한 뒤 하나를 골라 확정하고, 그 코드 위에서 나머지 일을 나눠 하는 것입니다. 세 사람 모두 해시 테이블을 직접 만들어 보고, 세 구현을 비교한 내용을 학습과 발표 재료로 쓰기 위해서입니다.

제안한 결정은 지켜도 되고 바꿔도 되는 참고용입니다.

- 키는 비어 있지 않은 문자열이고, 값은 JSON으로 표현할 수 있는 값입니다. API로 주고받을 수 있는 형태여야 하기 때문입니다.
- 값으로 `null`은 저장할 수 없습니다. 저장소의 `get`이 돌려주는 `None`이 언제나 "없음"만 뜻하게 하기 위해서입니다.
- 없는 키를 조회하면 저장소는 `None`, API는 404를 돌려줍니다. 없는 키를 삭제하면 오류가 아니라 저장소는 `False`, API는 200 `{"deleted": false}`를 돌려줍니다. 삭제의 목적은 "값이 없는 상태"이므로 이미 없어도 실패가 아니기 때문입니다.
- 이미 있는 키에 저장하면 값을 덮어씁니다.
- 충돌은 체이닝으로 처리하고, 체인의 각 항목에 키와 값을 함께 저장합니다. 같은 칸에 있는 항목 중 키가 일치하는 것을 찾아야 하기 때문입니다. 칸을 언제, 얼마나 늘릴지는 각자 정합니다.
- 만료는 남은 시간이 아니라 만료 "시점"을 저장합니다. 조회할 때 지금 시각과 비교만 하면 되기 때문입니다. `ttl`은 초 단위이고 0보다 커야 합니다. 0 이하는 저장하자마자 만료되어 의미가 없습니다.
- 만료 확인은 조회할 때 확인하고 지우는 지연 삭제를 기본으로 합니다. 만료된 키는 없는 키와 똑같이 다룹니다.
- 덮어쓰면 만료 시점도 새로 정하고, `ttl`을 생략하면 만료가 없어집니다. 이전 값의 만료 시점이 새 값에 남으면 예상하지 못한 삭제가 생기기 때문입니다.
- 동시 요청은 저장소 전체에 lock 하나로 막고, lock은 저장소 안에서 처리합니다. 저장소를 쓰는 쪽에서 lock을 빠뜨릴 수 없게 하기 위해서입니다.
- 입력 조건을 어긴 요청은 서버가 걸러 400으로 응답하고, 저장소에는 올바른 입력만 넘깁니다.

## 과제 원문과 팀 학습 원칙

과제의 학습 목표는 AI를 도구로 삼아 프로젝트에 몰입하고, 실무 기술을 직접 만들어 보며 CS 개념이 실제 시스템에서 어떻게 동작하는지 경험하는 것입니다. 결과물뿐 아니라 과정도 중요하며, AI가 작성한 코드라도 원리를 설명할 수 있어야 합니다.

학습 원칙은 세 가지입니다. 학습보다 구현이 우선이라 AI를 적극적으로 써서 결과물을 먼저 만듭니다. 다만 결과물의 핵심 로직은 이해하고 설명할 수 있어야 하고, 코드를 AI로 생성했다면 반드시 공부해 원리를 이해해야 합니다. 그리고 다른 팀과 차별화할 수 있는 추가 구현을 함께 고민합니다.

과제 본문은 해시 테이블로 키-값 저장소를 직접 만들고, 외부에서 쓸 수 있게 하고, 해시 테이블의 설계와 주요 함수를 설명할 수 있게 하는 것입니다. 기술 스택은 자유입니다. 고민할 지점으로는 동시성 문제를 막는 구조, 만료된 값의 처리, 외부에서 쓰기 쉬운 API, 저장된 데이터의 무효화, 그리고 선택으로 서버가 꺼져도 데이터를 지키는 방법이 주어졌습니다.

원문: [docs/REQUIREMENTS.md](../REQUIREMENTS.md)

## 팀 결정 기록

팀은 반드시 같아야 하는 것만 먼저 함께 정하고, 나머지는 각자 구현하면서 골랐습니다.

함께 정한 것은 이렇습니다. 언어는 파이썬입니다. AI가 쓴 코드도 읽고 직접 설명하기 쉽기 때문입니다. API는 HTTP입니다. `curl`이나 브라우저로 바로 시연할 수 있고, 실제 Redis 프로토콜(RESP)까지 맞추는 것은 과제 범위가 아니었기 때문입니다. 해시 테이블에는 파이썬 `dict`를 쓰지 않고, 칸 배열로만 `list`를 씁니다. 해시 계산, 충돌 처리, 확장을 직접 구현해야 과제 조건에 맞기 때문입니다. 서버는 HTTP만 알고 저장소는 저장만 알도록 나누어, 둘은 `set`, `get`, `delete` 세 함수로만 만나게 했습니다. 그래서 임시 `dict`를 직접 만든 해시 테이블로 바꿀 때 세 사람 모두 서버 코드를 고치지 않았습니다.

충돌 처리 방식이나 확장 기준 같은 구현 세부는 팀 규칙으로 고정하지 않았습니다. 언어와 API처럼 꼭 같아야 하는 것과 구현하며 정해지는 것을 구분하자는 의견에 따라, 설계 문서의 결정 목록도 "결정 기록"에서 "결정 참고사항"으로 이름을 바꿨습니다.

진행은 각자 구현하되 몇 단계마다 모여 서로의 선택을 짧게 공유하는 방식으로 했습니다. 끝까지 혼자 구현하고 마지막에 한 번에 비교하면 다룰 양이 너무 많아지기 때문입니다. 공유 자리에서 주고받은 피드백은 결정에 직접 반영되었습니다. 예를 들어 `None`을 "없음" 표시로 쓰면 진짜 `None` 값과 구분할 수 없다는 지적으로 `value: null`을 400으로 막았고, 만료 확인과 삭제 사이에 다른 저장이 끼어들 수 있다는 지적으로 조회 함수까지 lock으로 감쌌습니다.

원문: [docs/DECISIONS.md](../DECISIONS.md)

## 단계별 선택 비교

세 사람(김소망, 이현지, 김은기)이 같은 문제에 어떤 답을 골랐는지 비교했습니다.

서버 틀은 세 사람 모두 Flask를 골랐습니다. 코드가 짧아 해시 테이블에 집중할 수 있기 때문입니다. 포트는 두 사람이 8000, 한 사람이 5001을 썼고, 셋 다 5000을 피했습니다. macOS의 AirPlay 수신 기능이 5000을 쓰기 때문입니다.

해시 테이블은 세 사람 모두 체이닝으로 충돌을 처리했지만 체인 모양이 달랐습니다. 김소망과 김은기는 노드를 직접 만들어 연결 리스트로 이었고, 새 항목을 체인 맨 앞에 붙였습니다. 이현지는 파이썬 `list`에 `(키, 값)` 튜플을 넣고 맨 뒤에 붙였습니다. 연결 리스트는 칸 배열 말고 모든 것을 직접 만들어 노드를 끊고 잇는 과정을 설명할 수 있고, `list`는 코드가 가장 짧고 삭제가 한 줄로 끝납니다. 해시 함수는 김소망이 FNV-1a 64비트, 이현지가 31을 곱하며 더하는 32비트 방식을 직접 구현했고, 김은기는 처음에 파이썬 내장 `hash()`를 썼다가 직접 만든 함수로 바꿨습니다. 내장 `hash()`는 실행할 때마다 문자열의 해시 값이 달라져 어떤 키끼리 충돌하는지 다시 보여 줄 수 없기 때문입니다.

칸 수 확장은 세 사람이 같은 값을 골랐습니다. 키 수를 칸 수로 나눈 값이 0.75를 넘으면 칸을 2배로 늘리고, 칸 수는 줄이지 않습니다. 시작 칸 수만 8, 8, 4로 달랐습니다. 이 값은 정답이 아니라 속도와 메모리 사이에서 고르는 값이라고 정리했습니다. 2배로 늘리면 키 100개를 넣을 때 191번 옮기지만, 한 칸씩 늘리면 같은 조건에서 5,029번 옮긴다는 측정도 있었습니다.

만료에서 구조 차이가 가장 컸습니다. 세 사람 모두 만료 시점을 저장하고 지연 삭제를 썼지만, 김소망과 이현지는 저장소가 `(값, 만료 시점)` 묶음을 해시 테이블의 값으로 넣었고, 김은기는 해시 테이블 노드에 만료 시점 칸을 따로 두었습니다. 앞의 방식은 해시 테이블이 "키로 값을 찾는 일" 하나만 하고, 시계를 가짜로 바꿔 끼워 기다리지 않고 만료를 테스트할 수 있습니다. 뒤의 방식은 저장소 코드가 짧아지지만 해시 테이블이 두 가지 일을 하게 됩니다. 시계는 뒤로 가지 않는 `time.monotonic`을 골랐습니다. 컴퓨터 시각이 바뀌어도 만료가 흔들리지 않기 때문입니다.

lock은 세 사람의 결과가 같았습니다. 저장소 전체에 lock 하나를 두고 `set`, `get`, `delete`를 모두 감쌌습니다.

입력 검증은 응답이 가장 많이 갈린 부분입니다. 김소망과 이현지는 모르는 항목(예: `ttl`을 `ttI`로 잘못 쓴 경우), 아주 큰 정수 `ttl`, `Content-Type`이 없는 JSON을 모두 400으로 막았고, 김은기는 오타를 무시해 만료 없이 저장하거나 아주 큰 `ttl`에서 500 오류를 냈습니다. 없는 주소와 틀린 메서드에는 김소망과 김은기가 JSON으로, 이현지가 HTML로 404와 405를 돌려줬습니다.

원문: [docs/DECISIONS.md](../DECISIONS.md)

## 기준 구현을 고른 과정

입력 검증까지 각자 구현한 뒤 세 구현 중 하나를 기준으로 골라야 했습니다. 그 뒤의 일은 한 코드 위에서 나눠 해야 하기 때문입니다.

이현지가 세 브랜치를 입력 검증까지 끝낸 시점으로 맞춘 뒤, 같은 요청 23개를 세 서버에 똑같이 보내 비교했습니다. 각자의 테스트는 각자가 생각한 경우만 확인하므로, 같은 요청을 보내야 차이가 드러나기 때문입니다. 결과는 이렇습니다. 각자의 테스트는 김소망 31개, 이현지 56개, 김은기 7개가 모두 통과했습니다. 공통 요청에서 500 오류는 김은기 구현에서 아주 큰 정수 `ttl`로 1건 나왔습니다. 8개 스레드가 2,000번씩 동시에 저장한 뒤 사라진 값은 세 구현 모두 0건이었습니다. 만료 테스트는 김소망과 이현지가 가짜 시계를, 김은기가 실제로 기다리는 방식을 썼습니다.

선택 기준은 설계 문서에 미리 적어 둔 세 가지였습니다. 공통 테스트를 통과하는가, 읽고 설명하기 쉬운 코드인가, 결정 기록을 따르는가입니다.

결과로 김소망의 구현을 기준 구현으로 골랐습니다. 이유는 네 가지입니다. 세 사람의 장점이 이미 한 코드에 합쳐져 있었습니다. 검증은 이현지의 방식을, 없는 주소와 틀린 메서드의 JSON 응답은 김은기의 방식을 가져와 있었습니다. 같은 요청 23개에서 500 오류나 무시되는 오타 같은 빈틈이 없었습니다. 만료와 lock이 저장소에만 있어 해시 테이블을 따로 떼어 설명할 수 있었습니다. 그리고 고칠 것 없이 바로 다음 작업을 시작할 수 있었습니다.

고르지 않은 구현에서도 가져온 것이 있습니다. 이현지의 검증 함수 구성과 `ttl` 상한 10년, 계층별 테스트 장면(동시 저장과 삭제, 만료 뒤 다시 저장 등)을 가져왔고, 김은기가 정리한 "서버 안 캐시가 망가지는 다섯 장면"은 데모와 시연의 뼈대가 되었습니다.

기준 구현을 최종 확정한 회의의 회의록은 찾지 못해 확인이 필요합니다. 위 이유는 비교 보고서의 제안과 이후 분담 기록을 바탕으로 적었습니다.

## 알고도 남겨둔 약점

알고 있지만 과제 범위와 시간을 고려해 고치지 않은 약점이 여섯 가지 있습니다.

해시 값이 고정되어 있습니다. 해시 함수가 언제 실행해도 같은 값을 내므로, 한 칸에 몰리는 키를 미리 계산해 계속 보내면 체인이 길어져 서버가 느려집니다. 고정이어야 어떤 키끼리 충돌하는지 다시 보여 줄 수 있어 그대로 두었습니다. 실제 Redis는 실행할 때마다 다른 비밀 값을 섞는 해시 함수를 씁니다.

만료된 키를 지연 삭제로만 지웁니다. 아무도 다시 조회하지 않는 만료 키는 계속 남아 칸을 차지합니다. 일정 간격으로 만료 키를 찾아 지우는 정리 기능은 시간이 남으면 할 일로 미뤘습니다. 실제 Redis는 지연 삭제와 주기적 정리를 함께 씁니다.

칸을 늘릴 때 모든 키를 한 번에 옮깁니다. 키가 아주 많으면 확장하는 순간 다른 요청이 잠깐 멈춥니다. 과제 규모에서는 문제가 될 가능성이 낮아 그대로 두었습니다. 실제 Redis는 요청을 처리하는 사이사이에 조금씩 나눠 옮깁니다.

lock이 하나뿐입니다. 요청이 많아지면 모든 요청이 한 줄로 기다립니다. 대신 단순하고 틀리기 어렵습니다.

키와 값의 크기 제한이 없습니다. 아주 큰 값을 계속 보내면 메모리가 바닥납니다. 과제의 목적은 기능 확인이므로 제한을 두지 않기로 하고, 그 사실을 테스트로 고정해 두었습니다. 실제 Redis는 메모리 한도와, 한도에 닿았을 때 어떤 키를 지울지 정하는 정책이 있습니다.

서버를 다시 켜면 값이 모두 사라집니다. 값을 메모리에만 두기 때문입니다. 파일에 저장하고 시작할 때 되살리는 기능은 선택 요구사항으로 남겨 두었습니다.

## 데모 API 설계

데모 API는 mini-redis를 DB 앞의 캐시로 쓰는 앱입니다. 거래량 상위 종목 목록을 조회할 때 먼저 mini-redis를 보고, 값이 있으면 바로 응답하고, 없으면 DB에서 읽어 mini-redis에 넣은 뒤 응답합니다. 이렇게 앱이 캐시를 먼저 보고 없을 때 직접 채우는 방식을 Cache-Aside라고 부릅니다.

데모 API는 mini-redis 코드를 `import`하지 않고 HTTP로 호출합니다. 같은 프로그램 안에서 불러 쓰면 서버 밖의 공용 저장소라는 모습을 보여 줄 수 없고, 과제의 "외부에서 사용"을 보여 주려면 다른 서버로 접속해야 하기 때문입니다. 같은 이유로 mini-redis 코드는 데모를 만들면서 하나도 고치지 않았습니다.

종목 가격을 바꿀 때는 DB를 먼저 고치고 그다음 mini-redis의 키를 지웁니다. 캐시에 새 값을 덮어쓰지 않고 지우는 이유는, 덮어쓰면 DB 수정과 캐시 수정의 순서가 어긋날 때 옛 값이 남을 수 있기 때문입니다. 지우기만 하면 다음 조회가 DB에서 최신 값을 가져와 채웁니다. DB를 먼저 고치는 이유는, 캐시를 먼저 지우면 DB를 고치기 전에 다른 요청이 옛 값을 다시 캐시에 채울 수 있기 때문입니다.

mini-redis가 꺼져 있어도 데모 API는 DB에서 읽어 응답합니다. 캐시는 빠르기의 문제일 뿐 기능의 문제가 아니므로, 통신 실패를 "캐시에 값이 없음"과 똑같이 처리합니다.

가짜 DB는 SQLite 파일입니다. 데모 API를 여러 대 띄워도 원본 데이터는 하나여야 하기 때문입니다. 파이썬 `dict`로 두면 서버마다 DB가 따로 생겨 시연이 성립하지 않습니다.

비교를 위해 캐시를 서버 안에 두는 모드(`--cache local`)를 일부러 남겨 두었습니다. 앱 코드는 그대로 두고 캐시 위치만 바꿔 끼워, 서버가 여러 대일 때 서버 안 캐시에서 어떤 문제가 생기는지 먼저 보여 주기 위해서입니다.

로그인 세션도 별도 기능 없이 같은 `set`과 `get`으로 저장합니다. 세션도 결국 키-값이기 때문이고, 로그인 유지 시간(기본 30분)이 그대로 TTL이 됩니다.

## TTL 60초를 정한 근거

거래량 상위 종목 캐시의 TTL은 60초입니다.

TTL은 무효화를 대신하는 것이 아니라 안전망입니다. 가격을 바꿀 때 캐시를 제대로 지우면 TTL은 거의 쓰일 일이 없고, TTL이 실제로 일하는 순간은 캐시를 지우는 데 실패했을 때뿐입니다. 그래서 "얼마나 오래 캐시하고 싶은가"가 아니라 "캐시 삭제에 실패했을 때 사용자가 틀린 값을 보는 시간을 얼마까지 참을 수 있나"로 값을 정했습니다.

후보는 세 가지였습니다. 5초로 하면 틀린 값을 보는 시간은 최대 5초로 짧지만, 같은 목록을 계속 조회할 때 1분에 DB를 12번 읽게 되어 캐시 효과가 거의 없어집니다. 10분으로 하면 DB는 10분에 한 번만 읽지만, 캐시 삭제에 버그가 있으면 사용자가 10분 동안 틀린 가격을 봅니다. 60초는 1분에 DB를 한 번 읽고 틀린 값을 보는 시간도 최대 1분이라, 거래량 상위 종목 목록에 충분하다고 보고 골랐습니다.

시연 스크립트만 TTL을 600초로 씁니다. 발표 중 장면마다 멈춰 설명하는 사이 캐시가 만료되면 안 되기 때문입니다. 이 값은 코드의 기본값을 바꾸지 않고 환경변수 `DEMO_CACHE_TTL`로 넣습니다. 기본값을 바꾸면 운영 설정이 시연 편의에 끌려가기 때문입니다.

TTL을 짧게 줄여도 "데이터가 바뀌었는데 옛 값이 보이는" 문제는 풀리지 않습니다. 틀린 값을 보는 시간이 짧아질 뿐 없어지지 않고 DB 조회만 늘어납니다. 만료는 저장소가 시간이 되면 알아서 지우는 것이고, 무효화는 값이 바뀐 것을 아는 앱이 바로 지우는 것입니다. 진짜 해결은 값이 바뀌는 순간 지우는 무효화입니다.

## 측정 방법

같은 데모 API에서 캐시만 빼고 비교했습니다. `/stocks/top?nocache=1`로 조회하면 같은 코드 경로를 지나되 mini-redis를 건너뛰고 매번 DB를 읽습니다. 캐시 말고 다른 조건이 모두 같아야 차이가 캐시 때문이라고 말할 수 있기 때문입니다.

측정 조건은 이렇습니다. 가짜 DB는 조회마다 3초를 기다리게 했습니다(`DEMO_DB_DELAY`). 실제 DB가 디스크를 읽고 조건에 맞는 데이터를 찾는 시간을 흉내 낸 값입니다. 캐시 TTL은 60초입니다. mini-redis, 데모 API, 측정 스크립트를 한 컴퓨터에서 실행했고, 응답 시간은 요청을 보낸 측정 스크립트 쪽에서 쟀습니다. 사용자가 실제로 기다리는 시간이기 때문입니다.

각 경우를 10번씩 조회했고, 캐시를 쓸 때는 첫 조회와 그 이후를 나눠 쟀습니다. 첫 조회는 캐시가 비어 있어 DB를 읽으므로 느린 것이 정상이고, 이를 이후 조회와 섞어 평균을 내면 측정 횟수에 따라 숫자가 달라져 뜻이 없어지기 때문입니다. 응답 시간과 함께 DB 조회 횟수도 셌습니다. 빠르기의 배수는 가짜 DB에 넣은 지연 시간에 따라 얼마든지 달라지지만, DB 조회가 몇 번으로 줄었는지는 조건이 바뀌어도 의미가 같기 때문입니다.
