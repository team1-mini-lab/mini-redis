# 결정 기록과 문서 모음

[← README로 돌아가기](../../README.md)

mini-redis를 만들며 따른 요구사항, 팀이 내린 결정, 데모와 측정의 근거를 항목별로 정리했습니다. 각 항목 끝에 원문 문서 링크가 있습니다.

## 요구사항

과제 가이드에서 뽑아 낸 요구사항입니다.

**기능**

- 해시 테이블을 직접 구현한 키-값 저장소 (저장, 조회, 삭제)
- 해시 테이블의 설계 원리, 구현 과정, 주요 함수의 동작을 설명할 수 있음
- 다른 프로그램이 쓸 수 있는 API 구조
- 여러 요청이 동시에 들어와도 값이 깨지지 않는 구조
- 보관 기간이 지난 값을 요청받았을 때의 처리
- 저장된 값이 더 이상 맞지 않을 때 지우는 방법 (무효화)

**품질**

- 저장, 조회, 삭제를 단위 테스트로 확인
- 간단한 API의 응답을 mini-redis에 저장해 쓰는 기능 테스트
- 엣지 케이스 고려
- mini-redis를 쓸 때와 쓰지 않을 때의 성능 비교

**선택**

- 서버가 꺼져도 데이터를 최대한 지키는 방법
- 다른 팀과 차별화되는 기능

**하지 않기로 한 것**

- 문자열 말고 다른 Redis 자료형과 명령
- 실제 Redis 클라이언트와의 호환
- 여러 서버로 나누거나 복제하는 기능
- 인증

## 결정 참고사항

설계 문서에는 팀이 확정한 결정과, 각자 구현할 때 참고하도록 제안한 결정이 함께 적혀 있습니다.

**팀이 확정한 결정**

| 결정 | 이유 |
| --- | --- |
| 사용 언어는 파이썬 | 팀 전체가 익숙하고, 이어서 만들 미니 DBMS도 같은 언어로 만듦 |
| API 형식은 HTTP | 구현, 테스트, 시연이 모두 쉬움 |

**제안한 결정**

| 주제 | 제안 | 이유 |
| --- | --- | --- |
| 키와 값 | 키는 비어 있지 않은 문자열, 값은 JSON으로 표현할 수 있는 값 | API로 주고받을 수 있는 형태여야 함 |
| `null` 값 | 저장할 수 없음 | 저장소의 `get`이 돌려주는 `None`이 언제나 "없음"만 뜻하게 함 |
| 없는 키 조회 | 저장소는 `None`, API는 404 | "없음"을 값과 구분되는 방식으로 알림 |
| 없는 키 삭제 | 저장소는 `False`, API는 200 `{"deleted": false}` | 삭제의 목적은 "값이 없는 상태"이므로 이미 없어도 실패가 아님 |
| 같은 키에 다시 저장 | 덮어씀 | 캐시 값을 갱신하는 기본 동작 |
| 충돌 처리 | 체이닝. 체인의 각 항목에 키와 값을 함께 저장 | 같은 칸의 항목 중 키가 일치하는 것을 찾아야 함 |
| 칸 수 확장 | 언제, 얼마나 늘릴지는 각자 정함 | 구현해 보며 비교할 수 있는 선택 |
| 만료 저장 | 남은 시간이 아니라 만료 "시점"을 저장 | 조회할 때 지금 시각과 비교만 하면 됨 |
| `ttl` | 초 단위, 0보다 큰 숫자 | 0 이하는 저장하자마자 만료되어 의미가 없음 |
| 만료 확인 | 조회할 때 확인하고 지우는 지연 삭제. 만료된 키는 없는 키와 똑같이 다룸 | 과제 요구에 해당하고 비용이 작음 |
| 덮어쓸 때 만료 | 만료 시점도 새로 정함. `ttl`을 생략하면 만료 없음 | 이전 값의 만료 시점이 새 값에 남으면 예상하지 못한 삭제가 생김 |
| 동시 요청 | 저장소 전체에 lock 하나, lock은 저장소 안에서 처리 | 단순하고, 저장소를 쓰는 쪽에서 lock을 빠뜨릴 수 없음 |
| 입력 검증 | 조건을 어긴 요청은 서버가 400으로 응답. 저장소에는 올바른 입력만 넘김 | 검증을 한 곳에 모아 저장소를 단순하게 유지 |

## 과제 원문과 팀 학습 원칙

**학습 목표**

- AI를 도구로 삼아 프로젝트에 몰입합니다.
- 실무 기술을 직접 만들어 보며 CS 개념이 실제 시스템에서 어떻게 동작하는지 경험합니다.
- 결과물뿐 아니라 과정도 중요합니다. AI가 작성한 코드라도 원리를 설명할 수 있어야 합니다.

**학습 원칙**

- 학습보다 구현이 우선입니다. AI를 적극적으로 써서 결과물을 먼저 만듭니다.
- 핵심 로직은 이해하고 설명할 수 있어야 합니다. 코드를 AI로 생성했다면 반드시 공부해 원리를 이해합니다.
- 다른 팀과 차별화할 수 있는 추가 구현을 함께 고민합니다.

**과제 본문**

해시 테이블로 키-값 저장소를 직접 만들고, 외부에서 쓸 수 있게 하고, 해시 테이블의 설계와 주요 함수를 설명할 수 있게 하는 것입니다. 기술 스택은 자유입니다. 고민할 지점으로 다음이 주어졌습니다.

- 동시성 문제를 막는 구조
- 만료된 값의 처리
- 외부에서 쓰기 쉬운 API
- 저장된 데이터의 무효화
- (선택) 서버가 꺼져도 데이터를 지키는 방법

## 팀 결정 기록

팀은 반드시 같아야 하는 것만 먼저 함께 정하고, 나머지는 각자 구현하면서 골랐습니다.

**함께 정한 것**

| 항목 | 결정 | 이유 |
| --- | --- | --- |
| 언어 | 파이썬 | AI가 쓴 코드도 읽고 직접 설명하기 쉬움 |
| API | HTTP | `curl`이나 브라우저로 바로 시연 가능. 실제 Redis 프로토콜(RESP)까지 맞추는 것은 과제 범위가 아님 |
| `dict` 사용 | 해시 테이블에는 쓰지 않고, 칸 배열로만 `list`를 씀 | 해시 계산, 충돌 처리, 확장을 직접 구현해야 과제 조건에 맞음 |
| 역할 나누기 | 서버는 HTTP만, 저장소는 저장만 앎. 둘은 `set`, `get`, `delete`로만 만남 | 임시 `dict`를 직접 만든 해시 테이블로 바꿀 때 세 사람 모두 서버 코드를 고치지 않음 |
| 구현 세부 | 팀 규칙으로 고정하지 않고 각자 선택 | 꼭 같아야 하는 것과 구현하며 정해지는 것을 구분. 그래서 설계 문서의 "결정 기록"을 "결정 참고사항"으로 이름을 바꿈 |

**진행 방식**

각자 구현하되 몇 단계마다 모여 서로의 선택을 짧게 공유했습니다. 끝까지 혼자 구현하고 마지막에 한 번에 비교하면 다룰 양이 너무 많아지기 때문입니다.

**공유 자리의 피드백이 결정이 된 예**

- `None`을 "없음" 표시로 쓰면 진짜 `None` 값과 구분할 수 없다 → `value: null`을 400으로 막음
- 만료 확인과 삭제 사이에 다른 저장이 끼어들면 새 값이 지워진다 → 조회 함수까지 lock으로 감쌈
- `(값, 만료 시점)`이 묶음 하나라면 칸을 늘려 다시 넣어도 만료가 사라지지 않아야 한다 → 확인 후 테스트 추가
- 만료와 무효화는 다른 일이다 → 데모 API가 DB를 고친 뒤 캐시 키를 지우고, TTL은 안전망으로 둠

원문: [docs/DECISIONS.md](../DECISIONS.md)

## 단계별 선택 비교

세 사람(김소망, 이현지, 김은기)이 같은 문제에 어떤 답을 골랐는지 비교했습니다.

| 주제 | 김소망 | 이현지 | 김은기 |
| --- | --- | --- | --- |
| 서버 도구 | Flask | Flask | Flask |
| 포트 | 8000 | 8000 | 5001 |
| 충돌 처리 | 체이닝 | 체이닝 | 체이닝 |
| 체인 모양 | 직접 만든 노드의 연결 리스트 | 파이썬 `list`에 `(키, 값)` 튜플 | 직접 만든 노드의 연결 리스트 |
| 새 항목 위치 | 맨 앞 | 맨 뒤 | 맨 앞 |
| 해시 함수 | FNV-1a 64비트 직접 구현 | 31을 곱하며 더하는 32비트 직접 구현 | 내장 `hash()` → 직접 만든 함수로 변경 |
| 확장 기준과 배수 | 0.75 넘으면 2배 | 같음 | 같음 |
| 시작 칸 수 | 8 | 8 | 4 |
| 만료 시점을 두는 곳 | 저장소가 `(값, 만료 시점)` 묶음으로 저장 | 같음 | 해시 테이블 노드에 따로 칸을 둠 |
| 만료 테스트 | 가짜 시계 | 가짜 시계 | 실제로 기다림 |
| lock | 저장소 전체에 하나, `set`·`get`·`delete` 모두 | 같음 | 같음 |
| 모르는 항목 (`ttl` 오타 `ttI`) | 400 | 400 | 200, 오타를 무시하고 만료 없이 저장 |
| 아주 큰 정수 `ttl` | 400 | 400 | 500 |
| 없는 주소, 틀린 메서드 | JSON 404, 405 | HTML 404, 405 | JSON 404, 405 |

갈린 선택의 장단점입니다.

- **연결 리스트 vs `list`**: 연결 리스트는 칸 배열 말고 모든 것을 직접 만들어 노드를 끊고 잇는 과정을 설명할 수 있습니다. `list`는 코드가 가장 짧고 삭제가 한 줄로 끝나지만, 잇고 끊는 일을 파이썬이 대신 합니다.
- **직접 만든 해시 함수 vs 내장 `hash()`**: 내장 `hash()`는 실행할 때마다 문자열의 해시 값이 달라져 어떤 키끼리 충돌하는지 다시 보여 줄 수 없습니다. 그래서 김은기도 직접 만든 함수로 바꿨습니다.
- **만료를 저장소에 vs 노드에**: 저장소에 두면 해시 테이블이 "키로 값을 찾는 일" 하나만 하고, 시계를 가짜로 바꿔 끼워 기다리지 않고 테스트할 수 있습니다. 노드에 두면 저장소 코드는 짧아지지만 해시 테이블이 두 가지 일을 합니다.

확장 기준 0.75와 배수 2배는 세 사람이 같았지만 팀이 정한 값은 아닙니다. 정답이 아니라 속도와 메모리 사이에서 고르는 값이라고 정리했습니다. 2배로 늘리면 키 100개를 넣을 때 191번 옮기지만, 한 칸씩 늘리면 같은 조건에서 5,029번 옮긴다는 측정도 있었습니다.

## 기준 구현을 고른 과정

입력 검증까지 각자 구현한 뒤 하나를 기준으로 골라야 했습니다. 그 뒤의 일은 한 코드 위에서 나눠 해야 하기 때문입니다.

**비교 방법**

이현지가 세 브랜치를 입력 검증까지 끝낸 시점으로 맞춘 뒤, 같은 요청 23개를 세 서버에 똑같이 보냈습니다. 각자의 테스트는 각자가 생각한 경우만 확인하므로, 같은 요청을 보내야 차이가 드러나기 때문입니다.

| 확인한 것 | 김소망 | 이현지 | 김은기 |
| --- | --- | --- | --- |
| 각자의 테스트 | 31개 통과 | 56개 통과 | 7개 통과 |
| 공통 요청 23개에서 500 오류 | 없음 | 없음 | 1건 (아주 큰 정수 `ttl`) |
| 8개 스레드가 2,000번씩 동시 저장 후 사라진 값 | 0건 | 0건 | 0건 |
| 만료 테스트 | 가짜 시계 | 가짜 시계 | 실제로 기다림 |

**선택 기준** (설계 문서에 미리 적어 둔 것)

- 공통 테스트를 통과하는가
- 읽고 설명하기 쉬운 코드인가
- 결정 기록을 따르는가

**결과: 김소망의 구현을 기준 구현으로 골랐습니다.**

- 세 사람의 장점이 이미 한 코드에 합쳐져 있었습니다. 검증은 이현지의 방식, 없는 주소와 틀린 메서드의 JSON 응답은 김은기의 방식입니다.
- 같은 요청 23개에서 500 오류나 무시되는 오타 같은 빈틈이 없었습니다.
- 만료와 lock이 저장소에만 있어 해시 테이블을 따로 떼어 설명할 수 있었습니다.
- 고칠 것 없이 바로 다음 작업을 시작할 수 있었습니다.

**고르지 않은 구현에서 가져온 것**

| 가져온 것 | 어디서 |
| --- | --- |
| 검증 함수의 구성, `ttl` 상한 10년, 모르는 항목 400 | 이현지 |
| 계층별 테스트 장면 (동시 저장과 삭제, 만료 뒤 다시 저장 등) | 이현지 |
| JSON 404, 405 응답 | 김은기 |
| 서버 안 캐시가 망가지는 다섯 장면 (데모와 시연의 뼈대) | 김은기 |

## 알고도 남겨둔 약점

알고 있지만 과제 범위와 시간을 고려해 고치지 않은 약점입니다.

| 약점 | 무슨 일이 생기나 | 남겨 둔 이유 | 실제 Redis |
| --- | --- | --- | --- |
| 해시 값이 고정 | 한 칸에 몰리는 키를 미리 계산해 계속 보내면 체인이 길어져 서버가 느려짐 | 고정이어야 어떤 키끼리 충돌하는지 다시 보여 줄 수 있음 | 실행마다 다른 비밀 값을 섞는 해시 함수 |
| 지연 삭제만 있음 | 아무도 다시 조회하지 않는 만료 키가 계속 남아 칸을 차지함 | 주기적 정리는 시간이 남으면 할 일로 미룸 | 지연 삭제와 주기적 정리를 함께 씀 |
| 한 번에 전부 옮김 | 키가 아주 많으면 칸을 늘리는 순간 다른 요청이 잠깐 멈춤 | 과제 규모에서는 문제가 될 가능성이 낮음 | 요청 처리 사이사이에 조금씩 나눠 옮김 |
| lock 하나 | 요청이 많아지면 모든 요청이 한 줄로 기다림 | 단순하고 틀리기 어려움 | 명령을 하나씩 실행 |
| 크기 제한 없음 | 아주 큰 값을 계속 보내면 메모리가 바닥남 | 목적이 기능 확인. 제한이 없다는 사실을 테스트로 고정 | 메모리 한도와, 한도에 닿으면 어떤 키를 지울지 정하는 정책 |
| 재시작하면 사라짐 | 서버를 다시 켜면 값이 모두 없어짐 | 파일 저장은 선택 요구사항으로 남김 | 파일에 저장하는 방식이 두 가지 있음 |

## 데모 API 설계

데모 API는 mini-redis를 DB 앞의 캐시로 쓰는 앱입니다. 거래량 상위 종목 목록을 조회하는 흐름은 이렇습니다.

1. 먼저 mini-redis에서 찾습니다.
2. 있으면 바로 응답합니다.
3. 없으면 DB에서 읽어 mini-redis에 넣은 뒤 응답합니다.

이렇게 앱이 캐시를 먼저 보고, 없을 때 직접 채우는 방식을 Cache-Aside라고 부릅니다.

| 결정 | 이유 |
| --- | --- |
| mini-redis를 `import`하지 않고 HTTP로 호출 | 같은 프로그램 안에서 불러 쓰면 서버 밖의 공용 저장소라는 모습을 보여 줄 수 없음. 과제의 "외부에서 사용"을 보여 줌 |
| mini-redis 코드는 고치지 않음 | 데모는 mini-redis를 "쓰는 쪽"임 |
| 가격을 바꾸면 캐시에 새 값을 덮어쓰지 않고 키를 지움 | 덮어쓰면 DB 수정과 캐시 수정의 순서가 어긋날 때 옛 값이 남을 수 있음. 지우면 다음 조회가 DB에서 최신 값을 채움 |
| DB를 먼저 고치고 그다음 캐시를 지움 | 캐시를 먼저 지우면 DB를 고치기 전에 다른 요청이 옛 값을 다시 캐시에 채울 수 있음 |
| 종목 하나가 바뀌어도 목록 키 전체를 지움 | 거래량 상위 목록을 키 하나에 통째로 저장하기 때문. 다음 조회 한 번으로 다시 채워짐 |
| 캐시 삭제가 실패해도 가격 수정은 성공으로 처리 | DB가 이미 고쳐졌으므로 200으로 응답. 응답의 `cache_invalidated`가 캐시 삭제(무효화) 성공 여부를 알려 줌: 지웠으면 `true`, mini-redis가 꺼져 있어 못 지웠으면 `false`. 못 지운 옛 값은 캐시에 남지만 TTL(60초)이 지나면 사라지고, 다음 조회가 DB에서 새 가격을 가져옴 |
| mini-redis가 꺼져 있어도 DB에서 읽어 응답 | 캐시는 빠르기의 문제일 뿐 기능의 문제가 아님. 통신 실패를 "캐시에 값이 없음"과 똑같이 처리 |
| mini-redis 호출 타임아웃 1초 | mini-redis가 응답하지 않을 때 고객이 오래 기다리지 않고 바로 DB로 넘어가게 |
| 가짜 DB는 SQLite 파일 | 데모 API를 여러 대 띄워도 원본 데이터는 하나여야 함. 파이썬 `dict`로 두면 서버마다 DB가 따로 생김 |
| 서버 안에 캐시를 두는 모드(`--cache local`)를 일부러 남김 | 앱 코드는 그대로 두고 캐시 위치만 바꿔, 서버가 여러 대일 때 생기는 문제를 먼저 보여 줌 |
| 서버 안 캐시도 mini-redis와 같은 TTL·지연 삭제로 구현 | 두 경우의 차이가 캐시 위치 하나뿐이어야 공정한 비교가 됨 |
| 로그인 세션도 같은 `set`, `get`으로 저장 | 세션도 결국 키-값임. 로그인 유지 시간(기본 30분)이 그대로 TTL이 됨 |

## TTL 60초를 정한 근거

거래량 상위 종목 캐시의 TTL은 60초입니다.

TTL은 무효화를 대신하는 것이 아니라 안전망입니다. 가격을 바꿀 때 캐시를 제대로 지우면 TTL은 거의 쓰일 일이 없고, 실제로 일하는 순간은 캐시를 지우는 데 실패했을 때뿐입니다. 그래서 "얼마나 오래 캐시하고 싶은가"가 아니라 "캐시 삭제에 실패했을 때 사용자가 틀린 값을 보는 시간을 얼마까지 참을 수 있나"로 값을 정했습니다.

| TTL | 틀린 값을 보는 최대 시간 | 같은 목록을 계속 조회할 때 1분당 DB 조회 | 판단 |
| --- | --- | --- | --- |
| 5초 | 5초 | 12번 | 캐시 효과가 거의 없어짐 |
| **60초** | **60초** | **1번** | **거래량 상위 종목 목록에 충분해 채택** |
| 10분 | 10분 | 0.1번 | 캐시 삭제에 버그가 있으면 10분 동안 틀린 가격이 보임 |

**시연 스크립트만 600초**

- 발표 중 장면마다 멈춰 설명하는 사이 캐시가 만료되면 안 되기 때문입니다.
- 코드의 기본값을 바꾸지 않고 환경변수 `DEMO_CACHE_TTL`로 넣습니다. 기본값을 바꾸면 운영 설정이 시연 편의에 끌려가기 때문입니다.

**TTL을 줄여도 풀리지 않는 문제**

- "데이터가 바뀌었는데 옛 값이 보이는" 문제는 TTL을 줄여도 없어지지 않습니다. 틀린 값을 보는 시간이 짧아질 뿐이고 DB 조회만 늘어납니다.
- 만료는 저장소가 시간이 되면 알아서 지우는 것이고, 무효화는 값이 바뀐 것을 아는 앱이 바로 지우는 것입니다.
- 진짜 해결은 값이 바뀌는 순간 지우는 무효화입니다.

## 측정 방법

같은 데모 API에서 캐시만 빼고 비교했습니다. `/stocks/top?nocache=1`로 조회하면 같은 코드 경로를 지나되 mini-redis를 건너뛰고 매번 DB를 읽습니다. 캐시 말고 다른 조건이 모두 같아야 차이가 캐시 때문이라고 말할 수 있기 때문입니다.

**측정 조건**

| 조건 | 값 |
| --- | --- |
| 가짜 DB 지연 | 조회마다 3초 (`DEMO_DB_DELAY`) |
| 캐시 TTL | 60초 |
| 실행 환경 | mini-redis, 데모 API, 측정 스크립트를 한 컴퓨터에서 실행 |
| 응답 시간을 잰 곳 | 요청을 보낸 측정 스크립트 쪽 |
| 횟수 | 각 경우 10번 |

**측정할 때 지킨 것**

- 캐시를 쓸 때는 첫 조회(미스)와 그 이후(히트)를 나눠 쟀습니다. 첫 조회는 캐시가 비어 있어 느린 것이 정상이고, 이후 조회와 섞어 평균을 내면 측정 횟수에 따라 숫자가 달라져 뜻이 없어지기 때문입니다.
- 응답 시간과 함께 DB 조회 횟수도 셌습니다. 빠르기의 배수는 가짜 DB에 넣은 지연 시간에 따라 얼마든지 달라지지만, DB 조회가 몇 번으로 줄었는지는 조건이 바뀌어도 의미가 같기 때문입니다.

**다시 재는 방법**

mini-redis와 데모 API를 띄운 뒤 `python -m bench.benchmark --markdown`을 실행합니다. 결과는 [성능 비교](./performance.md) 문서에 있습니다.
