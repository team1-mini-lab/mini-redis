# 왜 레디스인가 — 설명자료

> 한 줄 요약: 로컬 캐시는 상태를 **각 서버의 메모리에 묶어둔다.** 레디스는 그 상태를 **서버 밖의 빠른 공용 저장소로 빼낸다.**
>
> 직접 해 보기: [시뮬레이터를 브라우저에서 실행](https://htmlpreview.github.io/?https://github.com/team1-mini-lab/mini-redis/blob/eungi/docs/study/why_redis_simulator.html)하면 아래 다섯 장면을 버튼으로 재현할 수 있습니다.

## 1. 출발점: 로컬 캐시는 좋은 도구다

DB에서 상품 하나를 조회하면 약 200ms가 걸립니다. 같은 상품을 계속 DB에 묻지 않으려고, 한 번 가져온 값을 서버 메모리(딕셔너리)에 저장해 두는 것이 로컬 캐시입니다. 두 번째부터는 약 0.01ms로 끝납니다.

```python
cache = {}                      # 서버 메모리 안의 캐시

def get_product(pid):
    if pid in cache:
        return cache[pid]       # 0.01ms
    product = db.query(pid)     # 200ms
    cache[pid] = product
    return product
```

로그인 정보(세션)도 같은 방식으로 서버 메모리에 둡니다. 네트워크를 타지 않아 가장 빠르고, DB 요청이 줄어 DB도 보호됩니다. **서버가 한 대라면 여기서 끝이고, 레디스는 필요 없습니다.**

## 2. 조건: 서버가 여러 대가 된다

트래픽(세일 날 10배), 장애(한 대가 죽으면 전체 정지), 배포(한 대씩 바꿔야 무중단) 때문에 같은 서버를 A, B, C 세 대로 늘리고 앞에 로드밸런서를 둡니다. 코드는 그대로이고, 서버마다 **자기 메모리에** `cache`와 `sessions`를 따로 들고 있습니다.

로드밸런서는 요청을 A, B, C에 번갈아 보내므로, **같은 사람의 요청도 매번 다른 서버로 갈 수 있습니다.** 요청은 항상 사람이 쓰는 브라우저(고객 또는 관리자)에서 출발하고, 서버는 받은 요청을 처리할 뿐입니다.

> 조건은 문제가 터지는 **상황**이지 원인이 아닙니다. 같은 코드도 서버가 한 대면 멀쩡합니다.

## 3. 문제: 다섯 장면

다섯 장면은 모두 **2번의 구조 그대로, 아무것도 고치지 않은 상태**에서 벌어집니다. 특히 ④는 ①②를 고치려다 생긴 문제가 아닙니다.

### ① 새로고침할 때마다 가격이 바뀐다

관리자가 키보드를 50,000원에서 40,000원으로 할인합니다. 이 요청은 서버 A로 가서, A는 DB와 **자기 캐시만** 고칩니다. B와 C의 캐시에는 50,000원이 그대로 남습니다. 고객이 새로고침할 때마다 40,000 → 50,000 → 50,000원이 번갈아 보입니다. 서버 A는 서버 B, C의 메모리를 지울 방법이 없기 때문입니다.

### ② 로그인했는데 다음 클릭에서 풀린다

kim의 로그인 요청이 서버 A로 가서, A가 세션을 자기 메모리에 저장합니다. kim의 다음 클릭이 서버 B로 가면 B에는 세션이 없어 "로그인하세요"가 뜹니다. 로그인 기록이 서버 A의 메모리에만 있기 때문입니다.

### ③ 배포할 때마다 DB가 휘청인다

평소에는 캐시가 차 있어 DB에 초당 100건 정도만 갑니다. 배포로 A, B, C를 재시작하면 프로세스 메모리가 날아가 **캐시 세 개가 동시에 비고**, 모든 요청이 DB로 몰립니다(예: 초당 5,000건). 세일 날 서버 D를 추가해도 빈 캐시로 시작하니 오히려 DB 부하가 늘어납니다. 캐시의 목적이 DB 보호인데, 가장 위험한 순간에 지키지 못합니다.

### ④ 값이 같아도 낭비다

인기 상품 1,000개를 캐시에 올리려면 A도 DB에 1,000번, B도 1,000번, C도 1,000번 묻고, 내용이 똑같은 사본을 세 벌 저장합니다. 서버가 10대면 메모리도 DB 조회도 10배입니다. 캐시 크기는 각 서버의 메모리 한도를 넘을 수 없습니다.

> ①은 서버마다 값이 **달라서** 생기는 문제, ④는 값이 **같아도** 생기는 문제입니다.

### ⑤ 함께 세야 하는 값은 만들 수 없다

한정판 키보드가 1개 남았을 때, kim은 서버 A에서, lee는 서버 B에서 동시에 재고를 확인합니다. 둘 다 "1개 남음"을 보고 주문해서 **1개를 2명에게 팔아버립니다.** 같은 이유로 아래 기능들도 만들 수 없습니다.

| 만들고 싶은 기능 | 로컬 캐시로 하면 |
| --- | --- |
| 상품 전체 조회수 | 서버마다 따로 셈. 합칠 곳이 없음 |
| 쿠폰 선착순 100명 | 서버마다 100명씩, 300명이 받음 |
| 결제 버튼 두 번 클릭 방지 | 다른 서버로 가면 둘 다 결제됨 |
| 로그인 5회 실패 시 잠금 | 서버를 바꿔가며 15번까지 시도 |

### 누가 겪고, 어떻게 드러나나

| 장면 | 누가 겪나 | 어떻게 드러나나 |
| --- | --- | --- |
| ① 가격 | 고객 | 화면의 가격이 오락가락, 문의·환불 |
| ② 로그아웃 | 고객 | 클릭할 때마다 로그인이 풀림 |
| ③ 배포 | 운영자, DB | 배포 때마다 DB 요청 폭증, 심하면 고객도 느려짐 |
| ④ 중복 | 회사 | 고객 눈엔 안 보임, 메모리·DB 비용이 서버 수만큼 |
| ⑤ 재고 | 개발자 → 회사·고객 | 기능을 못 만듦, 억지로 만들면 초과 판매 |

정리하면 **①②는 고객이 바로 보는 문제, ③④는 고객 눈엔 안 보이는 운영·비용 문제, ⑤는 기능 자체를 못 만드는 문제**입니다.

## 4. 뿌리: 원인은 하나다

> **상태가 각 서버 프로세스의 메모리에 묶여 있다.**

| 장면 | 같은 원인을 다르게 본 것 |
| --- | --- |
| ① 가격 | 서버마다 `cache` 상태가 다름 |
| ② 로그아웃 | 서버마다 `sessions` 상태가 다름 |
| ③ 배포 | 재시작하며 상태가 같이 사라짐 |
| ④ 중복 | 같은 상태를 서버마다 따로 들고 있음 |
| ⑤ 재고 | 모두가 봐야 할 상태를 둘 곳이 없음 |

**상태**는 같은 요청인데 답을 다르게 만드는, 서버가 기억하고 있는 데이터입니다. `mypage("abc")`는 똑같은 요청이지만, 로그인 전에는 "로그인하세요", 로그인 후에는 "kim님 마이페이지"를 돌려줍니다. `sessions`에 무엇이 들었느냐에 따라 답이 바뀌는 것입니다.

자기만 아는 상태를 들고 있는 서버를 **stateful**, 상태를 들고 있지 않아 어느 서버로 가도 같은 답을 주는 서버를 **stateless**라고 합니다. 은행 창구 직원마다 자기 수첩에 손님 기록을 적는 상황을 떠올리면 됩니다. 손님은 그 직원에게 가야만 일이 이어지고, 직원이 퇴근하면 기록도 사라집니다.

세션과 캐시는 둘 다 상태지만 잃었을 때 결과가 다릅니다. **세션은 원본**이라 잃으면 다시 로그인해야 하고(기능이 깨짐), **캐시는 사본**이라 DB에서 다시 채우면 됩니다(잠깐 느려짐).

### 증상만 막으면 하나가 남는다

| 시도 | 막는 것 | 남는 것 |
| --- | --- | --- |
| 캐시 TTL을 짧게 (예: 5초) | ① 불일치 시간이 짧아짐 | 5초 동안은 여전히 다름. 짧을수록 DB 요청이 늘어 ③이 심해짐 |
| 오래된 키를 지워 메모리 절약 | ④ 메모리 사용 | 서버마다 따로 있는 구조는 그대로 |
| 스티키 세션 (같은 사용자는 같은 서버로) | ② 로그아웃 | 그 서버가 죽으면 세션도 사라짐. 부하 쏠림 |

## 5. 해결: 상태를 서버 밖 한 곳으로 뺀다

앱 서버는 기억하지 않게(stateless) 하고, 기억은 서버 밖 공용 저장소 한 곳에 둡니다.

```
사용자 → 로드밸런서 → 서버 A / B / C (상태 없음, 코드만)
                          ↓
              공용 저장소 (cache · sessions · 재고 · 조회수)
                          ↓
                       DB (원본)
```

| 장면 | 풀리는 방식 |
| --- | --- |
| ① | 가격을 바꾸면 공용 저장소의 키 하나만 지운다 → 모두 새 가격 |
| ② | 세션이 공용 저장소에 → 어느 서버로 가도 kim |
| ③ | 저장소는 앱과 따로 산다 → 앱을 재시작해도 캐시 유지 |
| ④ | 한 벌만 저장하고, DB에도 한 번만 묻는다 |
| ⑤ | 모두가 같은 재고 키를 본다 → 1개면 한 명만 |

공용 저장소를 어디에 둘지 후보는 셋입니다. 앱 서버 안은 곧 로컬 캐시라 탈락, DB는 공유는 되지만 느리고 캐시의 목적(DB 보호)과 정반대입니다. **메모리 기반 별도 서버**가 공유되고, RAM이라 빠르고, DB 앞에서 요청을 막아 줍니다. 이것이 레디스입니다. 리액트가 상태와 화면을 분리했다면, 레디스는 상태와 서버를 분리합니다.

## 6. 레디스 이전과 이후

2003년 **Memcached**가 "메모리 기반 캐시 서버를 따로 두고 모두 공유한다"는 구조를 자리 잡게 했습니다. 하지만 값은 문자열만 저장할 수 있었습니다. 랭킹에 점수 하나를 넣으려면 전체를 꺼내서(GET) 앱에서 고치고 다시 통째로 저장(SET)해야 했고, 그 사이에 다른 서버가 끼어들면 값이 사라졌습니다. 공유를 얻는 대신 자료구조를 잃은 셈입니다.

2009년 **레디스**는 공유하면서 자료구조와 운영 기능까지 되찾았습니다.

| 요구 | 로컬 캐시 | Memcached | 레디스 |
| --- | --- | --- | --- |
| 모든 서버가 같은 값 보기 | ✗ | ✓ | ✓ |
| 구조 있는 데이터를 일부만 수정 | ✓ 내 메모리 | ✗ 문자열만 | ✓ List · Hash · Sorted Set |
| 여러 서버가 동시에 숫자 올리기 | ✗ | △ 숫자만 | ✓ INCR |
| 같은 작업을 한 서버만 (락) | ✗ | △ 흉내만 | ✓ SET NX EX |
| 재시작해도 데이터 유지 | ✗ | ✗ | ✓ RDB / AOF |
| 캐시 서버가 죽어도 서비스 유지 | 해당 없음 | ✗ | ✓ Replication |
| 데이터가 늘면 나눠 담기 | ✗ | △ 앱이 직접 | ✓ Cluster |
| 서버끼리 "값이 바뀌었다" 알리기 | ✗ | ✗ | ✓ Pub/Sub |

### 읽고·고치고·쓰기를 레디스 안에서 한 번에

조회수가 100일 때 서버 A와 B가 거의 동시에 GET으로 100을 읽고, 각자 101을 SET하면 두 번 올렸는데 결과는 101입니다. 레디스는 `INCR` 한 명령으로 읽기·더하기·쓰기를 끝내고, 명령을 한 스레드에서 하나씩 순서대로 처리하므로 중간에 아무도 끼어들 수 없습니다(원자적). 재고는 `DECR` 결과가 0 미만이면 주문을 취소하면 됩니다. 원칙은 **읽고 쓰기를 앱에서 나눠 하지 말고, 레디스 안에서 한 번에 끝낸다**입니다.

## 7. 레디스를 "쓴다"는 것의 의미

레디스는 라이브러리가 아니라 **따로 돌아가는 서버 프로그램**입니다. DB처럼 별도로 켜 두고, 앱 서버 A, B, C가 모두 네트워크로 같은 레디스에 접속해 명령을 보냅니다. 코드로는 서버 메모리의 딕셔너리에 읽고 쓰던 부분을 레디스 명령으로 바꾸는 일입니다.

```python
r = redis.Redis(host="레디스서버주소", port=6379)   # A, B, C 모두 같은 곳에 접속

def get_product(pid):                                # Cache-Aside 읽기
    v = r.get(f"product:{pid}")
    if v:
        return v                                     # 있으면 바로 반환 (DB 안 감)
    product = db.query(pid)                          # 없으면 DB
    r.set(f"product:{pid}", product, ex=60)          # 60초 TTL로 저장
    return product

def update_price(pid, price):                        # Cache-Aside 쓰기 (장면 ①)
    db.update(pid, price)
    r.delete(f"product:{pid}")                       # 키 하나만 지우면 A, B, C 모두 해결

r.set("session:abc", "kim")                          # 로그인 (장면 ②)

left = r.decr("stock:keyboard")                      # 재고 차감 (장면 ⑤)
if left < 0:
    r.incr("stock:keyboard")
    cancel_order()
```

원본은 항상 DB이고, 레디스는 빠른 사본입니다. 쓸 때 레디스 키를 **지우는 것**이 장면 ①을 실제로 막는 방법입니다.

### 만료와 무효화: 무엇을, 어디서, 언제, 누가 지우나

캐시에서 값이 사라지는 길은 두 가지이고, 함께 씁니다. 무효화가 놓친 경우를 만료가 안전망으로 잡아 줍니다.

| | 만료 (expiration) | 무효화 (invalidation) |
| --- | --- | --- |
| 무엇을 | TTL이 붙은 키 | 원본(DB)이 바뀐 데이터의 캐시 키 |
| 언제 | 정해 둔 시간이 지나면 | 원본을 고친 직후 |
| 누가 지우나 | 저장소(레디스). 앱은 저장할 때 TTL만 정함 | 앱이 직접 삭제 요청(DEL) |
| 어디서 | 저장소 안: 조회할 때 확인(지연 삭제) + 주기적 정리 | 앱의 쓰기 코드: DB 수정 → 키 삭제 (Cache-Aside) |
| 놓치면 | 조회되지 않는 만료 키가 메모리에 남음 | 옛 값이 TTL이 끝날 때까지 보임 |
| 우리 미니 레디스 | `hash_table.py`의 `get`·`delete`가 `expire_at`을 확인해 지연 삭제 (4단계). 주기적 정리는 13단계(선택) | `DELETE /delete` API (1단계). 앱이 쓰는 쪽은 8단계 데모 API에서 "원본 수정 시 캐시 삭제" |

## 8. 우리 과제: 왜 해시 테이블인가

레디스는 두 층입니다. **바깥 층은 키로 값을 찾는 해시 테이블 하나**, 안쪽 층은 찾은 값의 모양(String, List, Set, Sorted Set, Hash)입니다. 어떤 명령이든 첫 단계는 "해시 테이블에서 키를 찾기"이므로, 해시 테이블은 자료구조 중 하나가 아니라 모든 값으로 가는 입구입니다.

캐시에 오는 질문은 항상 "이 키의 값 줘"라서 순서나 범위가 필요 없습니다. 리스트는 O(N), 트리는 O(log N)에 쓰지 않는 정렬 비용까지 내지만, 해시 테이블은 칸 번호를 바로 계산해 O(1)로 찾습니다.

아래 표는 레디스의 기능을 우리 단계와 실제 코드에 연결하고, 그렇게 정한 이유를 적은 것입니다. 자세한 결정 과정은 [DECISIONS.md](../eungi/DECISIONS.md)에 있습니다.

| 레디스의 기능 | 우리 단계 | 우리 코드에서 | 이유 | 상태 |
| --- | --- | --- | --- | --- |
| 키로 값 찾기 (모든 명령의 입구) | 2, 3 | `hash_table.py`: `_hash`(다항식 해시, 곱하는 수 131) → `% capacity`로 칸 번호, 같은 칸은 `Node` 연결 리스트로 체이닝(맨 앞 삽입), 항목 수 ÷ 칸 수가 0.75를 넘으면 칸을 2배로 늘려 재배치 | 체이닝은 구현과 설명이 단순함. 0.75와 2배는 확장 비용을 평균적으로 일정하게 유지. 해시 함수는 팀 회의에서 직접 구현으로 결정 | 완료 |
| EXPIRE 자동 삭제 | 4 / 13 | `Node.expire_at = time.monotonic() + ttl`, `get`·`delete`에서 지났으면 지움(지연 삭제) | 과제 요구가 "만료된 값을 요청받았을 때"의 처리라 지연 삭제로 충족, 비용이 작음. 시계 보정에 흔들리지 않게 monotonic 사용 | 4 완료, 13 선택 |
| 동시 접근 안전 | 5 | `store.py`의 `Store`가 `HashTable`을 감싸고 모든 함수를 lock 하나로 보호 | Flask가 요청을 여러 스레드로 받음. 지연 삭제 때문에 조회도 쓰기가 될 수 있어 조회에도 lock. 레디스는 싱글 스레드로 같은 효과 | 완료 |
| 잘못된 명령 거절 | 6 | `server.py`가 빈 키, `null` 값, 0 이하·문자열·`true`인 `ttl`, JSON이 아닌 본문을 400으로 거절 | 저장소에는 올바른 입력만 보내 저장소를 단순하게 유지 | 완료 |

## 9. 언제 로컬 캐시, 언제 레디스?

| 데이터 성격 | 로컬 캐시 | 레디스 |
| --- | --- | --- |
| 거의 안 바뀜 (카테고리 목록, 설정) | 적합 | 굳이 필요 없음 |
| 가끔 바뀌고 잠깐 늦어도 됨 (공지 목록) | TTL로 버틸 수 있음 | 더 안전함 |
| 자주 바뀌고 정확해야 함 (가격, 재고) | 부적합 | 필요 |
| 모든 서버가 함께 써야 함 (세션, 락, 카운터) | 불가능 | 필요 |

기준은 **바뀌는 데이터**와 **함께 써야 하는 데이터** 두 가지입니다. 실무에서는 섞어 씁니다: 로컬 캐시(가장 빠름) → 레디스(공유) → DB(원본).

## 10. 레디스도 공짜는 아니다, 그래서 이렇게 보완한다

| 비용 | 무엇이 문제인가 | 보완 |
| --- | --- | --- |
| 네트워크 비용 | 로컬은 나노초, 레디스는 약 1ms (DB보다는 훨씬 빠름) | 거의 안 바뀌는 데이터는 로컬 캐시와 함께(2단 캐시). 여러 명령은 파이프라이닝으로 한 번에, 연결은 커넥션 풀로 재사용 |
| 새로운 단일 장애점 | 모든 서버가 레디스 한 대에 의존 | Replication + Sentinel로 자동 장애 조치, 커지면 Cluster. 레디스가 죽어도 앱은 DB로 바로 가게 설계(Cache-Aside라 가능) |
| DB 대체가 아님 | 영속성이 있어도 설정에 따라 마지막 몇 초~몇 분은 잃을 수 있음 | 원본은 DB에 둔다. 캐시는 지워져도 DB에서 다시 채우는 구조로. 꼭 남겨야 할 레디스 데이터는 AOF(everysec)로 손실을 약 1초로 줄임 |
| 메모리 한도 | RAM이 꽉 차면 더 못 쓰거나 키를 지움 | 캐시 키에 TTL을 붙이고, maxmemory와 삭제 정책(예: allkeys-lru) 설정. 필요한 필드만 저장 |

### 헷갈리기 쉬운 짝

- **파일 저장(RDB/AOF)은 단일 장애점의 해법이 아닙니다.** 파일 저장은 레디스를 *재시작한 뒤* 데이터를 되살리는 용도입니다. 레디스가 죽어 있는 *동안* 서비스를 이어 주는 것은 복제(Replication)와 Sentinel의 자동 장애 조치입니다.
- **TTL은 "DB 대체가 아님"의 해법이 아닙니다.** TTL은 데이터가 너무 오래되지 않게 하고 메모리를 비우는 장치라서 메모리 한도와 신선도 쪽 보완책입니다. 데이터를 잃을 수 있다는 문제는 원본을 DB에 두는 것으로 풉니다.

## 예상 질문

**Q. 스티키 세션이면 되지 않나요?** 로그아웃(②)만 막힙니다. 그 서버가 죽으면 세션이 사라지고, 나머지 장면은 그대로입니다.

**Q. DB에 세션을 저장하면?** 공유는 되지만 느리고, DB 보호라는 캐시의 목적과 반대입니다.

**Q. 레디스가 있으면 로컬 캐시는 안 쓰나요?** 섞어 씁니다. 거의 안 바뀌는 데이터는 로컬 캐시가 가장 빠릅니다.

**Q. 레디스가 죽으면?** 복제와 Sentinel로 다른 레디스가 이어받고, 그 사이 앱은 DB로 직접 가도록 짭니다.

**Q. 레디스는 싱글 스레드인데 우리는 왜 lock을 쓰나요?** 우리 구현은 여러 요청을 동시에 받을 수 있어서, lock으로 "한 번에 하나씩"이라는 같은 효과를 냅니다.
