# 미니 레디스 · 미니 DBMS 전체 그림

구현을 시작하기 전에 두 과제가 무엇을 만드는 것인지, 서로 어떤 관계인지를 한 번에 훑기 위한 문서입니다.
세부 구현은 다루지 않습니다. 각 과제의 범위와 접점은 과제별 `DESIGN.md`에 정리합니다.

## 1. 한 줄 흐름

**미니 레디스**

```
외부 요청 → 서버가 명령 해석 → 메모리의 해시 테이블에 저장/조회 → 응답
```

**미니 DBMS**

```
외부 요청 → SQL 파싱 → 실행 (id 조건이면 B+ 트리로 위치 찾기) → 파일 읽기/쓰기 → 응답
```

## 2. 출발점이 되는 문제

"인기 상품 목록" 화면이 있다고 가정합니다.

- 목록을 만들려면 데이터베이스에서 수백만 건을 계산해야 해서 한 번 조회에 3초가 걸립니다.
- 이 화면은 1초에 수백 명이 봅니다.

요청이 올 때마다 같은 계산을 반복하는 대신, 한 번 계산한 결과를 저장해 두고 다음 요청부터는 저장된 것을 돌려줍니다.
이 방식을 **캐시(cache)** 라고 하고, 그 저장소 역할을 하는 것이 레디스입니다.

```
요청 → 레디스에 결과가 있나?
         ├─ 있음 → 바로 응답
         └─ 없음 → DBMS에서 조회 (느림) → 레디스에 저장 → 응답
```

DBMS가 원본을 보관하고, 레디스가 그 앞에서 자주 쓰는 결과를 잠시 보관합니다.

이것은 레디스가 푸는 첫 번째 문제일 뿐입니다. 캐시를 웹 서버 안의 변수가 아니라 별도 서버에 두는 이유, 메모리에 두는 이유, 그리고 그 선택이 만드는 문제들(만료, 동시성, 데이터 유지)이 이어서 나옵니다. 이 흐름은 `REDIS_OVERVIEW.md` 1절에 정리되어 있습니다.

## 3. 미니 레디스

### 값을 즉시 찾는 방법: 해시 테이블

레디스는 값을 저장할 때 이름표(키)를 붙입니다. 수십만 개 중에서 원하는 키를 하나씩 비교하지 않고 바로 찾기 위해 해시 테이블을 씁니다.

```
hash("인기상품") → 큰 숫자 → 칸 수로 나눈 나머지 → 3

배열:  [0] [1] [2] [3: "인기상품" → 상품 목록] [4] ...
```

- 해시 함수가 키를 숫자로 바꾸고, 그 숫자로 배열의 몇 번 칸인지 정합니다.
- 저장할 때와 찾을 때 같은 계산을 하므로, 데이터가 많아져도 찾는 시간이 거의 같습니다.
- 서로 다른 키가 같은 칸에 배정되는 **충돌**을 처리하는 방법이 구현의 핵심입니다.
- 파이썬의 `dict`를 그대로 쓰지 않고 직접 구현하는 것이 과제의 요구사항입니다.

### 메모리에 저장한다는 것

- 메모리에 두기 때문에 빠릅니다.
- 서버가 꺼지면 데이터가 사라집니다. 캐시는 원본이 DBMS에 있으므로 다시 계산하면 됩니다.
- 다만 꺼진 직후에는 캐시가 비어 있어 요청 전부가 DBMS로 몰립니다. 이것이 "서버 다운 시 데이터 유지"가 선택 항목으로 있는 이유입니다.

### 과제의 중점 포인트와의 대응

| 과제 항목 | 의미 |
| --- | --- |
| 외부에서 사용 가능한 API | 다른 프로그램이 저장/조회/삭제를 요청할 수 있는 서버 |
| 만료된 값의 처리 | 저장할 때 보관 기간을 정하고, 기간이 지난 값은 돌려주지 않음 |
| 데이터 무효화 | 원본이 바뀌었을 때 저장된 값을 직접 지움 |
| 동시성 | 여러 요청이 같은 데이터를 동시에 건드릴 때 문제가 없도록 하는 구조 |
| 성능 비교 | 레디스를 거칠 때와 매번 원본을 조회할 때의 응답 시간 차이 |
| (선택) 서버 다운 시 데이터 유지 | 메모리의 내용을 파일에도 남겨 두는 방식 |

## 4. 미니 DBMS

### 레디스 방식을 그대로 쓸 수 없는 이유

DBMS는 원본 데이터를 보관하므로 요구 조건이 다릅니다.

| 요구 조건 | 레디스 방식의 한계 | DBMS의 해결 |
| --- | --- | --- |
| 서버가 꺼져도 데이터 유지 | 메모리는 꺼지면 사라짐 | 파일에 저장 |
| 다양한 조건으로 조회 | 해시 테이블은 키 하나로만 찾음 | SQL로 조건을 표현 |
| 범위 조건 (id 100~200) | 해시는 키를 뒤섞어 배치하므로 전부 확인해야 함 | 정렬을 유지하는 B+ 트리 |

### 빨리 찾는 방법: 정렬과 인덱스

파일에 100만 건이 있을 때 `WHERE id = 987654`를 첫 줄부터 읽어 찾으면 느립니다.
정렬되어 있으면 가운데를 보고 절반씩 버릴 수 있어서 수십 번 이내의 비교로 찾습니다.

데이터 파일 자체를 매번 다시 정렬할 수는 없으므로, "id → 그 데이터가 파일의 어디에 있는지"만 정렬해서 담은 별도의 구조를 만듭니다. 이것이 **인덱스**이고, 이를 나무 모양으로 구현한 것이 **B+ 트리**입니다.

```
B+ 트리 (인덱스)                    데이터 파일
id 987654 → "파일의 987654번째 줄"  →  987654,지영,28
```

과제는 id에만 인덱스를 만듭니다.

| 조회 | 찾는 방식 | 속도 |
| --- | --- | --- |
| `WHERE id = 987654` | B+ 트리로 위치를 찾아 그 줄만 읽음 | 빠름 |
| `WHERE name = '지영'` | 파일을 처음부터 끝까지 읽으며 비교 (선형 탐색) | 느림 |

Phase 2의 성능 비교는 이 차이를 숫자로 보여주는 것입니다.

### 세 단계의 연결

| 단계 | 만드는 것 | 앞 단계와의 관계 |
| --- | --- | --- |
| Phase 1 | SQL 처리기: 파싱 → 실행 → 파일 저장, CLI | 기본 엔진 |
| Phase 2 | B+ 트리 인덱스, 100만 건 성능 비교 | Phase 1의 실행 단계에서 id 조건이면 인덱스를 사용 |
| Phase 3 | API 서버 + 스레드 풀 | Phase 1+2 전체를 감싸 외부에서 호출 가능하게 함 |

세 단계는 하나의 시스템을 나눈 것이므로, Phase 1의 결정(예: 파일 저장 형식)이 Phase 2에 영향을 줍니다.
DBMS를 시작할 때 세 단계를 함께 보고 범위와 접점을 정합니다.

## 5. 둘의 차이

| | 미니 레디스 | 미니 DBMS |
| --- | --- | --- |
| 역할 | 결과를 잠시 보관 (캐시) | 원본을 영구 보관 |
| 저장 위치 | 메모리 | 파일 |
| 서버가 꺼지면 | 사라짐 | 남아 있음 |
| 찾는 방법 | 키 하나로 즉시 | SQL로 다양한 조건 |
| 핵심 자료구조 | 해시 테이블 | B+ 트리 |
| 그 자료구조를 쓰는 이유 | 정확히 일치하는 키를 가장 빠르게 찾음 | 정렬을 유지해 범위 조건도 처리 |
| 낡은 데이터 문제 | 만료, 무효화로 처리 | 원본이므로 해당 없음 |

## 6. 둘에 공통인 부분

- **외부에서 호출하는 서버**: 레디스의 API와 DBMS Phase 3이 같은 종류의 작업입니다.
- **동시성**: 여러 요청이 같은 데이터를 동시에 건드릴 때의 문제를 둘 다 다룹니다.

레디스에서 먼저 경험한 서버 구조와 동시성 처리를 DBMS Phase 3에서 다시 활용합니다.
