# 왜 레디스인가

> **한 줄 요약**
> 로컬 캐시는 상태(캐시·세션)를 **각 서버의 메모리에 묶어두기** 때문에, 서버가 여러 대가 되는 순간 서버마다 다른 답을 주고, 로그인이 풀리고, 배포할 때마다 DB가 휘청인다.
> 레디스는 그 상태를 **서버 밖의 빠른 공용 저장소로 빼내서**, 앱 서버가 몇 대든 모두가 같은 상태를 보게 하고 DB를 보호한다.

이 문서는 "레디스를 어떻게 쓰나(HOW)"보다 **"레디스가 무슨 문제를 풀려고 나왔나(WHAT)"**를 설명합니다.
해시 테이블 구현은 [REDIS_OVERVIEW.md](./REDIS_OVERVIEW.md), 범위와 단계는 [DESIGN.md](../DESIGN.md)를 참고합니다.

---

## 한눈에 보는 흐름

리액트가 "상태와 화면을 분리하자"는 목표가 아니라 **"DOM을 직접 고치니 화면이 어긋난다"는 고통**에서 출발했듯이, 레디스도 **로컬 캐시가 일으키는 고통**에서 출발합니다.

```
1. 출발점   로컬 캐시는 빠르고 좋은 도구다. 서버 한 대면 이걸로 충분하다.
               ↓
2. 조건     그런데 서버가 여러 대가 된다.
               ↓
3. 문제     그 순간 로컬 캐시가 다섯 가지를 망가뜨린다.
               ↓
4. 뿌리     다섯 가지의 원인은 하나다: 상태가 각 서버에 묶여 있다.
               ↓
5. 해결     상태를 서버 밖 한 곳으로 뺀다 → 레디스
```

두 단어만 먼저 짚고 갑니다.

- **조건**: 문제가 **터지는 상황**입니다. 원인은 아닙니다. 똑같은 코드라도 서버가 한 대면 아무 문제가 없고, 여러 대가 되는 순간 문제가 드러납니다.
- **뿌리**: 겉으로 보이는 다섯 가지 증상을 **하나로 묶는 진짜 원인**입니다. 증상을 하나씩 막는 대신 뿌리를 고쳐야 다섯 개가 한 번에 풀립니다.

아래에서는 **"정글마켓"**이라는 쇼핑몰 하나를 예로 끝까지 따라갑니다.

---

## 1. 출발점: 로컬 캐시는 좋은 도구다

정글마켓의 상품 조회는 DB를 거치면 200ms가 걸립니다. 같은 상품을 계속 DB에 묻지 않으려고 **서버 메모리에 저장**합니다.

```python
cache = {}                               # 서버 메모리 안의 캐시

def get_product(product_id):
    if product_id in cache:              # 있으면 바로 (0.01ms)
        return cache[product_id]
    product = db.query(product_id)       # 없으면 DB (200ms)
    cache[product_id] = product
    return product
```

```
첫 번째 조회:  캐시에 없음 → DB  → 200ms
두 번째 조회:  캐시에 있음        → 0.01ms
```

- 네트워크를 타지 않아서 **가장 빠릅니다.**
- DB에 가는 요청이 줄어서 **DB를 보호합니다.** 캐시의 원래 목적이 이것입니다.
- 로그인 정보(세션)도 같은 방식으로 서버 메모리에 둡니다.

**서버가 한 대라면 여기서 끝입니다. 레디스는 필요 없습니다.**

---

## 2. 조건: 서버가 여러 대가 된다

정글마켓이 커지면서 서버 한 대로는 버틸 수 없게 됩니다.

| 이유 | 상황 |
| --- | --- |
| 트래픽 | 세일 날 접속자가 10배. 서버 한 대를 더 좋게 만드는 건 한계가 있어서, 같은 서버를 여러 대 둠 |
| 장애 | 서버 한 대가 죽으면 쇼핑몰 전체가 멈춤. 여러 대면 나머지가 받음 |
| 배포 | 새 버전을 올릴 때 한 대씩 바꿔야 쇼핑몰을 안 멈추고 배포 가능 |

그래서 서버를 A, B, C 세 대로 늘리고, 앞에 **로드밸런서**를 둡니다.

```
                  ┌─→ 서버 A  (자기 메모리에 cache, sessions)
사용자 → 로드밸런서 ─┼─→ 서버 B  (자기 메모리에 cache, sessions)
                  └─→ 서버 C  (자기 메모리에 cache, sessions)
                              ↓
                             DB
```

로드밸런서는 요청을 **A, B, C에 번갈아** 보냅니다. **같은 사용자의 요청도 매번 다른 서버로 갈 수 있습니다.**
코드는 1번과 똑같습니다. 서버만 세 대로 늘었을 뿐인데, 이제부터 문제가 터집니다.

## 3. 문제: 로컬 캐시가 망가뜨리는 다섯 장면

### 장면 ① 같은 상품인데 새로고침할 때마다 가격이 바뀐다

```
[처음]   키보드 가격 50,000원. 서버 A, B, C 모두 캐시에 50,000원.

[관리자] 가격을 40,000원으로 할인 → 로드밸런서가 서버 A로 보냄
         서버 A: DB 수정 + 자기 캐시도 40,000원
         서버 B, C: 모름. 캐시엔 여전히 50,000원

[고객]   새로고침 1 → 서버 A → 40,000원
         새로고침 2 → 서버 B → 50,000원
         새로고침 3 → 서버 C → 50,000원
         장바구니에 담았더니 결제 화면에선 또 다른 가격
```

- **왜?** 서버 A는 서버 B, C의 메모리를 지울 방법이 없습니다.
- **고객 입장**: "할인한다더니 가격이 왔다 갔다 하네?" → 문의, 환불 요청

### 장면 ② 로그인했는데 다음 클릭에서 로그아웃된다

```
[로그인]      kim 로그인 → 서버 A → A의 메모리: { 세션abc: kim }
[마이페이지]   kim 클릭 → 서버 B → B의 메모리: { }  → "로그인하세요"
```

- **왜?** 로그인 기록이 서버 A의 메모리에만 있습니다.
- **고객 입장**: 클릭할 때마다 로그인이 풀렸다 붙었다 함 → 쇼핑몰을 떠남

### 장면 ③ 배포할 때마다 DB가 휘청인다

```
[평소]    캐시가 차 있어서 DB에는 초당 100건만 감

[배포]    서버 A, B, C를 새 버전으로 재시작
          → 재시작하면 메모리가 날아감 → 캐시 3개가 동시에 텅 빔
          → 모든 요청이 캐시에 없음 → 전부 DB로
          → DB에 초당 5,000건 → DB 응답이 느려지거나 멈춤
```

- **같은 일이 서버를 늘릴 때도** 생깁니다. 세일 날 트래픽이 몰려서 서버 D를 추가했는데, D는 빈 캐시로 시작해서 **오히려 DB 부하를 늘립니다.**
- **왜?** 캐시가 서버 프로세스 안에 있어서, 프로세스가 새로 켜지면 같이 비어버립니다.
- 캐시의 목적은 DB 보호인데, **가장 위험한 순간에 DB를 지키지 못합니다.**

### 장면 ④ 같은 데이터를 세 번 저장하고, DB에 세 번 묻는다

```
인기 상품 1,000개를 캐시에 올리려면

서버 A: DB에 1,000번 조회 → 메모리에 1,000개
서버 B: DB에 1,000번 조회 → 메모리에 1,000개 (A와 똑같은 내용)
서버 C: DB에 1,000번 조회 → 메모리에 1,000개 (A와 똑같은 내용)
```

- 서버가 10대면 **메모리 10배, DB 조회 10배**입니다.
- 캐시 크기는 각 서버의 메모리 한도를 넘을 수 없습니다.

### 장면 ⑤ 함께 세야 하는 값은 아예 만들 수 없다

```
[한정판 키보드 1개 남음]

고객 kim → 서버 A: 재고 확인 → 1개 → "구매 가능" → 주문
고객 lee → 서버 B: 재고 확인 → 1개 → "구매 가능" → 주문

→ 1개를 2명에게 팔아버림
```

같은 이유로 이것들도 만들 수 없습니다.

| 만들고 싶은 기능 | 로컬 캐시로 하면 |
| --- | --- |
| 상품 전체 조회수 | 서버마다 따로 셈. 합칠 곳이 없음 |
| 쿠폰 선착순 100명 | 서버마다 100명씩 줘서 300명이 받음 |
| 결제 버튼 두 번 클릭 방지 | 두 클릭이 다른 서버로 가면 둘 다 결제됨 |
| 로그인 5회 실패 시 잠금 | 서버를 바꿔가며 시도하면 15번까지 됨 |

①~④는 "틀리거나 느려지는" 문제지만, ⑤는 **기능 자체를 만들 수 없는** 문제입니다.

## 4. 뿌리: 다섯 장면의 원인은 하나다

### 4-1. 상태란 무엇인가 (눈으로 보기)

**상태 = 같은 요청인데 답을 다르게 만드는, 서버가 기억하고 있는 데이터**입니다.

```python
sessions = {}                       # ← 이게 상태

def mypage(session_id):
    return sessions.get(session_id) or "로그인하세요"
```

```
똑같은 요청 mypage("abc")

로그인 전   sessions = {}                → "로그인하세요"
로그인 후   sessions = {"abc": "kim"}    → "kim님 마이페이지"
```

요청은 똑같은데 **`sessions`에 무엇이 들어 있느냐에 따라** 답이 바뀝니다. 반대로 상태가 없는 함수는 언제 불러도 답이 같습니다.

```python
def add(a, b):
    return a + b                    # 기억하는 게 없음 → 항상 같은 답
```

정글마켓 서버 안의 상태는 이것들입니다.

```
서버 A의 메모리
├─ cache    = { "키보드": 40000, "마우스": 20000 }   ← 상태 (사본)
└─ sessions = { "abc": "kim" }                      ← 상태 (원본)
```

### 4-2. 다섯 장면을 다시 보면

| 장면 | 실제로 일어난 일 |
| --- | --- |
| ① 가격이 바뀜 | 서버마다 **`cache` 상태가 다름** |
| ② 로그아웃 | 서버마다 **`sessions` 상태가 다름** |
| ③ 배포 때 DB 폭주 | 서버가 재시작되면서 **상태가 같이 사라짐** |
| ④ 중복 | **같은 상태를 서버마다 따로** 들고 있음 |
| ⑤ 재고, 쿠폰 | 모두가 봐야 할 상태를 **둘 곳이 없음** |

전부 같은 말입니다.

> **뿌리: 상태가 각 서버 프로세스의 메모리에 묶여 있다.**

### 4-3. stateful, stateless

- **stateful 서버**: 자기만 아는 상태를 들고 있는 서버. 요청이 **"그 서버"로 가야만** 제대로 처리됨
- **stateless 서버**: 상태를 안 들고 있는 서버. **어느 서버로 가도** 같은 답

정글마켓 서버 A, B, C는 로컬 캐시와 세션 때문에 **stateful**이 됐습니다. 그래서 서로 바꿔 쓸 수 없고, 마음대로 늘리거나 끄거나 재시작할 수 없습니다.

은행으로 비유하면, 창구 직원(서버)마다 **자기 수첩**에 손님 기록을 적는 상황입니다. 손님은 그 직원 창구로 가야만 일이 이어지고, 직원이 퇴근하면 기록도 사라집니다.

### 4-4. 세션과 캐시는 무엇이 다른가: 원본이냐 사본이냐

둘 다 서버를 stateful로 만들지만, **잃어버렸을 때의 결과**가 다릅니다.

| | 서버 메모리에 있는 것 | 서버가 꺼지면 | 결과 |
| --- | --- | --- | --- |
| 세션 | **원본**. 이 기록은 그 서버에만 있음 | 되살릴 곳이 없음 | 다시 로그인 (**기능이 깨짐**) |
| 캐시 | **사본**. 원본은 DB에 있음 | DB에서 다시 채울 수 있음 | 잠깐 느려짐 (**성능만 나빠짐**) |

### 4-5. 증상만 막으면 왜 안 되나

뿌리를 두고 증상만 막으려는 시도는 하나를 막으면 다른 게 남습니다.

| 시도 | 막는 것 | 남는 것 |
| --- | --- | --- |
| 캐시 TTL을 짧게 (예: 5초) | ① 가격 불일치가 짧아짐 | 5초 동안은 여전히 다름. TTL이 짧을수록 DB 요청이 늘어 ③이 심해짐. ②⑤는 그대로 |
| 메모리를 아끼고 오래된 키 삭제 | ④ 메모리 사용 | 서버마다 따로 있다는 구조는 그대로. ①②③⑤ 그대로 |
| 같은 사용자는 같은 서버로 (스티키 세션) | ② 로그아웃 | 그 서버가 죽으면 세션도 사라짐. 부하가 한쪽에 몰림. ①③④⑤ 그대로 |

## 5. 해결 방향: 상태를 서버 밖 한 곳으로 뺀다

**앱 서버는 기억하지 않게(stateless) 하고, 기억은 서버 밖 공용 저장소 한 곳에 둡니다.**

```
                  ┌─→ 서버 A  (상태 없음, 코드만)  ─┐
사용자 → 로드밸런서 ─┼─→ 서버 B  (상태 없음, 코드만)  ─┼─→ [공용 저장소]  cache, sessions, 재고, 조회수
                  └─→ 서버 C  (상태 없음, 코드만)  ─┘          ↓
                                                            DB (원본)
```

다섯 장면이 이렇게 바뀝니다.

| 장면 | 공용 저장소를 두면 |
| --- | --- |
| ① 가격 | 관리자가 가격을 바꾸면 공용 저장소의 키 하나만 지움 → A, B, C 모두 새 가격을 봄 |
| ② 로그인 | 세션이 공용 저장소에 → 어느 서버로 가도 kim으로 보임 |
| ③ 배포 | 공용 저장소는 앱과 따로 살아 있음 → 서버를 재시작해도 캐시가 그대로 → DB 평소대로 |
| ④ 중복 | 한 벌만 저장, DB에도 한 번만 물어봄 |
| ⑤ 재고 | 모두가 같은 `재고` 키를 봄 → "1개 남았을 때 한 명만" 처리 가능 |

### 그런데 공용 저장소를 어디에 두나?

| 후보 | 결과 |
| --- | --- |
| 앱 서버 안 | 그게 로컬 캐시. 처음 문제로 돌아감 |
| DB | 공유는 됨. 하지만 느리고, DB는 늘리기 어려워서 캐시의 목적(DB 보호)과 정반대 |
| **메모리 기반 별도 서버** | 공유되고, RAM이라 빠르고, DB 앞에서 요청을 막아줌 → **레디스** |

### 리액트와 나란히 보면

| | 리액트 | 레디스 |
| --- | --- | --- |
| 출발한 고통 | DOM을 직접 고치니 화면과 데이터가 어긋남 | 서버 메모리에 캐시·세션을 두니 서버끼리 어긋남 |
| 뿌리 | 상태가 화면 곳곳에 흩어져 있음 | 상태가 각 서버에 묶여 있음 |
| 해결 | 상태를 한 곳에 두고 `UI = f(state)` | 상태를 서버 밖 한 곳에 두고 서버는 읽고 쓰기만 |
| 결과 | 상태와 **화면** 분리 | 상태와 **서버** 분리 |

## 6. 레디스 이전의 시도들

| 시도 | 방식 | 한계 |
| --- | --- | --- |
| 스티키 세션 | 같은 사용자는 항상 같은 서버로 | 4-5 참고. ②만 막고 나머지는 그대로 |
| 세션 복제 | 서버끼리 세션을 서로 복사 | 서버가 늘수록 복사 트래픽 폭증 |
| DB에 저장 | 세션·캐시를 DB 테이블에 | 느림. DB 부하가 오히려 늘어남 |
| **Memcached (2003)** | 메모리 기반 캐시 서버를 따로 두고 모두 공유 | 5장의 구조를 처음 자리 잡게 함. 하지만 **값은 문자열만**, 재시작하면 전부 사라짐, 복제 없음 |

Memcached로 공유는 해결됐지만, 값을 **문자열로만** 저장하다 보니 새 문제가 생겼습니다.

```
[Memcached로 랭킹에 점수 하나 추가]
1. 랭킹 전체를 문자열로 꺼냄 (GET)        ← 네트워크 왕복
2. 앱에서 리스트로 바꾸고 점수 수정, 다시 정렬
3. 문자열로 바꿔 통째로 저장 (SET)         ← 네트워크 왕복
```

- 데이터가 크면 매번 전부 주고받습니다.
- 1~3 사이에 다른 서버가 끼어들면 **값이 사라집니다** (7-3).
- 로컬 캐시 시절엔 내 메모리라 자료구조를 마음대로 썼는데, **공유하려다 자료구조를 잃어버린** 셈입니다.

## 7. 레디스 (2009): 공유되는 곳에 자료구조와 연산을 둔다

### 7-1. 로컬 캐시, Memcached, 레디스 비교

"레디스는 데이터를 관리하고 운영할 수 있다"는 말은 너무 넓어서, 구체적인 요구로 나눠 비교합니다.

| 구분 | 구체적인 요구 | 로컬 캐시 | Memcached | 레디스 |
| --- | --- | --- | --- | --- |
| 공유 | 모든 서버가 같은 값 보기 | ❌ 서버마다 따로 | ✅ | ✅ |
| 데이터 다루기 | 랭킹·목록처럼 구조 있는 데이터를 일부만 수정 | ✅ 내 메모리라 자유롭게 | ❌ 문자열만. 꺼내서 고치고 통째로 저장 | ✅ Sorted Set, List, Hash |
| | 여러 서버가 동시에 숫자 올리기 | ❌ 서버마다 따로 셈 | △ 숫자만 가능 | ✅ `INCR`, `HINCRBY`, `ZINCRBY` |
| | 같은 작업을 한 서버만 하게 막기 | ❌ 맞출 곳이 없음 | △ 흉내는 가능 | ✅ `SET NX EX` (분산 락) |
| | 일정 시간 뒤 자동 삭제 | △ 라이브러리마다 다름 | ✅ | ✅ `EXPIRE` |
| 운영 | 재시작해도 데이터 유지 | ❌ | ❌ 전부 사라짐 | ✅ RDB / AOF |
| | 캐시 서버가 죽어도 서비스 유지 | 해당 없음 (앱과 같이 죽음) | ❌ 복제 없음 | ✅ Replication, Sentinel |
| | 데이터가 늘면 나눠 담기 | ❌ 서버 메모리 한도 | △ 앱이 직접 나눠야 함 | ✅ Cluster |
| | 서버끼리 "값이 바뀌었다" 알리기 | ❌ | ❌ | ✅ Pub/Sub, Stream |

- **로컬 캐시**: 자료구조는 자유롭지만 공유가 안 됨
- **Memcached**: 공유는 되지만 자료구조와 운영 기능을 잃음
- **레디스**: 공유하면서 자료구조와 운영 기능까지 되찾음

### 7-2. 다양한 자료구조가 왜 중요한가

핵심은 **값의 일부만 바꿀 때 통째로 꺼내지 않아도 된다**는 것입니다.

| 하고 싶은 일 | 문자열만 있으면 (Memcached) | 레디스 |
| --- | --- | --- |
| 사용자 포인트만 100 올리기 | 사용자 정보 전체 꺼냄 → JSON 해석 → 수정 → 전체 저장 | Hash `HINCRBY user:kim point 100` |
| 최근 본 상품 10개 유지 | 목록 전체 꺼냄 → 앞에 추가 → 10개로 자름 → 전체 저장 | List `LPUSH recent:kim 키보드` + `LTRIM recent:kim 0 9` |
| 이 사람이 좋아요 눌렀나? | 좋아요 목록 전체 꺼냄 → 앱에서 찾기 | Set `SISMEMBER likes:키보드 kim` |
| 판매 랭킹 점수 올리기 | 랭킹 전체 꺼냄 → 수정 → 다시 정렬 → 전체 저장 | Sorted Set `ZINCRBY best 1 키보드` |
| 조회수 올리기 | 꺼냄 → +1 → 저장 | String `INCR views:키보드` |

두 가지 효과가 있습니다.

1. **주고받는 데이터가 작아집니다.** 좋아요 10만 개 중 하나를 확인할 때 10만 개를 꺼내지 않습니다.
2. **한 명령으로 끝나서 끼어들 틈이 없습니다.** 아래 7-3의 동시성 문제가 같이 사라집니다.

### 7-3. 왜 "레디스 안에서" 처리해야 하나: 동시성

여러 서버가 같은 키를 **읽고 → 고치고 → 쓰면** 그 사이에 서로 끼어듭니다.

```
조회수 100
서버 A: GET → 100        서버 B: GET → 100
서버 A: SET 101          서버 B: SET 101
→ 두 번 올렸는데 101
```

- 레디스는 명령을 **한 스레드에서 하나씩 순서대로** 처리합니다.
- 그래서 `INCR`처럼 "읽기 + 더하기 + 쓰기"가 한 명령이면 중간에 아무도 끼어들 수 없습니다 (**원자적 명령**).
- 장면 ⑤의 재고 문제도 `DECR`(1 빼고 결과 반환) 한 번으로, 결과가 0 미만이면 주문을 취소하는 식으로 풉니다.
- 원칙: **읽고 쓰기를 앱에서 나눠 하지 말고 레디스 안에서 한 번에 끝낸다.**

## 8. 그럼 우리는 왜 해시 테이블을 만드나?

### 8-1. 해시 테이블은 "모든 자료구조를 찾는 입구"다

7장의 자료구조들은 **키로 찾은 다음 담겨 있는 값의 모양**입니다. 해시 테이블은 그중 하나가 아니라 **그 값을 찾아가는 입구**입니다.

```
[바깥 층] 키 → 값을 찾는 곳     = 해시 테이블 하나   ← 우리가 만드는 것
[안쪽 층] 찾은 값의 모양         = String, List, Set, Sorted Set, Hash ...
```

```python
redis = {                                  # 바깥: 해시 테이블 하나
    "price:키보드": "40000",                # 값: String
    "session:abc": {"user": "kim"},        # 값: Hash
    "best": [("키보드", 350), ...],         # 값: Sorted Set
}
```

어떤 명령이든 **첫 단계는 똑같습니다.**

```
GET price:키보드          → ① 해시 테이블에서 "price:키보드" 찾기 → ② 값 돌려주기
ZINCRBY best 1 키보드      → ① 해시 테이블에서 "best" 찾기         → ② Sorted Set 수정
LPUSH recent:kim 키보드    → ① 해시 테이블에서 "recent:kim" 찾기   → ② List에 추가
```

**①이 없으면 어떤 자료구조도 꺼낼 수 없습니다.** 키가 수백만 개여도 ①이 빨라야 레디스 전체가 빠릅니다.

### 8-2. 왜 하필 해시 테이블인가

캐시에 오는 질문은 항상 **"이 키의 값 줘"**입니다. 순서나 범위가 필요 없습니다.

| 후보 | 키 하나 찾기 | 맞나? |
| --- | --- | --- |
| 리스트 | 처음부터 하나씩 비교, O(N) | 키가 늘수록 느려짐 |
| 트리 | O(log N), 대신 정렬 순서를 유지 | 쓰지 않는 기능(정렬)에 비용을 냄 |
| **해시 테이블** | 해시로 칸 번호를 바로 계산, **O(1)** | "키로 바로 찾기"에 딱 맞음 |

### 8-3. 우리 범위와의 관계

우리 과제는 **바깥 층(해시 테이블)과 캐시로 쓰는 데 꼭 필요한 기능**을 만듭니다. 다른 자료형은 범위 밖입니다 (DESIGN.md "하지 않을 것").

| 7-1의 기능 | 우리 단계 |
| --- | --- |
| 키로 값 찾기 (모든 명령의 입구) | **2, 3** 해시 테이블, 칸 수 확장 |
| `EXPIRE` 자동 삭제 | **4** 만료(지연 삭제), **13** 주기적 정리 |
| 동시 접근 안전 | **5** lock (레디스는 싱글 스레드, 우리는 lock으로 같은 효과) |
| `INCR` 원자적 증가 | **12** 증가 명령 |
| RDB/AOF 데이터 유지 | **14** 데이터 유지 (선택) |
| DB 앞의 캐시로 쓰기 | **8** 데모 API, **9** 성능 비교 |
| Sorted Set, List, Replication, Cluster | 하지 않음 (해시 테이블 위에 얹는 기능) |

## 9. 실제로는 어떻게 쓰나: Cache-Aside

8단계 데모 API가 이 방식입니다.

```
읽기: 레디스에 있나? ─ 있음 → 바로 반환 (hit, DB 안 감)
                    └ 없음 → DB 조회 → 레디스에 저장(TTL) → 반환 (miss)

쓰기: DB 수정 → 레디스 키 삭제 → 다음 읽기 때 새 값으로 채워짐
```

- 쓰기 때 키를 **지우는 것**이 장면 ①(가격이 바뀜)을 실제로 막는 방법입니다.
- 원본은 항상 DB, 레디스는 빠른 사본입니다.

## 10. 언제 로컬 캐시, 언제 레디스?

| 데이터 성격 | 로컬 캐시 | 레디스 |
| --- | --- | --- |
| 거의 안 바뀜 (카테고리 목록, 설정) | 적합 | 굳이 필요 없음 |
| 가끔 바뀌고 잠깐 늦어도 됨 (공지 목록) | TTL로 버틸 수 있음 | 더 안전함 |
| 자주 바뀌고 정확해야 함 (가격, 재고) | 부적합 | 필요 |
| 모든 서버가 함께 써야 함 (세션, 락, 카운터) | 불가능 | 필요 |

- 레디스가 필요한 기준은 **"바뀌는 데이터"**와 **"함께 써야 하는 데이터"** 두 가지입니다.
- 실무에서는 섞어 씁니다: 로컬 캐시(가장 빠름) → 레디스(공유) → DB(원본).

## 11. 레디스의 비용과 주의점

| 주의점 | 내용 |
| --- | --- |
| 네트워크 비용 | 로컬 캐시보다 느림 (로컬 나노초 vs 레디스 약 1ms). 그래도 DB보다 훨씬 빠름. 그래서 HTTP 대신 가벼운 자체 프로토콜(RESP)을 씀 |
| 새로운 단일 장애점 | 모든 서버가 레디스 한 대에 의존 → Replication, Sentinel이 필요한 이유 |
| DB 대체가 아님 | 영속성이 있어도 설정에 따라 마지막 몇 초~몇 분은 잃을 수 있음. 원본은 DB에 |
| 메모리 한도 | RAM에 저장하므로 꽉 차면 정책에 따라 키를 지움 (예: 오래 안 쓴 키부터, LRU) |

## 12. 용어 정리

| 용어 | 뜻 |
| --- | --- |
| 로컬 캐시 | 앱 서버 프로세스 메모리 안의 캐시 |
| 상태 | 같은 요청인데 답을 다르게 만드는, 서버가 기억하고 있는 데이터 |
| stateful / stateless | 서버가 자기만 아는 상태를 들고 있나 / 아니나. "서버가 켜져 있나"가 아님 |
| 로드밸런서 | 요청을 여러 서버에 나눠 보내는 장치 |
| 일관성 | 모든 서버가 같은 질문에 같은 답을 주는 성질 |
| 콜드 스타트 | 서버가 막 켜져 캐시가 비어서 요청이 DB로 몰리는 상태 |
| 인메모리 | 디스크가 아니라 RAM에 저장. 빠르지만 꺼지면 사라짐 |
| TTL | Time To Live. 키에 붙이는 유통기한 |
| 원자적 명령 | 중간에 아무도 끼어들 수 없게 한 번에 실행되는 명령 |
| 분산 락 | 여러 서버 중 한 서버만 작업하도록 공용 저장소에 거는 잠금 |
| Cache-Aside | 앱이 캐시를 먼저 보고, 없으면 DB에서 가져와 캐시에 채우는 방식 |
