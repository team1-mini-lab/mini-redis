# 공부 노트 (eungi)

구현하면서 알게 된 개념을 정리합니다. 결정은 [DECISIONS.md](./DECISIONS.md)에 있습니다.

## 1. HTTP API를 쓴다는 말

외부 프로그램이 미니 레디스를 쓸 때 웹사이트에 요청을 보내는 것과 같은 방식으로 요청한다는 뜻임.

- 요청: 주소(URL), 메서드(GET, POST, DELETE), JSON 본문
- 응답: 상태 코드(200, 400, 404 등)와 JSON 본문
- 그래서 브라우저, curl, 파이썬 `requests` 같은 흔한 도구로 바로 쓸 수 있음
- 서버 쪽도 Flask 같은 도구가 요청을 해석해 주니 직접 만들 것이 적음

진짜 Redis는 HTTP를 쓰지 않고, TCP 연결 위에서 전용 텍스트 규약(RESP)으로 `SET name 현지` 같은 한 줄을 주고받음. 이걸 직접 만들려면 연결 관리, 문자열 해석, 오류 처리까지 구현해야 함. 이게 "자체 텍스트 규약"임.

| | RESTful HTTP API | Redis API |
| --- | --- | --- |
| 요청의 중심 | 리소스(명사), 동작은 HTTP 메서드 | 명령(동사) |
| 요청 예시 | `GET /keys/name` | `GET name` |
| 통신 | HTTP, 요청마다 독립적 | TCP 연결을 열어 두고 명령을 계속 보냄 |
| 데이터 | JSON + 헤더라 무거움 | 단순 텍스트라 가볍고 빠름 |
| 결과 | 상태 코드와 본문 | 값, `nil`, 오류 메시지 |

우리 설계는 둘을 섞음: **통신은 HTTP, 요청 모양은 Redis 명령(`/set`, `/get`, `/delete`)**. 하루 안에 0~6단계를 마쳐야 하니 핵심인 해시 테이블에 시간을 쓰는 게 나음.

- 성능 비교(R10)에서 "진짜 Redis보다 왜 느린가?" → HTTP 헤더와 JSON 처리 비용 때문

## 2. 만료와 무효화

| | 만료 (R5) | 무효화 (R6) |
| --- | --- | --- |
| 언제 | 시간이 지나면 | 데이터가 더 이상 맞지 않게 될 때 (원본이 바뀜 등) |
| 누가 | 저장소가 자동으로 | 사용하는 쪽이 직접 요청 |
| 어떻게 | 저장할 때 `ttl`을 같이 넘김, 조회할 때 확인 (4단계) | 그 일이 생긴 순간 `delete` 호출 |
| 그 뒤 조회 | 404 | 404 |

- **ttl은 남은 기간, 만료 시각은 정확한 시점**. 사용자는 ttl(기간)로 말하고, 저장소는 `만료 시각 = 저장한 시각 + ttl`로 바꿔서 보관함
- 예: "ttl 600초로 저장" → 요청은 `set`, 저장소 안에서는 `name → (값, 지금+600초)`
- 조회할 때 지금 시각이 만료 시각을 지났으면 지우고 `None`을 돌려줌 → 이게 4단계의 **지연 삭제**
- ttl을 생략하면 만료 시각이 비어 있어서 계속 남아 있음
- 덮어쓰면 만료 시각도 새로 정함. ttl 없이 덮어쓰면 만료가 없어짐 (Redis와 같음)

## 3. 동시성

여러 요청이 같은 데이터를 거의 동시에 건드리면 문제가 생김. 두 층으로 나뉨.

### 명령 하나의 안전성

저장·조회·삭제 각각이 실행되는 도중에 다른 요청이 끼어들면 해시 테이블 내부가 망가짐.

- 한 요청이 칸 수를 늘리며 재배치하는 도중에 다른 요청이 조회
- 같은 칸의 리스트에 두 요청이 동시에 항목을 추가
- 한 요청이 만료된 값을 지우는 도중에 다른 요청이 그 값을 읽음 → 지연 삭제 때문에 **get도 쓰기**가 됨. 조회에도 lock이 필요함

| 방식 | 설명 | 특징 |
| --- | --- | --- |
| 여러 스레드 + lock 하나 | 요청은 동시에 받되 저장소를 건드리는 순간에는 하나만 진입 | 단순함. HTTP 도구는 기본적으로 여러 스레드로 요청을 받아서 이 방식이 맞음. DBMS Phase 3에서 다시 씀 |
| 단일 스레드 순차 처리 | 요청을 줄 세워 하나씩 처리 | lock이 필요 없음. 진짜 Redis 방식. 이벤트 루프를 직접 짜야 해서 HTTP 도구와 잘 안 맞음 |

→ 팀 결정: 저장소 전체에 lock 하나 (5단계)

### 여러 명령에 걸친 안전성

방문자 수를 두 사용자가 거의 동시에 읽고, 1을 더해, 저장하는 경우. 읽기와 저장이 서로 다른 요청이라 각 요청에 lock을 걸어도 값이 덜 올라감. 해결책은 "읽고, 더하고, 저장"을 **하나의 명령(증가 명령)**으로 묶어 미니 레디스 안에서 한 번에 처리하는 것. 캐시 용도에서는 이 문제가 거의 생기지 않음.

## 4. 주기적 정리 (시간이 남으면, 13단계)

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| 지연 삭제만 | 추가 구현이 없음 | 아무도 조회하지 않는 만료 키는 메모리에 계속 남음 |
| 주기적 정리도 구현 | 메모리가 쌓이지 않음 | 정리 작업도 같은 lock을 잡아야 하고 단계가 하나 늘어남 |

- 단순한 구현: 일정 간격(예: 1초)마다 lock을 잡고 테이블 전체를 훑어 만료 키를 지움
- 진짜 Redis는 지연 삭제와 주기적 정리(일부 키 샘플링)를 함께 씀. 둘 다 있으면 설명이 완성됨
- 판단 기준: 질의응답에서 "조회하지 않는 만료 키는 어떻게 되나요?"에 말로 답할지, 코드로 보여줄지

## 5. 증가 명령 INCR (시간이 남으면, 12단계)

- `incr(key)`: 키를 받아 1 올린 뒤의 값을 돌려줌. 키가 없으면 0에서 시작해 1. 값이 정수가 아니면 오류
- 접점 1에 함수 하나, 접점 2에 `POST /incr` 하나 추가. 성공 200, 숫자가 아니면 400
- "읽고, 더하고, 쓰기"를 lock 안에서 한 번에 해야 해서 **lock이 왜 필요한지 보여 주는 좋은 예시**. lock이 없으면 동시에 올릴 때 값이 덜 오름
- 판단 기준: 동시성(R4)을 발표에서 강조할 생각이라면 가치가 큼. 지금의 세 기능만 하면 동시성을 말로만 설명하게 됨

## 6. 알게 된 것

1. `set`으로는 문자열, 숫자, 목록 등 아무 값이나 저장할 수 있어서, 숫자가 아닌 값이 저장된 키에 `incr`을 호출하는 경우가 생김. 이때 400 오류를 돌려줘야 함
   - 예: `set`으로 `"현지"` 저장 → 누군가 `incr(name)` 호출 → `"현지"`에 1을 더할 수 없음
2. `get`은 넣어 둔 값을 그대로 돌려주고, `delete`는 키를 지울 뿐 값은 보지 않음
3. 세 함수는 값을 상자에 든 물건처럼 다룸. 안을 열어 보지 않고 넣고, 꺼내고, 버리기만 함. 그래서 **값의 종류를 따지는 명령을 추가할 때마다 이런 오류 처리가 필요함** (예: 목록 뒤에 값을 붙이는 명령이라면 값이 목록이 아닐 때의 오류)
4. `get`과 `delete`는 값이 무엇이든 그대로 동작하지만, `incr`은 값에 따라 결과가 갈림
5. DBMS는 원본을 파일에 영구 보관하고, Redis는 그 앞에서 자주 쓰는 결과를 메모리에 잠시 보관함
6. 같은 "없음" 문제는 언어마다 다르게 풂: Python `in`/`KeyError`, JavaScript `undefined`와 `null` + `in`, Java `containsKey()`, Go `v, ok := m[key]`, Rust `Option`
7. Redis를 이해하려면 문서만 읽기보다 직접 깔아서 써 보는 게 좋음. 써 보면 미니 레디스에 어떤 기능이 필요한지 보임 (사용자, 운영자, 개발자 입장에서 CLI, 라이브러리, 해시, CRUD)
