# 팀 결정 기록

세 사람(김소망, 이현지, 김은기)이 0~6단계를 각자 구현하며 내린 결정, 그 이유, 서로 주고받은 피드백, 그리고 팀이 최종 구현을 고른 이유를 한곳에 모은 문서입니다.

- 단계 번호는 [DESIGN.md](./DESIGN.md)의 개발 단계를 따릅니다.
- 근거는 문서 맨 아래 「근거 자료」에 있습니다. 회의록에 없는 내용은 "확인 필요"로 표시했습니다.
- 표의 **굵은 글씨**는 지금 `main`에 들어가는 최종 구현의 선택입니다.

## 1. 어떻게 진행했나

| 순서 | 한 일 | 이유 |
| --- | --- | --- |
| 1 | 언어, API 형식, 진행 방식만 팀이 먼저 확정 | 반드시 같아야 하는 것만 같이 정함 |
| 2 | 0~6단계를 세 사람이 각자 구현 | 구현 세부(충돌 처리, 확장 기준 등)는 직접 골라 봐야 이유를 설명할 수 있음 |
| 3 | 단계를 묶어 체크인에서 서로의 선택을 공유 | 다 끝내고 한 번에 비교하면 양이 너무 많음. 속도를 맞출 필요는 없고, 아직 안 한 단계 이야기에도 참여 가능 |
| 4 | 7단계에서 세 구현을 같은 요청으로 비교해 기준 구현 하나를 선택 | 8단계부터는 한 코드 위에서 나눠 작업해야 함 |
| 5 | 기준 구현 위에서 8·9단계(김은기), 10·11단계(김소망)를 분담 | 폴더가 겹치지 않게 나눔 |

진행 방식 후보는 두 가지였습니다.

| 안 | 내용 | 결과 |
| --- | --- | --- |
| A. 단계별 체크인 | 각자 구현하되 단계마다 모여 짧게 공유 | **채택.** 김은기가 선호했고, 속도 차이 우려에는 이현지가 "정한 대로 하는 자리가 아니라 이야기해 보는 자리"라고 답함 |
| B. 완전 개인 구현 | 혼자 구현하고 마지막에 한 번에 공유 | 채택하지 않음. 마지막에 다룰 양이 너무 많아짐 |

## 2. 팀이 함께 정한 것

| 항목 | 결정 | 제안과 이유 | 고르지 않은 것 |
| --- | --- | --- | --- |
| 언어 | Python | 김소망 제안. AI가 쓴 코드도 읽고 직접 설명하기 쉬움. 셋 다 다룰 수 있음 | - |
| API 형식 | HTTP (`POST /set`, `GET /get`, `DELETE /delete`) | 김소망 제안. `curl`이나 브라우저로 바로 시연 가능. DBMS 서버에도 그대로 쓸 수 있음 | 실제 Redis 프로토콜(RESP). 과제 범위가 실제 Redis와 다름 |
| `dict` 사용 | 해시 테이블에는 `dict`를 쓰지 않음. 칸 배열은 `list` 허용. 1단계의 임시 `dict`는 허용 | 김소망 제안. 해시 계산, 충돌 처리, 확장을 직접 구현하면 과제 조건에 맞음 | 칸 배열까지 직접 구현 |
| 구현 세부 | 팀이 정하지 않고 각자 선택 | 이현지 의견. 언어와 API처럼 꼭 같아야 하는 것과, 구현하면서 정해지는 것을 구분 | 충돌 처리, 확장 기준을 팀 규칙으로 고정 |
| 서버 도구 | 각자 자유 | 과제가 기술 스택을 자유로 둠 | Flask로 통일 |
| 없는 키 응답 | 조회는 404, 삭제는 200 `{"deleted": false}` | 조회의 목적은 값을 받는 것이라 없으면 실패. 삭제의 목적은 "없는 상태"라 이미 없어도 성공. 다시 보내도 결과가 같아 재시도가 안전함 | 삭제도 404 |
| 역할 나누기 | 서버는 HTTP만 알고, 저장소는 저장만 앎. 둘은 `set`, `get`, `delete`로만 만남 | 이현지 설명. 저장소 안쪽이 바뀌어도 서버를 고칠 필요가 없음 | 서버에서 저장소 내부를 직접 사용 |

마지막 줄은 2단계에서 효과를 확인했습니다. 임시 `dict`를 직접 만든 해시 테이블로 바꿨을 때 세 사람 모두 서버 코드를 고치지 않았습니다.

## 3. 단계별로 세 사람이 고른 것

### 0~1단계: 서버 틀과 임시 저장소

| 결정 | 김소망 | 이현지 | 김은기 |
| --- | --- | --- | --- |
| 서버 도구 | **Flask** | Flask | Flask |
| 고른 이유 | 코드가 짧아 해시 테이블에 집중할 수 있음. FastAPI는 입력을 자동으로 검증해 6단계를 직접 이해할 기회를 가림 | 코드가 짧고 400 응답을 직접 쓰기 쉬움 | 가볍고 API 몇 개에 충분 |
| 포트 | **8000** | 8000 | 5001 |
| 폴더 구조 | **`mini_redis/` 패키지** | 최상위에 파일 3개 | `mini_redis/` 패키지 |
| 임시 저장소 | **`Store` 클래스가 `dict`를 감쌈** | `Store` 클래스 | `Store` 클래스 |
| 테스트 도구 | **`unittest`** (추가 설치 없음) | `pytest` (`assert` 한 줄로 읽기 쉬움) | - |

포트가 5000이 아닌 이유는 같습니다. macOS의 AirPlay 수신 기능이 5000을 씁니다.

### 2단계: 해시 테이블과 충돌 처리

| 결정 | 김소망 | 이현지 | 김은기 |
| --- | --- | --- | --- |
| 충돌 처리 | **체이닝** | 체이닝 | 체이닝 |
| 체인 구조 | **직접 만든 노드의 연결 리스트** | 파이썬 `list`에 `(키, 값)` 튜플 | 직접 만든 노드의 연결 리스트 |
| 새 항목 위치 | **체인 맨 앞** | 맨 뒤 (`append`) | 체인 맨 앞 |
| 해시 함수 | **FNV-1a 64비트 직접 구현** | 31을 곱하며 더하는 방식 직접 구현, 32비트 | 6단계까지 내장 `hash()`, 이후 직접 만든 함수로 변경 |
| 충돌 테스트 방법 | **해시 함수를 바꿔 끼워 모든 키를 한 칸으로** | 칸 수를 작게 | 같은 칸에 걸리는 키를 골라 넣음 |

체인 구조의 장단점입니다.

| | 연결 리스트 (김소망, 김은기) | 파이썬 `list` (이현지) |
| --- | --- | --- |
| 장점 | 칸 배열 말고는 모두 직접 만들어 "직접 구현"이 분명함. 노드를 끊고 잇는 과정을 설명할 수 있음. 빈 칸은 `None` 하나 | 코드가 가장 짧음. 삭제가 `pop(i)` 한 줄. 원소가 메모리에 이어져 있어 짧은 체인을 훑기 빠름 |
| 단점 | 이전 노드를 기억하며 끊고 잇는 코드가 필요 | 잇고 끊는 일을 파이썬이 대신 함. 칸마다 빈 리스트 객체를 미리 만들어 둠 |
| 찾는 속도 | 앞에서부터 하나씩 확인 | 같음 |

해시 함수의 장단점입니다.

| | 직접 구현 (FNV-1a, 31 곱하기) | 내장 `hash()` |
| --- | --- | --- |
| 장점 | 언제 실행해도 값이 같아 어떤 키끼리 충돌하는지 다시 보여 줄 수 있음. 해시 테이블 전체를 직접 설명할 수 있음 | 코드가 필요 없음 |
| 단점 | 값이 고정이라 한 칸에 몰리는 키를 미리 계산해 보낼 수 있음 (7장 참고) | 문자열 해시가 실행할 때마다 달라 칸 배치를 다시 보여 줄 수 없음. "직접 구현" 요구에서 질문받을 수 있음 |

### 3단계: 칸 수 확장

| 결정 | 김소망 | 이현지 | 김은기 |
| --- | --- | --- | --- |
| 확장 기준 | **키 수 ÷ 칸 수 > 0.75** | 같음 | 같음 (Java `HashMap` 기본값 참고) |
| 늘리는 배수 | **2배** | 2배 | 2배 |
| 시작 칸 수 | **8** | 8 | 4 |
| 재배치 | **기존 노드를 그대로 옮김** | 튜플을 그대로 옮김 | 기존 노드를 그대로 옮김 |
| 칸 수 줄이기 | **하지 않음** | 하지 않음 | - |

세 사람이 같은 값을 골랐지만 팀이 정한 값은 아닙니다. 체크인에서 "적재율과 배수는 정답이 아니라 속도와 메모리 사이에서 고르는 값"이라고 정리했습니다.

| 값 | 고른 이유 | 다른 값이면 |
| --- | --- | --- |
| 0.75 | 체인의 평균 길이가 1보다 짧아 조회가 빠르고 빈 칸 부담이 작음 | 낮추면 빈 칸이 늘고, 높이면 체인이 길어짐. 실제 Redis는 1.0 |
| 2배 | 확장 간격이 두 배씩 벌어져 키 하나당 평균 옮기는 횟수가 일정함. 이현지 측정으로는 키 100개에 191번 옮김 | 한 칸씩 늘리면 같은 조건에서 5,029번 옮김 |
| 시작 8칸, 4칸 | 키 몇 개만 넣어도 충돌과 확장을 눈으로 볼 수 있음 | 크게 잡으면 초반 확장은 줄지만 확인하기 어려움 |

### 4단계: 만료

| 결정 | 김소망 | 이현지 | 김은기 |
| --- | --- | --- | --- |
| 무엇을 저장 | **만료 시점 (지금 + ttl)** | 같음 | 같음 |
| 어디에 저장 | **저장소가 `(값, 만료 시점)` 묶음을 해시 테이블의 값으로 넣음** | 같음 | 해시 테이블 노드에 `expire_at` 칸을 둠 |
| 만료 확인 | **지연 삭제 (조회, 삭제할 때 확인해 지움)** | 같음 | 같음 |
| 시계 | **`time.monotonic`, 바꿔 끼울 수 있음** | 같음 | `time.time`, 이후 `monotonic`으로 변경 |
| 경계 | **지금 >= 만료 시점이면 만료** | 같음 | - |
| 만료된 키 삭제 | **200 `{"deleted": false}`** | 같음 | 같음 |
| 덮어쓰기 | **만료 시점도 새로 정함. ttl을 생략하면 만료 없음** | 같음 | 같음 |

만료 시점을 어디에 두는지가 세 구현의 가장 큰 구조 차이였습니다.

| | 저장소에 둠 (김소망, 이현지) | 해시 테이블 노드에 둠 (김은기) |
| --- | --- | --- |
| 장점 | 해시 테이블이 "키로 값을 찾는 일" 하나만 함. 2~3단계 코드와 테스트를 고치지 않음. 가짜 시계를 끼워 기다리지 않고 만료를 테스트함 | 저장소 코드가 아주 짧아짐 |
| 단점 | 저장소 코드가 길어짐 | 해시 테이블이 두 가지 일을 함. 시계를 바꿔 끼울 수 없어 만료 테스트가 실제로 기다려야 함 |

시계의 장단점입니다.

| | `time.monotonic` | `time.time` |
| --- | --- | --- |
| 장점 | 뒤로 가지 않아 만료가 흔들리지 않음 | 재시작해도 의미가 유지되어 파일 저장에 유리. 실제 Redis가 쓰는 방식(이현지 조사) |
| 단점 | 재시작하면 기준점이 바뀜. 14단계에서 파일에 저장하려면 방법을 따로 정해야 함 | 컴퓨터 시각이 바뀌면 만료가 늦어지거나 빨라짐 |

### 5단계: lock

세 사람의 결과가 같았습니다.

| 결정 | 세 사람 공통 | 이유 | 고르지 않은 것 |
| --- | --- | --- | --- |
| lock 위치 | **저장소 (`Store`)** | "만료 확인 → 삭제"처럼 여러 단계로 된 동작을 아는 곳이 저장소. 사용하는 쪽이 lock을 빠뜨릴 수 없음 | 해시 테이블, 서버 |
| lock 개수 | **저장소 전체에 하나** | 키가 달라도 같은 칸 배열, 개수, 확장을 함께 만짐. 확장 때는 어차피 전체를 잠가야 함 | 칸마다, 키마다 하나 |
| 감싸는 함수 | **`set`, `get`, `delete` 전부** | 읽기도 고치는 중간 상태를 볼 수 있음. `get`의 만료 확인과 삭제 사이에 `set`이 끼면 새 값이 지워짐 | 쓰기만 |
| lock 종류 | **`threading.Lock`** (김소망, 이현지) | lock을 쥔 채 다른 저장소 함수를 부르는 곳이 없음 | `RLock` |

### 6단계: 입력 검증

세 구현의 응답이 가장 많이 갈린 단계입니다.

| 요청 | 김소망 | 이현지 | 김은기 |
| --- | --- | --- | --- |
| `key`, `value`, `ttl` 말고 다른 항목 (오타 `"ttI"`) | **400** | 400 | 200, 오타가 무시되어 만료 없이 저장 |
| 아주 큰 정수 `ttl` | **400** | 400 | 500 |
| `ttl` 상한 | **10년** | 10년 | 없음 |
| `Content-Type` 없는 JSON | **400** | 400 | 200 |
| 없는 주소, 틀린 메서드 | **JSON 404, 405** | HTML 404, 405 | JSON 404, 405 |
| 오류 문장 | **한국어** | 한국어 | 영어 |

셋이 같았던 것은 이렇습니다. 빈 키, 숫자 키, `value: null`, `ttl`이 `0`·`true`·`"5"`·`Infinity`인 경우는 모두 400입니다.

| 결정 | 최종 구현 | 이유 |
| --- | --- | --- |
| 검증 위치 | 서버 | 요청의 모양은 HTTP를 받는 쪽만 앎. 저장소에는 올바른 입력만 넘김 |
| 모르는 항목 | 400 | 오타가 무시되면 곧 사라질 줄 안 값이 계속 남아 캐시가 낡은 값을 줌 |
| `ttl` 범위 | `0 < ttl <= 10년` 비교 하나 | 0, 음수, `NaN`, `Infinity`, 아주 큰 정수를 한 번에 막음. `math.isfinite()`는 아주 큰 정수에서 오류를 내 500이 됨 |
| `ttl`에 `true` | 400 | 파이썬의 `bool`은 `int`의 한 종류라 막지 않으면 1초로 저장됨 |
| `ttl`에 `null` | 생략과 같이 만료 없음 | JSON의 `null`은 "없음"이라는 뜻 |
| `value`에 `null` | 400. `0`, `false`, `""`, `[]`는 저장 | 저장소의 `None`이 언제나 "없음"을 뜻하게 함 |
| 공백 키 `" "` | 허용. 빈 문자열만 400 | 실제 Redis도 키 내용을 따지지 않음 |
| 없는 주소, 틀린 메서드 | JSON 404, 405 | API를 쓰는 쪽은 응답을 JSON으로 읽음 |
| 키와 값의 크기 | 제한 없음 | 과제 범위에서는 기능 확인이 목적. 약점은 7장에 적음 |

## 4. 주고받은 피드백

| 언제 | 누가 누구에게 | 내용 | 결과 |
| --- | --- | --- | --- |
| 공통 결정 회의 | 이현지 → 팀 | 충돌 처리 같은 구현 세부를 팀이 지금 정하는 게 맞는가 | 팀 확정은 언어, API, 진행 방식으로 한정. 설계 문서의 「결정 기록」을 「결정 참고 사항」으로 이름 변경 |
| 1차 체크인 | 이현지 → 팀 | 서버와 저장소는 서로를 몰라야 함 | 세 사람 모두 `set`, `get`, `delete` 접점으로 분리 |
| 1차 체크인 | 김소망 → 이현지 | 칸 수 확장은 충돌의 해결책이 아니라, 체인을 짧게 유지하는 보조 수단 | 체이닝과 확장을 함께 쓰는 것으로 정리 |
| 1차 체크인 | 이현지 → 팀 | `None`을 "없음" 표시로 쓰면 진짜 `None` 값과 구분할 수 없음 | 6단계에서 `value: null`을 400으로 막음 |
| 2차 체크인 | 김소망 → 김은기 | "맨 앞에 붙이면 체인 끝까지 안 가도 된다"는 이유는 성립하지 않음. 같은 키가 있는지 보려고 어차피 한 번 끝까지 돎 | 이유를 "방금 넣은 값을 곧바로 읽는 일이 많은 캐시에 유리"로 정리 |
| 2차 체크인 | 이현지 → 팀 | "앞에 붙이나 뒤에 붙이나"와 "같은 키를 덮어쓰나"는 서로 다른 문제. 앞뒤는 자료구조에 따라 답이 다름 | 연결 리스트는 앞, 파이썬 `list`는 뒤가 맞다고 정리 |
| 2차 체크인 | 김소망 → 이현지 | `list` 체인은 잇고 끊는 일을 파이썬이 대신 함. 핵심 로직을 직접 설명해야 한다면 연결 리스트가 낫지 않은가 | 이현지는 `list`를 유지. 연결 리스트 버전을 만들어 속도를 재 본 뒤 이유를 기록 |
| 2차 체크인 | 팀 | 충돌에는 두 종류가 있고 막는 방법이 다름 | 나머지만 같은 충돌은 칸 수 확장으로, 해시 값이 같은 충돌은 좋은 해시 함수로 막는다고 합의 |
| 2차 체크인 이후 | 팀 → 김은기 | 내장 `hash()`는 실행할 때마다 값이 달라 충돌을 다시 보여 줄 수 없음 | 김은기가 직접 만든 해시 함수로 변경 |
| 코치 피드백 | 코치 → 팀 | "서버가 여러 대가 되면?"을 건너뛰었음. Redis가 푸는 문제는 상태를 서버 밖 한 곳으로 빼는 것 | 김은기가 로컬 캐시가 망가지는 다섯 장면을 정리. 8단계 데모가 서버 두 대 비교가 됨 |
| 3차 체크인 | 이현지 → 김소망 | `(값, 만료 시점)`이 튜플 하나라면 다시 넣어도 만료가 사라지지 않아야 함 | 확인 결과 이현지 말이 맞음. 확장과 재삽입 때 만료가 유지되는 테스트를 추가 |
| 3차 체크인 | 이현지 → 김소망 | `monotonic`은 재시작하면 기준점이 바뀜. 파일에 저장한다면 남은 초를 저장하면 됨 | 14단계를 할 때 쓸 방법으로 기록 |
| 3차 체크인 | 김소망 → 팀 | `get`이 만료 확인과 삭제를 나눠 하는 사이에 `set`이 끼면 새 값을 지움 | 5단계에서 세 사람 모두 `get`까지 lock으로 감쌈 |
| 3차 체크인 | 팀 | 만료와 무효화는 다른 일. 무효화는 원본을 고친 애플리케이션의 책임 | 8단계 데모 API가 DB를 고친 뒤 캐시 키를 지움. TTL은 무효화를 놓쳤을 때의 안전망 |
| 3차 체크인 | 이현지 → 김소망 | 여러 주제를 이어서 말하면 듣는 사람이 끼어들기 어려움 | 주제 하나씩 나누고 넘어가기로 함 |
| 7단계 비교 | 이현지 → 팀 | 각자의 테스트는 각자가 생각한 경우만 확인함. 같은 요청을 세 서버에 보내야 차이가 드러남 | 공통 요청 23개로 비교 (5장) |

## 5. 기준 구현을 고른 과정

### 비교 방법

이현지가 세 브랜치를 0~6단계까지 만든 시점으로 맞춰 비교했습니다. 김은기 브랜치는 13단계 기능이 들어가기 전 커밋을 썼습니다.

| 확인한 것 | 김소망 | 이현지 | 김은기 |
| --- | --- | --- | --- |
| 각자의 테스트 | 31개 통과 | 56개 통과 | 7개 통과 |
| 공통 요청 23개에서 500 오류 | 없음 | 없음 | 1건 (아주 큰 정수 `ttl`) |
| 8개 스레드가 2,000번씩 동시 저장 후 유실 | 0건 | 0건 | 0건 |
| 만료 테스트 | 가짜 시계 | 가짜 시계 | 실제로 기다림 |

선택 기준은 설계 문서에 미리 적어 둔 세 가지였습니다. 공통 테스트 통과, 읽고 설명하기 쉬운 코드, 결정 기록 준수입니다.

### 후보별 장단점

| 후보 | 장점 | 그대로 쓰려면 고칠 것 |
| --- | --- | --- |
| 김소망 | 공통 요청에서 빈틈이 없음. 해시 함수를 바꿔 끼울 수 있어 충돌 테스트가 쉬움. 6단계에서 이현지의 검증 방식과 김은기의 JSON 404, 405를 이미 합침 | 없음 |
| 이현지 | 구조와 검증이 김소망과 거의 같음. 코드가 가장 짧고 테스트가 가장 많음 | JSON 404, 405 추가. 폴더를 패키지로 맞출지 결정 |
| 김은기 | 저장소 코드가 가장 짧음 | 검증 빈틈 3개 보완. 해시 함수와 시계 변경. 가짜 시계를 쓰려면 만료를 저장소로 옮겨야 함 |

### 결과

**김소망의 구현을 기준 구현으로 골랐습니다.** 비교 보고서의 제안은 "김소망을 기준으로 하고, 이현지의 계층별 테스트 케이스를 보탠다"였습니다.

이유를 정리하면 이렇습니다.

1. 세 사람의 장점이 이미 한 코드에 합쳐져 있었습니다. 검증은 이현지 방식, 없는 주소와 틀린 메서드의 JSON 응답은 김은기 방식입니다.
2. 같은 요청 23개에서 500 오류나 무시되는 오타 같은 빈틈이 없었습니다.
3. 만료와 lock이 저장소에만 있어 해시 테이블을 따로 설명할 수 있었습니다.
4. 고칠 것 없이 바로 8단계를 시작할 수 있었습니다.

고르지 않은 구현에서 가져온 것도 있습니다.

| 가져온 것 | 어디서 | 어디에 |
| --- | --- | --- |
| 검증 함수의 구성, `ttl` 상한 10년, 모르는 항목 400 | 이현지 | `mini_redis/server.py` |
| JSON 404, 405 응답 | 김은기 | `mini_redis/server.py` |
| 계층별 테스트 장면 (동시 저장과 삭제, 만료 뒤 다시 저장 등) | 이현지 | 10단계 테스트 |
| 로컬 캐시가 망가지는 다섯 장면 | 김은기 | 8단계 데모와 시연 |

> 확인 필요: 기준 구현을 최종 확정한 회의(4차 체크인)의 회의록은 이 문서를 쓸 때 찾지 못했습니다. 위 이유는 비교 보고서의 제안과 이후 분담 기록을 바탕으로 적었습니다. 회의에서 나온 다른 이유가 있으면 보태 주세요.

## 6. 기준 구현을 고른 뒤의 결정

| 단계 | 결정 | 이유 | 고르지 않은 것 |
| --- | --- | --- | --- |
| 8 | 데모 API는 미니 Redis를 HTTP로 사용 | 과제의 "외부에서 사용"을 보여 주려면 코드를 불러 쓰는 게 아니라 다른 서버로 접속해야 함 | 같은 프로그램 안에서 불러 쓰기 |
| 8 | 읽을 때는 캐시를 먼저 보고, 없으면 DB에서 읽어 캐시에 채움 | 어떤 데이터를 캐시할지는 애플리케이션이 정함 | 미니 Redis가 DB를 직접 읽기 |
| 8 | 쓸 때는 DB를 고친 뒤 캐시 키를 지움 | DB 쓰기와 캐시 쓰기의 순서가 어긋나면 옛 값이 남을 수 있음. 지우기만 하면 다음 읽기가 새 값을 채움 | 캐시에 새 값을 덮어쓰기 |
| 8 | 인기 목록 캐시의 TTL은 60초, 시연 스크립트만 600초 | TTL은 무효화를 놓쳤을 때의 안전망. 틀린 값을 참을 수 있는 시간으로 정함. 시연은 설명 중에 만료되지 않게 길게 | 시연과 같은 600초를 기본값으로 |
| 8 | 미니 Redis 코드는 수정하지 않음 | 데모는 미니 Redis를 "쓰는 쪽"임 | - |
| 9 | 캐시를 쓸 때와 안 쓸 때의 응답 시간과 DB 조회 횟수를 함께 측정 | 빠르기는 가짜 DB의 지연 설정에 따라 달라지므로 조건을 함께 적어야 함 | 배수만 적기 |
| 10 | 실제 서버를 띄워 동시 요청을 보내는 테스트 추가 | 테스트 도구는 요청을 하나씩 처리해 서버 스레드끼리의 겹침을 못 봄 | 저장소만 스레드로 테스트 |
| 10 | 키와 값의 크기 제한을 두지 않고 그 사실을 테스트로 고정 | 6단계 표 참고 | 상한을 두고 413 응답 |
| 정리 | 함수 이름이 주석을 대신하도록 위에서 아래로 읽히게 정리. 동작은 그대로 | 발표에서 코드를 읽으며 설명하기 쉬움 | 주석으로 설명 |
| 화면 | 주식 매수 화면을 따로 두고, 화면 서버가 요청을 데모 API로 전달 | 데모 API 코드를 고치지 않고 화면을 붙임. 나중에 DBMS를 붙일 자리 | 데모 API가 화면까지 내주기 |
| 배포 | 서버 3개를 한 서비스에서 함께 실행 | 미니 Redis는 값을 메모리에 두므로 한 프로세스로 띄우는 구성이 가장 단순. 주소가 하나 | 서비스 세 개로 나누기 |

실제 Redis와 다르게 한 점은 [eungi/REDIS_COMPARISON.md](./eungi/REDIS_COMPARISON.md)에 정리되어 있습니다.

## 7. 알고도 남겨 둔 약점

| 약점 | 무슨 일이 생기나 | 남겨 둔 이유 | 실제 Redis |
| --- | --- | --- | --- |
| 해시 값이 고정 | 한 칸에 몰리는 키를 미리 계산해 보내면 체인이 길어져 서버가 느려짐 | 과제 범위 밖. 고정이어야 충돌을 다시 보여 줄 수 있음 | 실행마다 다른 비밀 값이 들어가는 해시 함수 |
| 지연 삭제만 있음 | 아무도 조회하지 않는 만료 키가 계속 남아 칸을 차지함 | 주기적 정리는 13단계 | 지연 삭제와 주기적 정리를 함께 씀 |
| 한 번에 전부 재배치 | 키가 아주 많을 때 확장 순간에 요청이 잠깐 멈춤 | 우리 규모에서는 문제 될 가능성이 낮음 | 조금씩 나눠 옮김 |
| lock 하나 | 요청이 많으면 모두 한 줄로 기다림 | 단순하고 틀리기 어려움 | 명령을 하나씩 실행 |
| 크기 제한 없음 | 아주 큰 값을 계속 보내면 메모리가 바닥남 | 기능 확인이 목적 | 메모리 한도와 정리 정책이 있음 |
| 재시작하면 사라짐 | 서버를 끄면 저장한 값이 모두 없어짐 | 파일 저장은 14단계 | 파일에 저장하는 방식이 두 가지 있음 |
