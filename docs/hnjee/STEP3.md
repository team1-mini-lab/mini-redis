# 3단계: 칸 수 확장

## 목표

해시 테이블이 일정 수준 이상 차면 칸 수를 늘리고, 들어 있던 키를 새 칸에 다시 배치합니다.

완료 기준

- 키 100개를 저장하면 칸 수가 늘어나고, 100개 모두 조회됨
- API 동작이 2단계와 같음
- 단위 테스트가 모두 통과함

## 핵심 문제

2단계의 해시 테이블은 칸이 8개로 고정이라, 키가 늘수록 칸마다 리스트가 길어집니다. `key0` ~ `key99` 100개를 넣으면 가장 긴 리스트가 13개가 됩니다. 조회할 때 훑어야 하는 항목이 늘어나므로, "칸 하나만 보면 된다"는 해시 테이블의 장점이 사라집니다.

```
칸 8개, 키 100개   →  가장 긴 리스트 13개
칸 256개, 키 100개 →  가장 긴 리스트 2개
```

풀어야 할 문제는 세 가지입니다.

1. 언제 늘리는가 → 적재율(키 수 ÷ 칸 수)이 기준을 넘을 때
2. 얼마나 늘리는가 → 2배
3. 늘린 뒤 기존 키를 어떻게 하는가 → 모든 키의 칸 번호를 다시 계산해 옮김 (재배치)

## 질문과 정리

| 질문 | 정리 |
| --- | --- |
| 늘려야 할 때를 무엇으로 판단하는가 | 적재율 = 키 수 ÷ 칸 수. 0.75를 넘으면 늘림 |
| 한 칸의 리스트 길이로 판단하면 안 되는가 | 쓰지 않음. 칸이 작아서 생기는 충돌은 적재율 규칙이 미리 막아 주고, 그래도 길어진 리스트는 해시 함수가 원인이라 칸을 늘려도 풀리지 않음. 아래 설명 참고 |
| 0.75는 어떤 값인가 | 정답이 아니라 속도와 메모리 사이에서 고른 한 지점. 낮추면 빈 칸이 늘고, 높이면 리스트가 길어짐. 아래 설명 참고 |
| 늘린 뒤 기존 키를 그대로 두면 안 되는 이유 | 칸 번호가 `해시 값 % 칸 수`라서 칸 수가 바뀌면 칸 번호도 바뀜. 그대로 두면 `get`이 다른 칸을 찾아가 값을 못 찾음 |
| 재배치가 너무 자주 일어나지 않는가 | 더하기가 아니라 곱하기(2배)로 늘리면 확장이 점점 드물어져, 키 하나당 평균 2번 정도만 옮김. 아래 설명 참고 |
| 해시 값이 같은 키는 | 칸을 늘려도 언제나 같은 칸에 있음. 그래서 체이닝은 계속 필요함 |

### 한 칸의 리스트 길이로 판단하지 않는 이유

"어떤 칸의 리스트가 너무 길면 늘린다"는 문제가 되는 상황(긴 리스트)을 직접 보는 기준이라 자연스럽습니다. 이 기준이 필요한지 보려면 먼저 충돌을 두 종류로 나눠야 합니다.

| 충돌의 종류 | 예 | 칸을 늘리면 |
| --- | --- | --- |
| 해시 값은 다른데 나머지가 같음 (칸이 작아서 생김) | `"name"`과 `"lemon"` (8칸에서 둘 다 3번) | 갈라질 수 있음 |
| 해시 값 자체가 같음 | `"Aa"`와 `"BB"` (둘 다 2112) | 절대 갈라지지 않음 |

**"칸 5개 중 한 칸에 10개"가 모였다면?** 해시 값이 서로 다르다면 칸이 작아서 모인 것이 맞고, 칸을 늘리면 갈라집니다. 그런데 적재율 0.75 규칙이 있으면 이 상태는 애초에 생기지 않습니다. 칸 5개의 기준은 `5 × 0.75 = 3.75`라서 4번째 키에서 이미 10칸으로 늘어났기 때문입니다.

그래서 결론은 이렇습니다.

1. **칸이 작아서 생기는 충돌은 적재율 규칙이 미리 막아 줍니다.** 리스트 길이를 따로 볼 필요가 없습니다.
2. **그런데도 한 칸에 길게 붙었다면 원인은 해시 함수입니다.** 해시 값이 같거나, 값은 다른데 나머지가 계속 겹치는 패턴인 경우입니다(예: 해시 값이 전부 16의 배수이면 8칸이든 16칸이든 모두 0번 칸). 이때는 칸을 늘려도 풀리지 않습니다.
3. **리스트 길이를 기준으로 삼으면 2번의 경우에 칸 수만 끝없이 늘어납니다.** `"Aa"`, `"BB"`, `"AaAa"`, `"AaBB"` … 몇 개만 넣어도 확장이 계속 일어납니다.

좋은 해시 함수의 조건은 "서로 다른 값을 준다"가 아니라 **"칸 번호가 고르게 퍼지도록 값을 준다"**입니다. (참고: 자바의 `HashMap`은 한 칸의 리스트가 8개 이상으로 길어지면 칸을 늘리는 대신 그 칸의 리스트를 트리로 바꿔서 대응합니다.)

### 0.75는 어떤 값인가

| 기준 | 얻는 것 | 내주는 것 | 쓰는 곳 |
| --- | --- | --- | --- |
| 낮게 (0.5) | 리스트가 더 짧음 | 빈 칸이 많음. 테이블의 절반 이상이 항상 비어 있음 | |
| 0.75 | 그 중간 | | 자바 `HashMap`, 우리 구현 |
| 높게 (1.0) | 메모리 절약 | 리스트가 조금 더 김 | 레디스 |

- 0.75는 정답이 아니라 **속도와 메모리 사이에서 고른 한 지점**입니다. 레디스는 리스트가 평균 1개 수준이면 충분히 빠르다고 보고 1.0을 씁니다.
- 0.75여도 충돌은 꽤 자주 일어납니다. 키가 고르게 퍼져도 한 칸에 하나씩 딱 맞게 들어가지는 않기 때문입니다. 적재율을 낮게 유지하면 충돌이 없어지는 것이 아니라 **리스트가 짧게 유지됩니다.**

### 재배치 비용: 왜 2배인가

키 100개를 차례로 넣을 때 일어나는 일을 계산하면 이렇습니다.

| 늘리는 방식 | 늘린 횟수 | 옮긴 키의 총 수 | 마지막 칸 수 |
| --- | --- | --- | --- |
| 2배씩 | 5번 | 191번 | 256 |
| 1칸씩 | 94번 | 5,029번 | 102 |

칸 8개에서 7번째 키로 확장이 일어난 직후를 비교하면 차이가 보입니다.

- **2배(16칸)**: 기준이 12이므로 키 5개를 더 넣는 동안 확장이 없습니다.
- **1칸(9칸)**: 기준이 6.75인데 키가 이미 7개라, 늘리자마자 기준을 넘은 상태입니다. 다음 키부터 넣을 때마다 매번 확장합니다.

2배씩 늘리면 늘릴 때마다 다음 확장까지의 여유도 커져서, 확장이 점점 드물어집니다.

| 확장 직후 칸 수 | 다음 확장까지 더 넣을 수 있는 키 |
| --- | --- |
| 16칸 (키 7개) | 5개 |
| 32칸 (키 13개) | 11개 |
| 64칸 (키 25개) | 23개 |
| 128칸 (키 49개) | 47개 |

```
7번째 키   →  8 → 16칸   (7개 옮김)
13번째 키  → 16 → 32칸   (13개 옮김)
25번째 키  → 32 → 64칸   (25개 옮김)
49번째 키  → 64 → 128칸  (49개 옮김)
97번째 키  → 128 → 256칸 (97개 옮김)
```

키 100개에 191번이므로 키 하나당 평균 2번 정도입니다. 키가 아무리 늘어도 이 평균은 유지됩니다.

중요한 것은 2라는 숫자가 아니라 **더하기가 아닌 곱하기로 늘린다**는 점입니다. 1.5배로 해도 같은 효과가 납니다. 배수가 크면 확장은 드물어지지만 빈 칸이 늘고, 작으면 그 반대입니다. 2배는 계산이 단순하고 레디스와 자바 `HashMap`도 쓰는 값입니다. 다만 확장이 일어나는 **그 한 번의 `set`은 느립니다.** 실제 레디스가 조금씩 나눠 옮기는(점진적 재해싱) 이유입니다.

### 재배치하면 키가 갈라지는 모습

8칸에서 3번 칸에 함께 있던 키들이, 16칸이 되면 3번과 11번으로 나뉩니다.

```
칸 8개                          칸 16개
[3] name -> lemon       →       [3]  lemon
                                [11] name
```

`"name"`의 해시 값 3373707은 `% 8 = 3`이지만 `% 16 = 11`입니다. 그래서 그대로 3번 칸에 두면 `get("name")`은 11번 칸을 찾아가 `None`을 돌려줍니다.

## 주요 함수

| 함수 | 하는 일 |
| --- | --- |
| `capacity` | 현재 칸 수(`len(self._buckets)`)를 돌려줌 |
| `set(key, value)` | 2단계와 같음. 새 키를 붙인 뒤 `키 수 > 칸 수 × 0.75`이면 `_resize()`를 부름 |
| `_resize()` | 칸이 2배인 새 빈 칸들을 만들고, 기존 항목을 모두 꺼내 새 칸 번호에 넣음 |

`_resize`의 흐름은 이렇게 됩니다.

```python
def _resize(self):
    old_buckets = self._buckets
    self._buckets = [[] for _ in range(len(old_buckets) * GROWTH_FACTOR)]   # 1. 새 칸 만들기
    for bucket in old_buckets:                                             # 2. 기존 항목을 모두 꺼내
        for key, value in bucket:
            self._buckets[self._index(key)].append((key, value))           # 3. 새 칸 번호에 넣기
```

`self._buckets`를 먼저 새 칸으로 바꿔 두기 때문에, 3번 줄의 `_index(key)`는 새 칸 수로 계산됩니다. 키 수(`_size`)는 변하지 않으므로 건드리지 않습니다.

## 알아 둘 것

- **확장 중에 `set`을 다시 부르지 않습니다.** `_resize` 안에서 `self.set(...)`으로 옮기면 `_size`가 두 번 세어지고, 확장 확인이 또 일어납니다. 그래서 새 칸에 직접 `append`합니다.
- **옮길 때는 같은 키가 있는지 확인하지 않아도 됩니다.** 기존 테이블에 이미 키가 하나씩만 있기 때문입니다.
- **칸 수가 늘면 메모리를 더 씁니다.** 키 100개에 256칸이면 빈 칸이 많습니다. 조회 속도를 얻는 대신 메모리를 쓰는 선택입니다.

<details>
<summary>2. "한 칸의 리스트가 길어지면 늘린다"로 하지 않은 이유는 뭔가요?</summary>

칸이 작아서 생기는 충돌은 적재율 규칙이 미리 막아 주기 때문입니다(칸 5개면 4번째 키에서 이미 확장). 그런데도 한 칸이 길어졌다면 원인은 해시 함수이고, 이때는 칸을 늘려도 풀리지 않아 칸 수만 끝없이 늘어납니다.
</details>

<details>
<summary>3. 칸을 늘린 뒤 기존 키를 그대로 두면 어떤 일이 생기나요?</summary>

칸 번호가 `해시 값 % 칸 수`라서 칸 수가 바뀌면 같은 키의 칸 번호가 달라집니다. `"name"`은 8칸에서 3번이지만 16칸에서는 11번이라, 3번에 그대로 두면 `get("name")`이 11번 칸을 보고 `None`을 돌려줍니다.
</details>

<details>
<summary>4. 왜 1칸씩이 아니라 2배씩 늘리나요? 꼭 2배여야 하나요?</summary>

1칸씩 늘리면 늘리자마자 다시 기준을 넘어 `set`마다 전체를 옮기게 됩니다(키 100개에 5,029번). 2배씩 늘리면 다음 확장까지의 여유가 점점 커져 191번, 키 하나당 평균 2번 정도로 끝납니다. 중요한 것은 곱하기로 늘린다는 점이라 1.5배여도 됩니다.
</details>

<details>
<summary>5. <code>_resize</code> 안에서 <code>self.set()</code>으로 옮기지 않는 이유는 뭔가요?</summary>

`set`은 `_size`를 늘리고 확장 여부도 다시 확인하기 때문입니다. 옮기는 것은 새 키를 추가하는 것이 아니므로, 새 칸에 직접 `append`합니다.
</details>

<details>
<summary>6. 이 방식의 약점은 뭐고, 실제 레디스는 어떻게 하나요?</summary>

확장이 일어나는 그 한 번의 `set`이 모든 키를 옮기느라 느립니다. 키가 수백만 개면 서버가 잠시 멈춥니다. 레디스는 테이블을 두 개 두고 요청마다 조금씩 옮기는 점진적 재해싱으로 이를 피합니다.
</details>

<details>
<summary>7. 적재율 기준을 0.5나 1.0으로 바꾸면 무엇이 달라지나요?</summary>

0.5로 낮추면 리스트는 더 짧아지지만 테이블의 절반 이상이 빈 칸이라 메모리를 더 씁니다. 1.0으로 높이면 메모리를 아끼는 대신 리스트가 조금 길어집니다. 0.75는 그 사이에서 고른 값이고, 레디스는 1.0을 씁니다.
</details>
