# 2단계: 해시 테이블

## 목표

임시 저장소의 `dict`를 직접 만든 해시 테이블로 바꿉니다. 칸 수는 고정이고, 충돌은 체이닝으로 처리합니다.

완료 기준

- API 동작이 1단계와 같음
- 같은 칸에 여러 키가 이어진 것이 출력으로 확인됨
- 단위 테스트가 모두 통과함

## 핵심 문제

```
"name" ──해시 함수──▶ 3373707 ──% 8──▶ 3번 칸
"city" ──해시 함수──▶ 3053931 ──% 8──▶ 3번 칸   ← 충돌
```

1. 키(문자열)를 칸 번호로 어떻게 바꾸는가 → 해시 함수 + 나머지 연산
2. 두 키가 같은 칸에 오면 어떻게 하는가 → 체이닝: 칸마다 리스트를 두고 `(키, 값)`을 이어 붙임

## 질문과 정리

| 질문 | 정리 |
| --- | --- |
| 해시 함수를 직접 만드는가 | 직접 만듦. 파이썬 `hash()`는 실행할 때마다 문자열의 해시 값이 달라져서(보안 때문) 어떤 키끼리 충돌하는지 재현할 수 없음. 다섯 줄이라 비용도 작음 |
| 같은 칸에 두 키가 오면 | 칸의 리스트에 `(키, 값)`을 이어 붙임. 찾을 때는 그 칸의 리스트만 훑으며 키가 같은 항목을 찾음 |
| 처음 칸 수 | 8개. 적어야 충돌이 자주 일어나 체이닝을 눈으로 볼 수 있음 |
| 체이닝 없이 칸만 늘리면 안 되는가 | 안 됨. 아래 설명 참고 |
| 실제 레디스는 어떤 충돌 처리법을 쓰는가 | 체이닝. 다만 무작위 seed 해시와 점진적 재해싱을 씀. 아래 설명 참고 |
| 연결 리스트(`Node`)로 만들지 않은 이유 | 체이닝 알고리즘은 같고 코드가 더 짧음. 측정해 보니 조회·삭제 속도는 같고, 저장·메모리 차이는 빈 칸 표현과 확장 방식에서 남. 아래 설명 참고 |
| 파이썬 `dict`는 개방 주소법, 레디스는 체이닝을 쓰는 이유 | 처한 상황이 다름. 파이썬은 작은 테이블이 많아 조회 속도와 메모리가 중요하고, 레디스는 거대한 테이블 하나를 멈추지 않고 운영해야 함. 아래 설명 참고 |

### 체이닝 없이 칸만 늘리면 안 되는 이유

1. **해시 값 자체가 같은 키가 있습니다.** `"Aa"`와 `"BB"`는 이 해시 함수에서 둘 다 2112입니다. 칸을 몇 개로 늘려도 언제나 같은 칸에 들어가므로, 충돌을 처리하는 방법이 반드시 있어야 합니다.
2. **해시 값이 달라도 칸이 같을 수 있습니다.** 가능한 키는 무한하고 칸은 유한하므로 충돌은 피할 수 없습니다. 칸을 키 수보다 훨씬 많이 만들어도 충돌은 꽤 일찍 생깁니다(생일 문제: 365칸에 23명만 넣어도 충돌 확률이 50%를 넘음).
3. **늘리는 일은 비쌉니다.** 칸을 늘리면 모든 키의 칸 번호를 다시 계산해 옮겨야 합니다. 충돌할 때마다 늘리면 저장할 때마다 전체를 옮기게 됩니다.

그래서 실제 해시 테이블은 **충돌은 체이닝으로 처리하고, 너무 많이 차면 칸을 늘리는** 두 방법을 함께 씁니다. 칸을 늘리는 것이 3단계입니다. 체이닝이 리스트를 짧게 유지하지 못하는 문제를 칸 늘리기가 보완합니다.

(참고: 리스트 없이 충돌을 처리하는 방법도 있습니다. 충돌하면 옆 칸으로 가서 빈 칸을 찾는 "개방 주소법"입니다. 결정 기록에서 체이닝으로 정했으므로 이번에는 쓰지 않습니다.)

### 실제 레디스는 어떻게 하는가

레디스의 해시 테이블(`dict.c`)도 **체이닝**을 씁니다. 다른 점은 아래와 같습니다.

| | 우리 구현 | 레디스 |
| --- | --- | --- |
| 새 키를 넣는 위치 | 리스트 끝 | 연결 리스트 맨 앞 (끝까지 따라가지 않아도 됨) |
| 해시 함수 | `h * 31 + 문자` (고정) | SipHash + 서버를 켤 때마다 무작위 seed |
| 칸 늘리기 | 한 번에 전부 옮김 (3단계) | 테이블 두 개를 두고 요청마다 조금씩 옮김 (점진적 재해싱) |

- **고정 해시의 트레이드오프**: 우리는 충돌을 재현하려고 고정 해시를 골랐습니다. 대신 같은 칸에 들어가는 키를 쉽게 만들 수 있습니다(`"Aa"`와 `"BB"`가 같으므로 `"AaAa"`, `"AaBB"`, `"BBAa"`, `"BBBB"`도 모두 같음). 공격자가 이런 키를 대량으로 보내 체인을 길게 만드는 것을 **해시 플러딩**이라 하고, 레디스와 파이썬 `hash()`는 무작위 seed로 이를 막습니다. → 재현성을 얻는 대신 보안을 포기한 선택
- **점진적 재해싱**: 키가 많을 때 한 번에 옮기면 그동안 서버가 멈추므로 레디스는 나눠서 옮깁니다. 3단계는 단순한 방식으로 만들고, 이 방식은 시간이 남으면 차별화 요소(R12)로 시도할 수 있습니다.
- **참고**: 레디스의 포크인 Valkey는 8.1에서 CPU 캐시 효율을 위해 개방 주소법 기반 해시 테이블로 바꿨습니다. 체이닝은 단순해서 오래 기본으로 쓰였지만 유일한 정답은 아닙니다. (발표에 쓰려면 Valkey 릴리스 노트로 확인할 것)

### 파이썬 `dict`는 개방 주소법, 레디스는 체이닝을 쓰는 이유

두 방식의 장단점은 같고, 처한 상황이 달라서 선택이 갈렸습니다.

| | 개방 주소법 | 체이닝 |
| --- | --- | --- |
| 조회 | 항목이 배열 하나에 모여 있어 CPU 캐시를 잘 활용함 | 리스트를 따라가며 메모리 여기저기를 읽음 |
| 메모리 | 항목마다 포인터가 필요 없음 | 항목마다 포인터와 별도 할당이 필요함 |
| 삭제 | 까다로움. 그냥 비우면 뒤로 밀려난 키를 못 찾으므로 "지워짐" 표시를 남김 | 쉬움. 리스트에서 빼면 끝 |
| 꽉 찼을 때 | 칸 수보다 많이 담을 수 없고 급격히 느려짐 | 칸 수보다 많이 담을 수 있고 조금씩 느려짐 |

- **파이썬 `dict` → 개방 주소법**: 변수 이름, 객체 속성, 키워드 인자가 모두 `dict`입니다. 작은 테이블이 아주 많고 조회가 대부분이라 조회 속도와 메모리가 가장 중요합니다.
- **레디스 → 체이닝**: 키 수백만 개가 든 테이블 하나를 멈추지 않고 운영해야 합니다. 칸끼리 독립적이라 점진적 재해싱이 쉽고, 만료와 삭제가 많아도 리스트에서 빼면 되며, 확장을 미루는 동안 칸 수보다 많이 담아도 동작합니다.
- **한 줄 정리**: "어느 쪽이 더 좋은가"가 아니라 "무엇을 가장 아껴야 하는 상황인가"로 갈린 선택입니다.

(구조는 소스 코드에서 확인되는 사실이고, "왜 골랐는가"에는 해석이 섞여 있습니다. 발표에서는 "이런 장점 때문으로 보인다"로 말하는 것이 안전합니다.)

### 연결 리스트(`Node`) 대신 파이썬 `list`를 쓴 이유

교과서와 레디스 `dict.c`는 체인을 연결 리스트로 만듭니다. 항목마다 다음 항목을 가리키는 칸을 두고, 칸에는 첫 항목만 둡니다. 우리는 칸마다 파이썬 `list`를 두고 `(키, 값)`을 담았습니다. **체이닝의 핵심인 "칸 찾기 → 그 칸의 항목을 키로 비교"는 두 방식이 똑같고, 체인을 무엇에 담는가만 다릅니다.**

같은 해시 함수, 적재율, 확장 규칙으로 연결 리스트 버전을 만들어 키 10만 개로 비교했습니다. (시간은 여러 번 잰 값의 중앙값)

| 체인 | 저장 | 조회 | 삭제 | 메모리 |
| --- | --- | --- | --- | --- |
| 파이썬 `list` (우리 구현, 3단계 튜플 재사용 전) | 272ms | 65ms | 75ms | 28.1MB |
| 연결 리스트 (`Node`에 `__slots__`) | 215ms | 63ms | 68ms | 10.5MB |

- **조회와 삭제는 같습니다.** 칸마다 항목이 평균 1개 수준이라 훑는 방식의 차이가 드러나지 않습니다.
- **메모리 차이는 빈 칸에서 납니다.** 키 10만 개면 칸이 262,144개이고 그중 178,267개가 빈 칸인데, 우리 구현은 빈 칸에도 빈 리스트 객체(56바이트)를 하나씩 둡니다. 그것만 17.4MB입니다. 연결 리스트는 빈 칸이 `None`입니다.
- **저장 차이는 확장에서 납니다.** 우리 구현은 확장할 때 빈 리스트를 2배 개수만큼 새로 만들고 튜플도 새로 만들어 옮겼습니다. 연결 리스트는 노드의 연결만 바꿉니다. 튜플을 새로 만드는 부분은 3단계에서 그대로 옮기도록 고쳤습니다(저장 약 6% 개선).

| | 파이썬 `list` | 연결 리스트 |
| --- | --- | --- |
| 코드 | 짧음. 삭제는 `pop(i)` 한 줄 | 첫 노드를 지울 때를 따로 처리하고 이전 노드도 따라가야 함 |
| 체이닝이 보이는가 | `list` 뒤에 숨음 | 노드가 다음 노드를 가리키는 구조가 코드에 드러남. 교과서, 레디스 `dict.c`와 같은 모양 |
| 새 키를 넣는 위치 | 끝 | 보통 맨 앞 (끝까지 가지 않아도 됨) |
| 확장 | 칸 리스트를 새로 만듦 | 연결만 바꿔 옮김 |
| 동시성, 만료 | 같음 (`Store`가 처리) | 같음 |

레디스가 연결 리스트를 쓰는 데에는 C 언어의 사정도 있습니다. 칸마다 크기가 변하는 배열을 두기 번거롭고, 항목 안에 다음을 가리키는 칸을 두면 메모리 할당이 적으며, 점진적 재해싱 때 항목을 새로 만들지 않고 옮길 수 있습니다. 파이썬에서는 `list`가 C로 구현된 동적 배열이라 짧은 체인을 훑는 데 빠르고 코드가 짧습니다. **설명에는 연결 리스트가 더 잘 보이고, 코드 길이에는 `list`가 유리합니다.** 이 트레이드오프를 알고 코드 길이를 택했습니다. 빈 칸을 `None`으로 두면 메모리 차이는 대부분 사라지지만, 네 함수에 `None` 확인 분기가 생겨 하지 않았습니다.

## 이 단계에서 정한 것

| 관련 코드 | 정한 것 | 이유 |
| --- | --- | --- |
| `store.py` `Store.__init__` · `hash_table.py` 전체 | 해시 테이블은 `hash_table.py`의 `HashTable`로 분리하고, `Store`는 그것을 감쌈 | 해시 테이블은 순수한 자료구조로 두고, 4단계의 만료와 5단계의 lock은 `Store`에서 처리 |
| `hash_table.py` `__init__` (`capacity=8`) | 처음 칸 수는 8 | 충돌이 자주 일어나 체이닝을 눈으로 확인하기 쉬움 |
| `hash_table.py` `__init__` (`_buckets`) · `set`, `get`, `delete` | 충돌 처리는 체이닝 | 구현과 설명이 단순하고 널리 쓰이는 방식. 실제 레디스도 체이닝을 씀 (DESIGN.md 제안과 같음) |
| `hash_table.py` `__init__` (`_buckets = [[] ...]`) · `set`, `get`, `delete` | 칸의 체인은 파이썬 `list`로 만들고, `Node` 클래스로 연결 리스트를 직접 만들지 않음 | 체이닝의 핵심은 "칸 찾기 → 그 칸의 항목을 키로 비교"이고, 체인을 무엇에 담든 이 알고리즘은 같음. 파이썬 `list`는 C로 구현된 동적 배열이라 짧은 체인을 훑는 데 빠르고, 삭제가 `pop(i)` 한 줄이라 첫 노드를 따로 처리할 필요가 없어 코드가 짧음. 연결 리스트 버전을 만들어 키 10만 개로 재 보니 조회·삭제 속도는 같았고, 저장은 약 20% 느리고 메모리는 2.7배(28MB 대 10.5MB)였음. 원인은 빈 칸마다 빈 리스트 객체(56바이트)를 두는 것과 확장 때 튜플을 새로 만든 것(3단계에서 고침)이며, 체이닝 알고리즘의 차이가 아님. 연결 리스트는 노드가 다음 노드를 가리키는 구조가 코드에 드러나 교과서와 레디스 `dict.c`와 같은 모양이라 설명에는 유리함. 이 트레이드오프를 알고 코드 길이를 택함 |
| `hash_table.py` `_hash` | 해시 함수는 직접 구현 (`h = h * 31 + 문자 코드`를 32비트 안으로 자름) | 파이썬 `hash()`는 실행할 때마다 값이 달라져서 어떤 키끼리 충돌하는지 재현할 수 없음. 해시 테이블 전체를 직접 설명할 수 있음 |
| `hash_table.py` `set` (`bucket[i] = (key, value)`, `bucket.append(...)`) | 칸의 항목은 `(키, 값)` 튜플. 덮어쓸 때는 튜플을 새로 바꿔 넣음 | 같은 칸의 항목 중 키가 일치하는 것을 찾아야 하므로 키와 값을 함께 저장 (DESIGN.md 제안과 같음) |
| `hash_table.py` `dump` | 칸 상태를 보는 `dump()`를 둠 | 완료 기준 "같은 칸에 여러 키가 이어진 것이 출력으로 확인됨"을 확인하기 위함 |
| `tests/` · `pytest.ini` · `requirements.txt` | 단위 테스트 도구는 pytest, 테스트는 `tests/` 폴더 | `assert` 한 줄로 쓸 수 있어 읽기 쉬움 |

## 주요 함수

| 함수 | 하는 일 |
| --- | --- |
| `_hash(key)` | 문자를 하나씩 읽으며 `h = h * 31 + 문자 코드`. 결과를 32비트 안으로 자름 |
| `_index(key)` | `_hash(key) % 칸 수`. 칸 번호는 0 ~ 7 |
| `set(key, value)` | 칸을 찾고, 같은 키가 있으면 값을 바꾸고 없으면 리스트 끝에 붙임 |
| `get(key)` | 칸을 찾고, 리스트에서 키가 같은 항목의 값을 돌려줌. 없으면 `None` |
| `delete(key)` | 칸을 찾고, 리스트에서 키가 같은 항목을 빼면 `True`. 없으면 `False` |

세 함수 모두 **칸 찾기 → 그 칸의 리스트만 훑기**로 같은 모양입니다. 전체를 훑지 않고 한 칸만 보므로 빠릅니다.

## 코드에서 알아 둘 것

- **`[[] for _ in range(8)]`과 `[[]] * 8`은 다릅니다.** 뒤의 것은 같은 리스트 하나를 8번 가리켜서, 한 칸에 넣으면 모든 칸에 들어간 것처럼 보입니다.
- **`& 0xFFFFFFFF`** 는 숫자를 32비트 안으로 자릅니다. 파이썬 정수는 한없이 커질 수 있어서, 긴 키에서 숫자가 불필요하게 커지는 것을 막습니다.
- **31을 곱하는 이유**: 문자의 순서를 해시 값에 반영하기 위해서입니다. 더하기만 하면 `"ab"`와 `"ba"`가 같은 값이 됩니다. 31은 자바의 문자열 해시에서도 쓰는 홀수 소수입니다.
- 테스트에서 `_index`, `_hash`처럼 `_`로 시작하는 내부 함수를 부르는 것은 충돌을 확인하기 위해서입니다. 서버는 이 함수들을 부르지 않습니다.

## 6단계로 미룬 것

- 문자열이 아닌 키(`"key": 123`)를 `/set`으로 보내면, 1단계에서는 저장됐지만 이제는 `_hash`에서 오류가 나 500이 됩니다. 6단계에서 400으로 걸러냅니다.

## 이해 확인 질문

코드를 보지 않고 한두 문장으로 답해 봅니다. 답은 눌러서 펼칠 수 있습니다.

<details>
<summary>1. <code>"name"</code>을 <code>set</code>하면 어떤 순서로 몇 번 칸에 들어가나요?</summary>

`_hash("name")`이 문자를 하나씩 읽으며 `h * 31 + 문자 코드`를 계산해 3373707을 만들고, `% 8`로 나머지 3을 구해 3번 칸에 넣습니다. 3번 칸에 `"name"`이 이미 있으면 값만 바꾸고, 없으면 리스트 끝에 `("name", 값)`을 붙입니다.
</details>

<details>
<summary>2. <code>get("city")</code>를 할 때, 같은 칸에 있는 <code>"name"</code>의 값을 잘못 돌려주지 않는 이유는 뭔가요?</summary>

칸에 값만이 아니라 `(키, 값)`을 함께 저장하고, 칸의 리스트를 훑으며 키가 `"city"`와 같은 항목의 값만 돌려주기 때문입니다.
</details>

<details>
<summary>3. 같은 키로 <code>set</code>을 두 번 하면 리스트에 항목이 두 개가 되나요?</summary>

아닙니다. `set`은 붙이기 전에 칸의 리스트에서 같은 키를 먼저 찾고, 있으면 그 자리의 튜플을 새 값으로 바꿉니다. 그래서 `len`도 1로 유지됩니다.
</details>

<details>
<summary>4. 파이썬 <code>hash()</code> 대신 해시 함수를 직접 만든 이유는 뭔가요?</summary>

파이썬 `hash()`는 문자열의 해시 값이 실행할 때마다 달라져서, 어떤 키끼리 충돌하는지 재현하고 테스트할 수 없기 때문입니다. 직접 만들면 해시 테이블 전체를 설명할 수도 있습니다. 대신 해시 플러딩에는 약합니다.
</details>

<details>
<summary>5. 칸이 8개뿐인데 키 50개를 넣어도 왜 모두 조회되나요? 이때의 문제는 뭔가요?</summary>

체이닝 덕분에 한 칸에 여러 키를 이어 붙일 수 있어서 모두 저장되고 조회됩니다. 문제는 칸마다 평균 6개 이상이 이어져 리스트가 길어지고, 조회할 때 훑어야 하는 항목이 늘어나 느려진다는 점입니다. 키가 늘수록 계속 느려지므로 칸 수를 늘려야 합니다(3단계).
</details>

<details>
<summary>6. 체이닝 없이 칸만 계속 늘리면 안 되는 이유는 뭔가요?</summary>

`"Aa"`와 `"BB"`처럼 해시 값 자체가 같은 키는 칸을 아무리 늘려도 같은 칸에 들어가므로, 충돌을 처리하는 방법이 반드시 필요합니다. 또 칸을 늘릴 때마다 모든 키를 옮겨야 해서 비쌉니다.
</details>
