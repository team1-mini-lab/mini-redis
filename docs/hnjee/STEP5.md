# 5단계: lock

## 목표

저장소 함수(`set`, `get`, `delete`)를 lock으로 감싸서, 여러 스레드가 동시에 저장소를 써도 데이터가 망가지지 않게 합니다.

완료 기준

- 여러 스레드가 동시에 저장과 조회를 반복해도 오류가 없음
- lock이 없으면 같은 테스트가 깨지는 것을 먼저 확인함
- API 동작이 4단계와 같음
- 단위 테스트가 모두 통과함

## 핵심 문제

지금까지는 "요청이 하나씩 차례로 온다"고 가정했습니다. 그런데 Flask 개발 서버는 **요청마다 스레드를 하나씩 만들어 동시에 처리합니다.** 그리고 모든 스레드가 `server.py`의 `store` 하나를 함께 씁니다.

스레드는 함수가 끝날 때가 아니라 **줄과 줄 사이 아무 곳에서나** 교대될 수 있습니다. 그래서 한 스레드가 저장소를 고치는 **중간 상태**를 다른 스레드가 보게 됩니다.

```python
def _resize(self):
    old_buckets = self._buckets
    self._buckets = [[] for _ in range(len(old_buckets) * GROWTH_FACTOR)]   # ① 새 칸은 텅 빔
    for bucket in old_buckets:                                             # ② 아직 옮기기 전
        ...
```

스레드 A가 ①까지 실행한 순간 스레드 B가 끼어들면 이런 일이 생깁니다.

| B가 한 일 | 결과 |
| --- | --- |
| `get("name")` | 새 칸이 비어 있어 `None`. 저장돼 있는 키에 404 |
| `set("name", "민수")` | 빈 새 칸에 새 키로 붙고, A가 예전 `name`도 옮겨 와 같은 키가 두 개가 됨 |

풀어야 할 문제는 세 가지입니다.

1. 어디에 lock을 거는가 → `Store` 안. `set`, `get`, `delete` 세 함수 전체
2. lock을 몇 개 두는가 → 저장소 전체에 하나
3. lock이 정말 필요한지 어떻게 보이는가 → lock 없이 먼저 테스트해 깨지는 것을 봄

## 질문과 정리

| 질문 | 정리 |
| --- | --- |
| resize 도중에 다른 스레드가 `get`하면 | 새 칸이 비어 있어 저장된 키를 못 찾음. 잠시 뒤에는 다시 찾아져서 재현하기 어려운 버그가 됨 |
| lock은 무엇인가 | 한 번에 한 스레드만 통과하는 문. `with self._lock:` 블록 안은 한 번에 한 스레드만 실행하고, 다른 스레드는 문 앞에서 기다림 |
| lock을 `HashTable`에 걸면 안 되는가 | 부족함. `Store.get`은 꺼내기 → 만료 확인 → 지우기를 `HashTable` 호출 두 번으로 하므로, 그 **사이**가 보호되지 않음. 아래 설명 참고 |
| lock을 `server.py`에 걸면 안 되는가 | 사용하는 쪽이 lock을 책임지게 됨. 8단계 데모 API나 테스트가 `Store`를 직접 쓰면 lock을 빠뜨릴 수 있음 |
| `Store`와 `HashTable` 둘 다 걸면 | 멈추지는 않지만 얻는 게 없음. 아래 설명 참고 |
| 칸마다 lock을 두면 더 빠르지 않은가 | 복잡도에 비해 얻는 게 적음. 아래 설명 참고 |
| 쓰기에만 lock을 걸면 되는가 | 안 됨. 읽기도 고치는 중간 상태를 볼 수 있음. 아래 설명 참고 |
| 레디스는 lock이 없다던데 | 레디스는 명령을 스레드 하나로 실행해 동시 접근 자체가 없음. 우리는 lock 하나로 같은 보장을 얻음. 아래 설명 참고 |
| 스레드 하나로 실행하는 서버가 더 좋지 않은가 | 조건에 따라 다름. 아래 "팀에 설명할 때" 참고 |
| lock 없이 무엇이 깨지는가 | 저장에 성공했는데 조회되지 않는 키가 생기고, `IndexError`로 스레드가 죽기도 함. 아래 설명 참고 |
| lock 덕분에 통과했다는 걸 어떻게 아는가 | lock 없는 코드로 같은 테스트를 먼저 돌려 깨지는 것을 봄 |

### lock은 의미 있는 동작 하나의 단위로

4단계의 `Store.get`은 `HashTable`을 두 번 부릅니다.

```python
def get(self, key):
    item = self._table.get(key)          # ① 꺼냄
    ...                                  #    ← 여기서 다른 스레드가 끼어들 수 있음
    if self._is_expired(expires_at):
        self._table.delete(key)          # ② 지움
        return None
```

lock이 `HashTable` 안에만 있으면 ①과 ② 각각은 안전하지만 그 사이는 보호되지 않습니다. `name`이 만료된 상태에서 이렇게 실행되면 문제가 생깁니다.

1. 스레드 A가 `get("name")`의 ①에서 만료된 항목을 꺼내고 "만료됐다"고 판단함
2. 스레드 B가 `set("name", "민수")`를 끝까지 실행함
3. 스레드 A가 ②에서 `delete("name")`을 실행함 → **B가 방금 저장한 `"민수"`가 지워짐**

B는 저장 성공 응답까지 받았는데 값이 사라지고, 에러도 나지 않습니다.

- `Store`가 지키는 것은 칸들만이 아니라 "꺼내고, 만료를 확인하고, 지운다"처럼 **여러 단계로 이뤄진 동작 하나**입니다. lock의 범위는 데이터 단위가 아니라 이 동작의 단위로 정합니다.
- 그 동작을 아는 쪽이 `Store`이므로 lock은 `Store`에 둡니다.
- `server`는 사용하는 쪽이라 lock을 모릅니다.

### `HashTable`에는 lock을 걸지 않음

lock 안에 lock을 거는 것 자체가 언제나 안 되는 것은 아닙니다.

| 경우 | 결과 |
| --- | --- |
| 같은 `Lock`을 같은 스레드가 두 번 잠금 | 자기가 잠근 문이 풀리길 자기가 기다려서 영원히 멈춤 (교착 상태) |
| 서로 다른 lock 두 개를 항상 같은 순서로 잠금 | 동작함 |
| 서로 다른 lock 두 개를 스레드마다 다른 순서로 잠금 | A는 1번을 쥐고 2번을, B는 2번을 쥐고 1번을 기다리면 영원히 멈춤 |

`Store`의 lock과 `HashTable`의 lock은 서로 다르고 순서도 늘 `Store` → `HashTable`이라 멈추지는 않습니다. 그래도 걸지 않는 이유는 **얻는 게 없어서**입니다.

- `HashTable`을 부르는 곳은 `Store`뿐이고, 언제나 `Store`의 lock 안에서 부릅니다. 안쪽 문에 도착하는 스레드는 늘 한 개라 안쪽 문은 한 번도 누구를 막지 않습니다.
- `HashTable`은 순수한 자료구조로 두고, lock은 `Store`에서 처리한다는 2단계 결정과 맞습니다. 파이썬 `dict`나 자바 `HashMap`도 그 자체로는 lock이 없고, 쓰는 쪽이 감쌉니다.

### 칸마다 lock을 두지 않는 이유

```
lock 하나                              칸마다 lock
┌─────────────────────────┐           [0] 🔒 Aa -> BB
│ [0] Aa -> BB            │           [3] 🔒 name   ← A는 3번 칸만 잠금
│ [3] name   ← A          │           [5] 🔒 city   ← B는 5번 칸만 잠금. 동시에 실행
│ [5] city   ← B는 기다림 │
└─────────────────────────┘
```

칸마다 lock을 두면 서로 다른 칸의 요청은 기다리지 않아 빨라 보입니다. 하지만 resize 때는 **모든 칸을 다 잠가야** 하고, 그러면 이런 일이 생깁니다.

- 칸이 256개면 lock 256개를 늘 같은 순서로 잠가야 합니다. 순서가 어긋나면 교착 상태가 생깁니다.
- 칸 수가 바뀌면 lock도 다시 만들어야 하고, lock을 바꾸는 동안 그것을 지켜 줄 또 다른 lock이 필요합니다.
- `_size`는 모든 칸이 함께 쓰는 값이라 lock이 하나 더 필요합니다.
- 4단계의 `Store.get`은 꺼내기부터 지우기까지 그 칸의 lock을 쥐고 있어야 합니다.

복잡도는 크게 늘지만 얻는 것은 적습니다.

- **파이썬은 GIL 때문에** 스레드가 여러 개여도 파이썬 코드는 한 번에 한 스레드만 실행합니다. 칸마다 lock을 두어도 진짜 동시 실행은 거의 일어나지 않습니다.
- **실제 레디스도 명령을 한 번에 하나씩 처리합니다.** 명령 하나가 아주 짧은 메모리 작업이라 그래도 충분히 빠릅니다.

(참고: 자바의 예전 `ConcurrentHashMap`이 칸을 여러 구역으로 나눠 구역마다 lock을 두는 비슷한 구조였습니다. 발표 때 비교 거리로 쓸 수 있습니다.)

### 읽기에도 lock이 필요함

**여러 스레드가 함께 쓰는 데이터를 어느 한 스레드라도 고칠 수 있다면, 그 데이터에 대한 모든 접근을 lock 안에서 해야 합니다.** 읽기도 포함합니다. resize 도중에 문제를 일으킨 쪽도 B의 `get`, 즉 읽기였습니다.

| 함께 일어나는 동작 | lock이 필요한가 |
| --- | --- |
| 읽기와 읽기 | 둘 다 고치지 않으므로 서로 문제없음 |
| 읽기와 쓰기 | 필요함. 읽는 쪽이 고치는 중간 상태를 봄 |
| 쓰기와 쓰기 | 필요함. 같은 키가 두 개가 되거나 `_size`가 틀어짐 |

그래서 `Store`의 세 함수 전부를 감쌉니다. `_resize`는 `HashTable.set` 안에서 일어나고, `HashTable.set`은 `Store.set`의 lock 안에서 불리므로 따로 lock을 걸지 않아도 저절로 보호됩니다.

(참고: "읽기끼리는 동시에, 쓰기는 혼자" 들어가게 하는 읽기-쓰기 lock도 있습니다. 파이썬 표준 라이브러리에는 없고 더 복잡해서 쓰지 않습니다.)

### lock이 없으면 무엇이 깨지는가: 꺼내 둔 값은 "그 시점의 사진"

스레드 10개가 각자 서로 다른 키 100개씩, 모두 1,000개를 동시에 `set`하면 lock이 없을 때 두 가지가 깨집니다.

**1. 저장에 성공했는데 조회되지 않는 키**

```python
def set(self, key, value):
    bucket = self._buckets[self._index(key)]   # B가 A의 resize 전에 실행 → 예전 칸 리스트를 쥠
    ...
    bucket.append((key, value))                # A가 그 칸을 다 옮긴 뒤에 붙임
    self._size += 1                            # 키 수는 늘어남
```

| 확인 | 결과 |
| --- | --- |
| `key500`이 들어간 곳 | 예전 칸 리스트. resize가 끝나면 `self._buckets`에서 닿을 수 없는 리스트 |
| `get("key500")` | 새 칸만 보므로 `None` |
| `len()` | B가 `_size`를 늘렸으므로 이 키도 셈 |

B의 `set`이 끝나면 그 예전 리스트를 쥔 곳이 하나도 남지 않아 파이썬이 메모리에서 치우고, `key500`은 완전히 사라집니다.

**2. `IndexError`로 스레드가 죽음**

```python
bucket = self._buckets[self._index(key)]
```

파이썬은 이 줄에서 `self._buckets`를 **먼저** 읽고, 그다음 `_index(key)`를 계산합니다. 그 사이에 resize가 일어나면 8칸짜리 예전 리스트를 쥔 채로, 16칸 기준의 칸 번호(0 ~ 15)를 받습니다. 번호가 8 이상이면 `IndexError: list index out of range`가 납니다.

두 문제의 원인은 같습니다. **`self._buckets`처럼 공유 데이터를 지역 변수나 계산 중간에 꺼내 두는 순간, 그 값은 "그 시점의 사진"이 됩니다.** 다른 스레드가 원본을 바꿔도 사진은 그대로입니다. 2~4단계에서는 스레드가 하나라 사진과 원본이 늘 같아서 문제가 보이지 않았습니다.

lock으로 `Store.set` 전체를 감싸면 B는 A의 `set`이 확장까지 모두 끝낸 뒤에야 들어오므로, 칸을 꺼낼 때는 언제나 새 칸입니다.

실제로 돌려 본 결과입니다. (구현 전 코드를 복사해 확인)

| 조건 | 20번 실행 결과 |
| --- | --- |
| lock 없음, 파이썬 기본 설정 | 20번 모두 통과 (깨지는 것을 볼 수 없음) |
| lock 없음, 스레드를 아주 자주 교대 | 20번 모두 깨짐. `IndexError`, 키 수 643개인데 조회되는 키 452개 등 |
| lock 있음, 스레드를 아주 자주 교대 | 20번 모두 통과 |

파이썬은 기본으로 약 0.005초마다 스레드를 교대시킵니다. 키 1,000개 저장은 그보다 훨씬 빨리 끝나서 끼어들 틈이 거의 없습니다. 그래서 테스트에서는 `sys.setswitchinterval(1e-6)`으로 교대를 아주 자주 일어나게 해 문제를 드러냅니다. **문제가 안 보인다고 문제가 없는 것이 아니라, 타이밍이 맞을 때만 나타나는 것**입니다.

### 레디스는 lock 없이, 우리는 lock으로

| | 레디스 | 우리 서버 (Flask 개발 서버) |
| --- | --- | --- |
| 명령을 실행하는 스레드 | 하나 | 요청마다 하나씩 새로 만듦 |
| 여러 요청을 받는 방법 | 이벤트 루프: 스레드 하나가 여러 연결을 번갈아 보며 도착한 명령을 하나씩 실행 | 스레드 여러 개가 각자 요청 하나씩 맡음 |
| 저장소에 동시에 접근하는가 | 안 함 | 함. 모든 스레드가 `store` 하나를 씀 |
| lock | 필요 없음 | 필요함 |

레디스가 lock 없이 되는 이유는 **애초에 동시에 접근할 스레드가 없기 때문**입니다. 결과는 같습니다. 저장소 전체에 lock이 하나면 저장소 명령은 한 번에 하나씩만 실행됩니다. 요청을 받고 응답을 보내는 일은 스레드들이 동시에 하고, 저장소를 만지는 순간만 줄을 섭니다.

(참고: 레디스 6부터는 네트워크 읽기와 쓰기에 스레드를 여러 개 쓸 수 있습니다. 명령 실행은 여전히 스레드 하나입니다.)

### 팀에 설명할 때: "스레드 하나로 실행하는 서버가 더 좋지 않았나?"

| | 스레드 여러 개 + lock (우리 선택) | 스레드 하나 |
| --- | --- | --- |
| 저장소 보호 | lock 필요 | lock 필요 없음 |
| 느린 요청 하나가 생기면 | 그 요청만 느림 | 뒤의 모든 요청이 기다림 |
| 저장소의 안전 | `Store`가 스스로 보장 | "서버가 스레드를 하나만 쓴다"는 바깥의 약속에 기댐 |
| 파이썬에서 만드는 법 | Flask 그대로 | `asyncio`로 서버를 새로 짜거나, Flask `threaded=False` (연결을 하나씩만 받음) |

먼저 인정할 부분: 미니 레디스 서버만 보면 명령이 모두 짧은 메모리 작업이라 스레드 하나도 좋은 선택입니다. "동시 접근 자체를 없앤다"도 과제의 동시성 요구에 대한 훌륭한 답입니다.

> 미니 레디스 서버만 보면 스레드 하나도 좋은 선택이라고 생각합니다. 명령이 짧아서 레디스와 같은 조건이니까요. 다만 그 방식은 "서버가 스레드를 하나만 쓴다"는 바깥의 약속에 기대야 합니다. 저는 저장소가 어떤 서버에서, 몇 개의 스레드가 쓰든 스스로 안전하길 원해서 `Store` 안에 lock을 하나 뒀습니다. lock이 하나라 명령은 한 번에 하나씩 실행되므로, 결과적으로 레디스와 같은 보장을 얻습니다.

"어느 쪽이 더 좋은가"보다 **"어떤 조건이면 어느 쪽이 낫다"**까지 말하면 비교와 기준 구현 선택에 도움이 됩니다.

## 이 단계에서 정한 것

| 관련 코드 | 정한 것 | 이유 |
| --- | --- | --- |
| `server.py` 맨 아래 (`app.run`) | 서버는 요청마다 스레드를 쓰는 Flask 기본 방식을 유지. 스레드 하나로 바꾸지 않음 | 느린 요청이 다른 요청을 막지 않음. 저장소의 안전은 서버 구조가 아니라 `Store`의 lock이 보장 |
| `store.py` `Store.__init__` (`_lock`) | lock은 `Store` 안에서 처리하고, 서버는 lock을 모름 | 저장소를 사용하는 쪽에서 lock을 빠뜨릴 수 없게 함. 만료 확인처럼 여러 단계로 된 동작을 아는 쪽이 `Store` (DESIGN.md 제안과 같음) |
| `store.py` `Store.__init__` (`_lock`) | 저장소 전체에 lock 하나. 칸마다 lock을 두지 않음 | resize 때 모든 칸을 잠가야 하고, 칸 수가 바뀌면 lock도 다시 만들어야 함. GIL 때문에 얻는 것도 적음. 명령을 하나씩 실행하는 레디스와 같은 보장 (DESIGN.md 제안과 같음) |

| `store.py` `Store.set`, `get`, `delete` | 세 함수의 전체를 `with self._lock:`으로 감쌈. 읽기인 `get`도 포함 | 읽기도 고치는 중간 상태를 볼 수 있음. `get`의 꺼내기 → 만료 확인 → 지우기 사이에 끼어들면 새 값이 지워짐 |
| `hash_table.py` | `HashTable`에는 lock을 걸지 않음 | 순수한 자료구조로 둠(2단계 결정). `Store`의 lock 안에서만 불려 안쪽 lock은 아무도 막지 않음 |
| `tests/test_store.py` | 동시성 테스트는 `test_store.py`에 추가하고, 테스트 동안 `sys.setswitchinterval(1e-6)`으로 스레드를 자주 교대시킴 | 기본 설정에서는 lock 없이도 20번 모두 통과해 lock의 효과를 확인할 수 없음. 자주 교대하면 lock 없이 20번 모두 깨짐 |
| `tests/test_store.py` (완료 테스트 순서) | lock 없는 코드로 동시성 테스트가 깨지는 것을 먼저 본 뒤 lock을 추가 | "lock 덕분에 통과했다"고 말할 수 있음 |

## 주요 함수

```python
import threading
import time

from hash_table import HashTable


class Store:
    def __init__(self, clock=time.monotonic):
        self._table = HashTable()
        self._clock = clock
        self._lock = threading.Lock()  # 저장소 전체에 lock 하나

    def set(self, key, value, ttl=None):
        with self._lock:  # 블록을 나오면 자동으로 풀림. 오류가 나도 풀림
            expires_at = None if ttl is None else self._clock() + ttl
            self._table.set(key, (value, expires_at))

    def get(self, key):
        with self._lock:  # 꺼내기 → 만료 확인 → 지우기를 한 덩어리로
            item = self._table.get(key)
            ...  # 4단계와 같음

    def delete(self, key):
        with self._lock:
            ...  # 4단계와 같음
```

| 부분 | 하는 일 |
| --- | --- |
| `threading.Lock()` | 한 번에 한 스레드만 쥘 수 있는 lock을 만듦 |
| `with self._lock:` | 들어갈 때 잠그고, 블록을 나올 때 자동으로 풂. `return`이나 오류로 나가도 풀림 |
| `_is_expired` | 고치지 않음. 언제나 lock 안에서만 불림 |

### 2. lock을 빼면 무엇이 깨지는지 직접 보기

lock을 추가한 뒤에도, 코드를 고치지 않고 lock만 "아무것도 안 하는 문"(`contextlib.nullcontext()`)으로 바꿔서 볼 수 있습니다.

```bash
python -c '
import contextlib, sys, threading
from store import Store
sys.setswitchinterval(1e-6)              # 스레드를 아주 자주 교대
store = Store()
store._lock = contextlib.nullcontext()   # lock을 아무것도 안 하는 문으로 바꿈
errors = []
def worker(n):
    try:
        for i in range(100):
            store.set(f"key{n * 100 + i}", i)
    except Exception as e:
        errors.append(type(e).__name__)
threads = [threading.Thread(target=worker, args=(n,)) for n in range(10)]
for t in threads: t.start()
for t in threads: t.join()
found = sum(store.get(f"key{k}") is not None for k in range(1000))
print("오류:", len(errors), "개", set(errors))
print("키 수(len):", len(store._table), "/ 실제로 조회되는 키:", found, "/ 기대: 1000")
' 2>/dev/null
```

기대 결과 (숫자는 실행마다 다름)

```
오류: 4 개 {'IndexError'}
키 수(len): 643 / 실제로 조회되는 키: 452 / 기대: 1000
```

- 오류가 난 스레드는 맡은 키를 끝까지 저장하지 못해 키 수가 1,000보다 작습니다.
- **키 수와 실제로 조회되는 키 수가 다른 것**이 "저장에 성공했는데 조회되지 않는 키"입니다.
- `store._lock = ...` 줄을 지우고 다시 실행하면 `오류: 0 개`, `1000 / 1000`이 나옵니다.
- `2>/dev/null`은 죽은 스레드들의 긴 오류 메시지를 숨기는 옵션입니다.

## 알아 둘 것

- **`curl`로 동시에 요청을 보내 보는 것으로는 lock의 효과를 확인하기 어렵습니다.** 요청 하나를 처리하는 시간에 비해 저장소를 만지는 순간이 아주 짧아서 겹칠 일이 거의 없습니다. 그래서 단위 테스트에서 스레드 교대를 자주 일으켜 확인합니다. 동시 요청 테스트는 10단계에서 보완합니다.
- **`sys.setswitchinterval`은 파이썬 전체의 설정입니다.** 그래서 fixture로 테스트 동안만 바꾸고, 끝나면 원래 값으로 되돌립니다.
- **lock 안에서는 짧은 일만 합니다.** lock을 쥔 동안 다른 모든 요청이 기다리므로, 느린 작업(네트워크, 파일)은 lock 밖에서 해야 합니다. 지금 `Store`는 메모리 작업만 해서 문제없습니다.
- **`with` 대신 `acquire()`와 `release()`를 직접 부를 수도 있습니다.** 하지만 중간에 `return`이나 오류가 나면 `release()`를 빠뜨려 lock이 영원히 잠깁니다. `with`는 어떻게 나가든 풀어 줍니다.

## 이해 확인 질문

코드를 보지 않고 한두 문장으로 답해 봅니다. 답은 눌러서 펼칠 수 있습니다.

<details>
<summary>1. 4단계까지는 문제가 없었는데, 왜 이제 lock이 필요한가요?</summary>

Flask 개발 서버는 요청마다 스레드를 만들어 동시에 처리하고, 모든 스레드가 `store` 하나를 함께 씁니다. 스레드는 줄과 줄 사이 아무 곳에서나 교대될 수 있어서, 한 스레드가 저장소를 고치는 중간 상태를 다른 스레드가 볼 수 있습니다.
</details>

<details>
<summary>2. resize 도중에 다른 스레드가 <code>get</code>하면 어떻게 되나요?</summary>

resize는 새 칸을 먼저 만들고 키를 옮깁니다. 옮기기 전에 끼어들면 새 칸이 비어 있어서, 저장돼 있는 키인데도 `None`을 돌려받고 API는 404를 냅니다.
</details>

<details>
<summary>3. lock을 <code>HashTable</code>이 아니라 <code>Store</code>에 거는 이유는 뭔가요?</summary>

`Store.get`은 꺼내기 → 만료 확인 → 지우기를 `HashTable` 호출 두 번으로 합니다. `HashTable`에만 lock이 있으면 두 호출 사이에 다른 스레드가 새 값을 저장했다가 지워질 수 있습니다. lock의 범위는 의미 있는 동작 하나의 단위여야 하고, 그 동작을 아는 쪽이 `Store`입니다.
</details>

<details>
<summary>4. <code>get</code>은 읽기만 하는데 왜 lock 안에서 실행하나요?</summary>

다른 스레드가 고치는 중간 상태를 읽을 수 있기 때문입니다. resize 중에 빈 새 칸을 읽는 것이 그 예입니다. 또 우리 `get`은 만료된 항목을 지우기도 하므로 쓰기이기도 합니다.
</details>

<details>
<summary>5. 칸마다 lock을 두지 않고 저장소 전체에 하나만 두는 이유는 뭔가요?</summary>

resize 때는 결국 모든 칸을 잠가야 하고, 칸 수가 바뀌면 lock도 다시 만들어야 하며, `_size`도 따로 보호해야 해서 복잡해집니다. 파이썬은 GIL 때문에 진짜 동시 실행이 거의 없어 얻는 것도 적습니다.
</details>

<details>
<summary>6. lock이 없을 때 "저장에 성공했는데 조회되지 않는 키"는 어떻게 생기나요?</summary>

스레드 B가 resize 전에 예전 칸 리스트를 지역 변수로 꺼내 두고, A가 그 칸을 다 옮긴 뒤에 거기에 키를 붙입니다. 그 리스트는 resize가 끝나면 아무도 보지 않으므로 키가 사라지는데, `_size`는 늘어서 키 수와 실제로 조회되는 수가 어긋납니다.
</details>

<details>
<summary>7. 레디스는 lock이 없는데, 우리는 왜 lock을 쓰나요?</summary>

레디스는 명령을 스레드 하나로 실행해 동시 접근 자체가 없습니다. 우리 서버는 요청마다 스레드를 쓰므로 lock이 필요합니다. 저장소 전체에 lock이 하나라 명령이 한 번에 하나씩 실행되므로, 결과적으로 레디스와 같은 보장을 얻습니다.
</details>

<details>
<summary>8. lock 없이도 테스트가 통과할 수 있는데, lock이 필요하다는 걸 어떻게 보였나요?</summary>

파이썬은 기본으로 약 0.005초마다 스레드를 교대시켜 끼어들 틈이 거의 없습니다. 테스트에서 `sys.setswitchinterval(1e-6)`으로 교대를 아주 자주 일으키면 lock 없는 코드는 매번 깨지고, lock이 있으면 매번 통과합니다. lock 없이 먼저 깨지는 것을 봤기 때문에 "lock 덕분에 통과했다"고 말할 수 있습니다.
</details>
