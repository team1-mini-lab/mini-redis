# 미니 레디스 전체 그림

미니 레디스가 하는 일을 가장 작은 예시로 처음부터 끝까지 따라가는 문서입니다.
레디스와 DBMS의 관계는 `OVERVIEW.md`를, 범위와 접점은 `DESIGN.md`를 참고합니다.

## 1. 한눈에 보기

```
외부 프로그램
   │ 요청 (저장 / 조회 / 삭제 + 키, 값, 만료 기간)
   ▼
서버: 요청 해석 → 저장소 함수 호출 → 응답                    [서버 모듈]
   ▼
lock: 한 번에 한 요청만 저장소에 진입
   ▼
해시 테이블: 해시 계산 → 칸 찾기 → 리스트에서 키 비교          [저장소 모듈]
   · 충돌은 체이닝으로 처리, 많이 차면 칸 수 확장
   · 항목마다 만료 시점 저장, 조회할 때 확인해 지났으면 삭제
```

데모 API와 성능 비교(활용 모듈)는 이 서버를 사용하는 바깥쪽 프로그램입니다.

## 2. 장면별로 따라가기

칸이 4개인 해시 테이블로 시작합니다.

```
칸:  [0] [1] [2] [3]
```

### 장면 1: 저장

`name`이라는 키에 `현지`를 저장하라는 요청이 들어옵니다.

1. 해시 함수가 키 `"name"`을 숫자로 바꿉니다. 결과가 14라고 가정합니다.
2. 칸 수로 나눈 나머지를 구합니다: 14 % 4 = 2
3. 2번 칸에 키와 값을 함께 저장합니다.

```
칸:  [0] [1] [2: name → 현지] [3]
```

### 장면 2: 조회

`name`의 값을 달라는 요청이 들어옵니다.

1. 같은 해시 함수로 계산합니다. 같은 키이므로 결과는 다시 14입니다.
2. 14 % 4 = 2
3. 2번 칸으로 바로 가서 `현지`를 돌려줍니다.

다른 칸은 확인하지 않습니다. 데이터가 많아져도 찾는 시간이 거의 같은 이유입니다.

### 장면 3: 충돌

`age`에 `25`를 저장하라는 요청이 들어옵니다. 해시값이 22라고 가정하면 22 % 4 = 2로, 이미 `name`이 있는 칸입니다.

- 덮어쓰면 `name`을 조회했을 때 `25`가 나오므로 안 됩니다.
- 같은 칸의 항목들을 리스트로 이어 붙입니다. 이 방식을 **체이닝**이라고 합니다.
- 리스트의 각 항목에는 값뿐 아니라 **키도 함께** 저장합니다. 조회할 때 리스트를 따라가며 키가 일치하는 항목을 찾아야 하기 때문입니다.

```
칸:  [0] [1] [2: (name → 현지) → (age → 25)] [3]
```

### 장면 4: 칸 수 확장

칸은 4개인데 데이터가 계속 들어오면 칸마다 리스트가 길어지고, 결국 하나씩 비교하게 되어 해시 테이블의 장점이 사라집니다.

- "저장된 개수 ÷ 칸 수"가 기준값(예: 0.75)을 넘으면 칸 수를 두 배로 늘립니다.
- 칸 수가 바뀌면 나머지 계산 결과도 바뀌므로, 기존 항목을 모두 새 위치로 다시 배치합니다.
- 이렇게 하면 리스트가 항상 짧게 유지됩니다.

### 장면 5: 만료

인기 상품 목록을 10분 동안만 보관하도록 저장합니다. 10분이 지난 뒤에는 값을 돌려주면 안 됩니다.

저장할 때 키, 값과 함께 **만료 시점**을 저장합니다. 기간이 아니라 시점을 저장하면, 조회할 때 현재 시각과 비교만 하면 됩니다.

만료된 값을 지우는 방법은 두 가지입니다.

| 방법 | 동작 | 장점 | 한계 |
| --- | --- | --- | --- |
| 지연 삭제 | 조회 요청이 올 때 만료 시점을 확인하고, 지났으면 지운 뒤 "없음"으로 응답 | 필요한 순간에만 확인하므로 비용이 거의 없음 | 다시 조회되지 않는 키는 메모리에 계속 남음 |
| 주기적 정리 | 일정 간격으로 만료된 값을 찾아 지움 | 조회되지 않는 키도 정리됨 | 전체를 매번 확인하면 부담이 큼 |

실제 레디스는 두 방법을 함께 씁니다. 지연 삭제를 기본으로 하고, 주기적 정리는 일부 키만 골라 확인하는 방식으로 부담을 줄입니다.

### 장면 6: 외부에서 사용하기

해시 테이블은 프로그램 안의 객체이므로, 다른 프로그램이 쓰려면 미니 레디스가 **서버**로 실행되어 네트워크 요청을 받아야 합니다.

```
다른 프로그램  ──요청──▶  미니 레디스 서버  ──▶  해시 테이블
	        ◀──응답──
```

요청에는 명령의 종류, 키, 값, (저장이라면) 만료 기간이 담기고, 응답에는 결과가 담깁니다.

| 동작 | 요청에 담기는 것 | 응답 |
| --- | --- | --- |
| 저장 | 키, 값, (선택) 만료 기간 | 성공 여부 |
| 조회 | 키 | 값. 없거나 만료되었으면 "없음" |
| 삭제 | 키 | 삭제 여부 |

요청과 응답의 형식은 두 가지 선택지가 있습니다.

| 방식 | 특징 |
| --- | --- |
| HTTP API | 파이썬 도구로 금방 만들 수 있고 테스트와 시연이 쉬움 |
| 자체 텍스트 규약 | 실제 레디스와 비슷하지만 연결 처리와 문자열 해석을 직접 구현해야 함 |

### 장면 7: 무효화

원본 데이터가 바뀌면 캐시에 저장된 값은 낡은 것이 됩니다. 만료 시점까지 기다리지 않고 바로 지우는 것이 무효화입니다.

```
사용자 ──▶ 웹 서비스 서버 ──┬──▶ DB (원본)
                          └──▶ 레디스 (캐시)
```

DB와 레디스는 서로 직접 연결되어 있지 않습니다. 삭제 요청은 DB가 아니라 **DB의 내용을 바꾼 프로그램**이 보냅니다.

1. 웹 서비스 서버가 DB의 데이터를 수정합니다.
2. 같은 서버가 레디스에 해당 키의 삭제를 요청합니다.
3. 다음 조회 때 레디스에 값이 없으므로, DB에서 새로 가져와 다시 저장합니다.

| 낡은 데이터를 없애는 방법 | 누가 | 언제 |
| --- | --- | --- |
| 만료 | 레디스가 스스로 | 정해둔 시점이 지나면 |
| 무효화 | 레디스를 사용하는 프로그램이 삭제 요청 | 원본이 바뀐 직후 |

과제의 데모 API가 위 그림의 웹 서비스 서버 역할을 합니다.

### 장면 8: 동시성

여러 요청이 같은 데이터를 거의 동시에 건드리면 문제가 생깁니다. 동시성 처리는 두 층으로 나뉩니다.

**첫 번째 층: 명령 하나의 안전성 (필수)**

저장, 조회, 삭제 각각이 실행되는 도중에 다른 요청이 끼어들면 해시 테이블 내부가 망가집니다.

- 한 요청이 칸 수를 늘리며 항목을 재배치하는 도중에, 다른 요청이 조회하는 경우
- 같은 칸의 리스트에 두 요청이 동시에 항목을 추가하는 경우
- 한 요청이 만료된 값을 지우는 도중에, 다른 요청이 그 값을 읽는 경우

이를 막는 구조는 두 가지입니다.

| 구조 | 방식 | 특징 |
| --- | --- | --- |
| 여러 스레드 + lock | 여러 요청을 동시에 받되, 저장소를 건드리는 순간에는 한 번에 하나만 진입 | 구현이 단순하고 DBMS Phase 3에서 같은 방식을 다시 사용 |
| 단일 스레드 순차 처리 | 요청을 줄 세워 한 번에 하나씩만 처리 | lock이 필요 없음. 실제 레디스가 쓰는 방식 |

**두 번째 층: 여러 명령에 걸친 안전성 (선택)**

방문자 수(`count → 10`)를 두 사용자가 거의 동시에 "읽고, 1을 더해, 저장"하는 경우입니다.

```
A: count 읽음 (10)
B: count 읽음 (10)
A: 11 저장
B: 11 저장      → 두 명이 방문했는데 결과는 11
```

읽기와 저장이 서로 다른 요청이므로, 각 요청에 lock을 걸어도 이 문제는 남습니다.
해결책은 "읽고, 더하고, 저장"을 하나의 명령(증가 명령)으로 묶어 미니 레디스 안에서 한 번에 처리하는 것입니다.

캐시 용도에서는 이 문제가 거의 생기지 않습니다. 두 요청이 동시에 같은 결과를 계산해 저장하더라도 저장하는 값이 같기 때문입니다. 그래서 증가 명령은 과제의 필수 항목이 아니지만, 분량이 작고 동시성 처리를 테스트와 시연으로 보여주기 좋습니다.

| 과제 항목 | 이 문서의 장면 |
