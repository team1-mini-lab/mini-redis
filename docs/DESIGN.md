# 미니 레디스 설계 문서

상태: 초안 (팀 합의 후 확정)

개념 설명은 [REDIS_OVERVIEW.md](./REDIS_OVERVIEW.md)에 있습니다.

## 1. 요구사항

과제 가이드에서 뽑은 요구사항입니다. 각 요구사항은 3번의 개발 단계와 연결되어 있어, 개발 단계를 모두 마치면 요구사항이 모두 충족됩니다.

| 번호 | 요구사항 | 충족되는 단계 |
| --- | --- | --- |
| R1 | 해시 테이블을 직접 구현한 키-값 저장소 (저장, 조회, 삭제) | 2, 3 |
| R2 | 해시 테이블의 설계 원리, 구현 과정, 주요 함수를 설명할 수 있음 | 7, 11 |
| R3 | 외부에서 사용할 수 있는 API 구조 | 1, 6 |
| R4 | 동시성 문제가 발생하지 않는 구조 | 5, 10 |
| R5 | 만료된 값을 요청받았을 때의 처리 | 4 |
| R6 | 저장된 데이터의 무효화 | 1, 8 |
| R7 | 단위 테스트로 저장, 조회, 삭제 검증 | 2, 3, 4 |
| R8 | 기능 테스트: 간단한 API의 응답 값을 미니 레디스에 저장해 활용 | 8, 10 |
| R9 | 엣지 케이스 고려 | 6, 10 |
| R10 | 미니 레디스를 쓸 때와 쓰지 않을 때의 성능 비교 | 9 |
| R11 | (선택) 서버가 다운되어도 데이터 유지 | 14 |
| R12 | (선택) 다른 팀과의 차별화 요소 | 12, 13 |

하지 않을 것: 실제 레디스의 다른 자료형과 명령어, 실제 레디스 클라이언트와의 호환, 분산과 복제, 사용자 인증.

## 2. 구조

### 전체 흐름

```
데모 API
   │ HTTP 요청                        (접점 2)
   ▼
서버: 요청 해석 → 입력 검증 → 저장소 함수 호출 → 응답
   │ 함수 호출                        (접점 1)
   ▼
저장소: lock → 해시 테이블 (체이닝, 확장, 만료 확인)
```

### 접점 1: 저장소 함수

| 함수 | 받는 것 | 돌려주는 것 |
| --- | --- | --- |
| `set(key, value, ttl=None)` | 키(문자열), 값, 보관 기간(초, 생략하면 만료 없음) | 없음 |
| `get(key)` | 키 | 값. 키가 없거나 만료되었으면 `None` |
| `delete(key)` | 키 | 지웠으면 `True`, 지울 키가 없었으면 `False` |

### 접점 2: API

| 동작 | 요청 | 성공 응답 | 실패 응답 |
| --- | --- | --- | --- |
| 저장 | `POST /set` 본문 `{"key": "name", "value": "현지", "ttl": 600}` (`ttl`은 선택) | 200 `{"ok": true}` | 400 (잘못된 입력) |
| 조회 | `GET /get?key=name` | 200 `{"key": "name", "value": "현지"}` | 404 (없거나 만료됨), 400 |
| 삭제 | `DELETE /delete?key=name` | 200 `{"deleted": true}` 또는 `{"deleted": false}` | 400 |

### 동작 규칙

세 명의 구현이 같은 테스트를 통과할 수 있도록 똑같이 지킵니다.

- 만료된 키는 없는 키와 똑같이 취급합니다. `get`은 `None`을, `delete`는 `False`를 돌려줍니다.
- 이미 있는 키에 `set`을 하면 값을 덮어쓰고 만료 시점도 새로 정합니다. `ttl`을 생략하면 만료가 없어집니다.
- 값으로 `None`은 저장할 수 없습니다. `get`이 돌려주는 `None`은 항상 "없음"을 뜻합니다.
- 키는 비어 있지 않은 문자열이고, 값은 JSON으로 표현할 수 있는 값입니다. `ttl`은 0보다 큰 숫자입니다.
- 위 조건을 어긴 입력은 서버가 걸러서 400으로 응답합니다. 저장소 함수에는 올바른 입력만 전달됩니다.
- 저장소 함수는 여러 스레드에서 동시에 호출해도 안전해야 합니다. lock은 저장소 안에서 처리합니다.

## 3. 개발 순서

API 서버를 먼저 세우고, 안쪽을 한 겹씩 채웁니다. 매 단계의 결과를 API로 확인합니다.

### 목요일: 각자 구현

세 명이 같은 접점과 동작 규칙을 지키며 각자 0~6단계를 진행합니다. 중간에 한 번 진행 상황을 한 줄씩 공유합니다.

| 단계 | 만드는 것 | 이것이 보이면 완료 | 요구사항 |
| --- | --- | --- | --- |
| 0. 준비 | 프로젝트 폴더, 서버 도구 설치, 응답 하나짜리 서버 | 브라우저에서 서버 주소를 열면 응답이 나옴 | |
| 1. 뼈대 | API 3개 + 임시 저장소 (파이썬 `dict`를 감싼 것) | API로 저장한 값이 조회되고, 삭제하면 404가 나옴 | R3, R6 |
| 2. 해시 테이블 | 칸 수가 고정된 해시 테이블과 체이닝. 임시 저장소의 `dict`를 교체 | API 동작이 1단계와 같음. 같은 칸에 여러 키가 이어진 것이 출력으로 확인됨 | R1, R7 |
| 3. 칸 수 확장 | 일정 수준 이상 차면 칸을 늘리고 재배치 | 키 100개를 저장하면 칸 수가 늘어나고, 100개 모두 조회됨 | R1, R7 |
| 4. 만료 | 만료 시점 저장, 조회할 때 확인 (지연 삭제) | 5초짜리로 저장한 값이 바로 조회되고, 5초 뒤에는 404가 나옴 | R5, R7 |
| 5. lock | 저장소 함수를 lock으로 감싸기 | 여러 스레드가 동시에 저장과 조회를 반복해도 오류가 없음 | R4 |
| 6. 입력 검증 | 동작 규칙을 어긴 요청을 서버가 걸러냄 | 빈 키, 잘못된 `ttl` 등에 400 응답 | R3, R9 |

2~4단계는 단계를 마칠 때 그 단계의 단위 테스트를 함께 작성합니다.

### 목요일 저녁: 비교

| 단계 | 하는 것 | 이것이 되면 완료 | 요구사항 |
| --- | --- | --- | --- |
| 7. 비교와 선택 | 각자 10분씩 구현을 설명하고, 서로 다른 선택과 이유를 비교. 기준 구현을 선택 | 기준 구현이 정해지고, 주요 선택이 4번 결정 기록에 적힘 | R2 |

구현을 끝내지 못한 사람이 있어도 비교를 진행합니다. 선택 기준은 공통 테스트 통과, 읽고 설명하기 쉬운 코드, 동작 규칙 준수입니다.

### 금요일: 기준 구현 위에서 분담

담당자는 목요일 저녁에 정합니다. 오후에는 새 기능을 멈추고 통합과 정리를 합니다.

| 단계 | 만드는 것 | 이것이 보이면 완료 | 요구사항 |
| --- | --- | --- | --- |
| 8. 데모 API | 느린 조회 결과를 미니 레디스에 저장해 쓰는 API. 원본 수정 시 캐시 삭제 | 두 번째 조회부터 빨라지고, 원본을 수정하면 새 값이 조회됨 | R6, R8 |
| 9. 성능 비교 | 캐시를 쓸 때와 쓰지 않을 때의 응답 시간 측정 | 비교 결과가 숫자로 정리됨 | R10 |
| 10. 테스트 보완 | API 기능 테스트, 동시 요청 테스트, 엣지 케이스 테스트 | 전체 테스트가 통과함 | R4, R8, R9 |
| 11. 문서 정리 | README (실행 방법, 구조, 해시 테이블 설명), 결정 기록 | 처음 보는 사람이 README만으로 실행하고 구조를 이해할 수 있음 | R2 |

### 시간이 남으면 (우선순위 순)

| 단계 | 만드는 것 | 이것이 보이면 완료 | 요구사항 |
| --- | --- | --- | --- |
| 12. 증가 명령 | 읽기, 더하기, 저장을 하나로 묶은 명령 | 동시에 100번 증가시키면 정확히 100이 됨 | R12 |
| 13. 주기적 정리 | 조회되지 않는 만료 키를 일정 간격으로 삭제 | 만료된 뒤 조회하지 않은 키도 저장소에서 사라짐 | R12 |
| 14. 데이터 유지 | 저장소 내용을 파일에 남기고 시작할 때 복원 | 서버를 껐다 켜도 값이 조회됨 | R11 |

진행 상황은 GitHub 이슈로 관리합니다. 단계 번호는 이슈와 결정 기록에서 참조하므로 바꾸지 않습니다. 단계를 추가할 때는 "3-1"처럼 붙입니다.

## 4. 결정 기록

"제안"은 관례를 따른 초안이고, "미정"은 팀이 선택할 항목입니다. 합의하면 "확정"으로 바꿉니다.
"관련 단계"는 3번의 개발 단계 번호이고, 특정 단계에 속하지 않는 결정은 "전체"로 적습니다.

| 날짜 | 결정 | 이유 | 관련 단계 | 상태 |
| --- | --- | --- | --- | --- |
| 11/11 | 충돌 처리는 체이닝 | 구현과 설명이 단순하고 널리 쓰이는 방식 | 2 | 제안 |
| 11/11 | 항목에 만료 "시점"을 저장 | 조회할 때 현재 시각과 비교만 하면 됨 | 4 | 제안 |
| 11/11 | 만료 확인은 지연 삭제를 기본으로 함 | 과제 요구에 해당하고 비용이 작음 | 4 | 제안 |
| 11/11 | 만료된 키는 없는 키와 같게 응답 | 사용하는 쪽에서 구분할 필요가 없고, 값이 특정 문자열과 겹치는 문제가 없음 | 1, 4 | 제안 |
| 11/11 | 사용 언어는 파이썬 | 팀 전체가 익숙하고 DBMS에서도 같은 언어를 사용 | 전체 | 미정 |
| 11/11 | API 형식은 HTTP | 구현, 테스트, 시연이 쉬움 | 1 | 미정 |
| 11/11 | 동시성 구조는 저장소 전체에 lock 하나 | 단순하고 DBMS Phase 3에서 같은 방식을 다시 사용 | 5 | 미정 |
| 11/12 | 목요일은 각자 구현, 금요일은 기준 구현 위에서 분담 | 전원이 해시 테이블을 직접 구현해 보고, 세 구현의 비교가 학습과 발표 재료가 됨 | 전체 | 미정 |
