# 개발 결정 기록

팀 `docs/DESIGN.md`의 단계 번호를 따릅니다. 단계마다 "고른 것 / 고르지 않은 것 / 이유"를 남겨, 7단계 비교에서 그대로 설명할 수 있게 합니다.

## 0단계. 준비

| 결정 | 고른 것 | 고르지 않은 것 | 이유 |
| --- | --- | --- | --- |
| 서버 도구 | Flask 3.1 | 표준 `http.server`, FastAPI | 코드가 짧아 저장소(해시 테이블) 구현에 집중할 수 있고 자료가 많음. FastAPI의 자동 검증은 6단계 입력 검증을 직접 이해할 기회를 가림 |
| 가상 환경 | `.venv` (venv) | 전역 설치 | 팀원과 버전을 맞추고 내 컴퓨터의 다른 프로젝트와 섞이지 않게 함. 버전은 `requirements.txt`에 고정 |
| 폴더 구조 | `mini_redis/server.py`, `mini_redis/store.py`, `tests/` | 파일 하나 | 서버와 저장소를 나누면 접점 1(저장소 함수)이 파일 경계와 같아짐 |

완료 기준: 브라우저에서 `http://127.0.0.1:8000`을 열면 `{"message": "mini-redis is running"}`이 나온다.

## 1단계. 뼈대

| 결정 | 고른 것 | 고르지 않은 것 | 이유 |
| --- | --- | --- | --- |
| 임시 저장소 | `Store` 클래스가 `dict`를 감쌈 | 서버에서 `dict`를 직접 사용 | 2단계에서 `Store` 내부만 해시 테이블로 바꾸면 서버 코드는 그대로 둘 수 있음 |
| 저장소 모양 | 클래스(`Store`)의 메서드 `set/get/delete` | 모듈 함수 세 개 | 테스트마다 새 저장소를 만들어 서로 영향을 주지 않게 할 수 있음 |
| 테스트 도구 | 표준 `unittest` + Flask `test_client` | `pytest` | 추가 설치가 없고, 서버를 띄우지 않고도 API 요청을 보낼 수 있음 |
| 입력 검증 | 하지 않음 (키나 본문이 없으면 Flask 기본 오류) | 지금 400 처리 | 팀 설계상 6단계에서 한 곳에 모아 처리 |

완료 기준: API로 저장한 값이 조회되고, 삭제하면 404가 나온다. (`tests/test_api.py` 3개 통과)

## 2단계. 해시 테이블

| 결정 | 고른 것 | 고르지 않은 것 | 이유 |
| --- | --- | --- | --- |
| 충돌 처리 | 체이닝 | 개방 주소법(빈 칸을 찾아 옆으로 이동) | 구현과 설명이 단순함. 개방 주소법은 삭제할 때 "지워진 자리" 표시가 따로 필요해 까다로움 |
| 체인 구조 | 직접 만든 노드(`key`, `value`, `next`)의 연결 리스트 | 칸마다 파이썬 `list`에 `(key, value)` 담기 | 칸 배열 외에는 내장 자료구조에 기대지 않아 "직접 구현"이 분명함. 노드를 끊어내는 삭제 과정을 설명할 수 있음 |
| 칸 배열 | 파이썬 `list` (`[None] * 칸 수`, 번호로만 접근) | 직접 만든 배열 | 팀 확정 사항. 해시 계산, 충돌 처리, 확장을 직접 하므로 과제 조건에 맞음 |
| 해시 함수 | FNV-1a 64비트 (키의 UTF-8 바이트에 적용) | 내장 `hash()` | 여섯 줄이라 직접 설명할 수 있고, 실행할 때마다 값이 같음. 내장 `hash()`는 문자열 해시가 실행마다 달라져 디버깅 출력이 매번 바뀜 |
| 새 항목 위치 | 체인 맨 앞 | 맨 뒤 | 끝까지 따라갈 필요 없이 바로 붙일 수 있음 |
| 파일 분리 | `hashtable.py`(자료구조)와 `store.py`(접점 1) | `store.py` 하나 | 해시 테이블은 만료와 lock을 모르게 두고, 4~5단계는 `store.py`에만 더함 |
| 해시 함수 교체 | 생성자에서 `hash_fn`을 받음 | 고정 | 테스트에서 모든 키를 한 칸으로 보내 충돌을 일부러 만들 수 있음 |

완료 기준: API 동작이 1단계와 같다. 같은 칸에 여러 키가 이어진 것이 출력으로 확인된다.

### 검증
- `python -m unittest -v` → 10개 통과 (해시 테이블 7개 + 1단계 API 테스트 3개 그대로)
  - 충돌: 모든 키를 0번 칸으로 보내 100개 저장 후 전부 조회, 체인의 앞, 중간, 끝 삭제
  - FNV-1a 공식 테스트 값 3개와 일치
- `server.py`는 한 줄도 바꾸지 않았다. `store.py` 내부만 `dict`에서 `HashTable`로 교체했다.
- 칸 4개에 키 5개를 넣은 `debug_dump()` 출력:

```text
[0] (job → 학생) → (age → 25)
[1] (lang → python)
[2] (city → 서울) → (name → 현지)
[3] 
```

## 3단계. 칸 수 확장

| 결정 | 고른 것 | 고르지 않은 것 | 이유 |
| --- | --- | --- | --- |
| 확장 기준 | 저장된 개수 ÷ 칸 수가 0.75를 넘을 때 | 1.0, 0.5 | 0.75면 체인의 평균 길이가 1보다 짧아 조회가 빠르고, 빈 칸은 `None` 하나라 메모리 부담이 작음 |
| 비교 연산자 | `>` (넘을 때만) | `>=` | 둘의 차이는 작음. "넘으면 확장"이라는 말과 코드가 그대로 맞음 |
| 늘리는 배수 | 2배 | 1.5배, 고정 개수씩 더하기 | 확장 간격이 점점 넓어져 키 하나당 평균 비용이 일정하게 유지됨. 빈 칸은 많아야 절반 정도 |
| 처음 칸 수 | 8 | 16, 1024 | 작게 시작해야 확장이 일어나는 것을 적은 키로 확인할 수 있음 |
| 재배치 방법 | 기존 노드를 새 칸 배열로 그대로 옮김 | 노드를 새로 만들어 다시 `put` | 새 노드를 만들지 않아도 되고, 재배치 도중 확장 검사가 다시 걸리지 않음 |
| 축소 | 하지 않음 | 키가 줄면 칸 수 줄이기 | 과제 요구사항이 아님 |

완료 기준: 키 100개를 저장하면 칸 수가 늘어나고, 100개 모두 조회된다.

### 검증
- `python -m unittest -v` → 15개 통과 (2단계 10개 + 확장 5개)
  - 키 6개까지는 8칸 유지(6 ÷ 8 = 0.75는 넘지 않음), 7번째에 16칸
  - 같은 키를 100번 덮어써도 확장하지 않음
  - 키 100개 저장 후 전부 조회
  - 키 10만 개 저장, 전부 조회, 절반 삭제
  - 모든 키가 한 칸에 몰린 상태에서 확장해도 전부 조회
- 키 100개를 넣는 동안 확장이 일어난 시점: 7번째(8→16), 13번째(16→32), 25번째(32→64), 49번째(64→128), 97번째(128→256)
- 키 10만 개를 넣은 뒤: 칸 262,144개, 가장 긴 체인의 길이 5

## 0~1단계 검증

### 0단계
- `python -m mini_redis.server` 실행 후 `http://127.0.0.1:8000` 접속 → `{"message": "mini-redis is running"}`

### 1단계: API 요청으로 확인 (curl)

| 확인 | 요청 | 기대 | 결과 |
| --- | --- | --- | --- |
| 저장 | `POST /set` `{"key": "name", "value": "somang"}` | 200 `{"ok": true}` | 통과 |
| 조회 | `GET /get?key=name` | 200 `{"key": "name", "value": "somang"}` | 통과 |
| 삭제 | `DELETE /delete?key=name` | 200 `{"deleted": true}` | 통과 |
| 삭제 후 조회 | `GET /get?key=name` | 404 `{"error": "not found"}` | 통과 |
| 없는 키 삭제 | `DELETE /delete?key=name` | 200 `{"deleted": false}` | 통과 |

### 1단계: 자동 테스트
- `python -m unittest -v` → 3개 통과
  - `test_set_get_delete`: 저장 → 조회 → 삭제 → 404
  - `test_delete_missing_key`: 없는 키 삭제는 200, `deleted: false`
  - `test_set_overwrites`: 같은 키로 다시 저장하면 덮어씀

### 6단계(입력 검증)로 미룬 빈틈

| 입력 | 지금 응답 | 문제 |
| --- | --- | --- |
| `POST /set` 본문에 `key`가 없음 | 500 | 서버 오류로 보임. 잘못된 입력이므로 400이어야 함 |
| `POST /set` `value`가 `null` | 저장 후 조회하면 404 | `get`의 `None`(없음)과 구분되지 않음 |
| `GET /get` 에 `key` 파라미터가 없음 | 400 (HTML 본문) | 다른 응답처럼 JSON이어야 함 |
