## 1. 구조: 만료를 어디서 처리하는가

가장 큰 설계 차이입니다.

| | hnjee, somang | eungi |
| --- | --- | --- |
| 해시 테이블 | 만료를 모름. 키와 값만 넣고, 찾고, 지움 | 노드에 `expire_at`이 있고, 만료 확인과 지연 삭제를 해시 테이블이 직접 함 |
| 저장소 (`Store`) | 값을 `(값, 만료 시점)`으로 묶어 해시 테이블에 넣음. 만료 확인과 lock을 맡음 | lock만 걸고 해시 테이블에 그대로 넘기는 창구 |
| 시계 | `Store(clock=time.monotonic)`. 테스트에서 가짜 시계를 끼울 수 있음 | 해시 테이블 안에서 `time.time()`을 직접 부름. 바꿔 끼울 수 없음 |

### 무엇이 달라지는가

- **테스트 속도**: eungi 방식은 가짜 시계를 쓸 수 없어 만료 테스트가 실제로 기다려야 합니다. DESIGN.md의 4단계 완료 기준인 "5초 뒤 404"를 테스트하면 정말 5초가 걸립니다. hnjee와 somang은 가짜 시계를 5초 앞으로 돌려서 바로 확인합니다.
- **역할 나누기**: hnjee와 somang의 해시 테이블은 "키로 값을 찾는 자료구조" 하나만 합니다. 그래서 2~3단계 해시 테이블 테스트가 만료를 신경 쓰지 않아도 됩니다. eungi는 `Store`가 아주 짧아지는 대신, 해시 테이블이 두 가지 일을 함께 합니다.
- **시계 종류**: `time.time()`은 컴퓨터의 시각이라 시간 동기화(NTP)나 수동 변경으로 앞뒤로 움직일 수 있습니다. 시각이 뒤로 가면 키가 늦게 만료되고, 앞으로 가면 일찍 만료됩니다. `time.monotonic()`은 앞으로만 가므로 이런 일이 없습니다. eungi는 13단계 커밋에서 monotonic으로 바꿨습니다.

### 해시 함수: 내장 `hash()`를 쓰면 생기는 일

파이썬은 보안을 위해 문자열의 `hash()` 값을 **실행할 때마다 다르게** 만듭니다 (`PYTHONHASHSEED`).

```bash
python -c 'print(hash("a") % 8)'   # 실행할 때마다 다른 칸 번호가 나옴
```

- 한 번 실행하는 동안에는 같은 키가 같은 값을 내므로 **저장, 조회, 삭제는 정상 동작**합니다.
- 하지만 2단계 완료 기준인 "같은 칸에 여러 키가 이어진 것이 출력으로 확인됨"을 매번 같은 결과로 보여 줄 수 없습니다. 발표에서 "a와 i가 같은 칸에 들어갑니다"라고 설명하기 어렵습니다.
- 과제의 "해시 테이블을 직접 구현"(R1)에서 해시 함수까지 직접 만들었는지 질문받을 수 있습니다.

eungi는 13단계 커밋에서 다항식 해시로 바꿨습니다.

### 체인: 리스트인가, 연결 리스트인가

| | 파이썬 리스트 (hnjee) | 연결 리스트 (eungi, somang) |
| --- | --- | --- |
| 코드 | 가장 짧음. `for`, `append`, `pop`으로 끝남 | 이전 노드(`prev`)를 기억하며 끊고 잇는 코드가 필요 |
| 설명 | "칸마다 목록이 있다"로 바로 이해됨 | 체이닝이 무엇인지 그림 그대로 보여 줌 |
| "직접 구현" | 파이썬 리스트에 기대는 부분이 있음 | 칸 배열 말고는 모두 직접 만듦 |

둘 다 체인을 앞에서부터 하나씩 확인하므로 찾는 속도는 같습니다.

## 3. 만료와 lock: 결과가 같음

공통 요청에서 세 구현의 결과가 모두 같았습니다.

| 확인한 것 | hnjee | eungi | somang |
| --- | --- | --- | --- |
| `ttl` 0.3초로 저장, 0.4초 뒤 조회 | 200 → 404 | 200 → 404 | 200 → 404 |
| 만료된 키를 삭제 | `{"deleted": false}` | `{"deleted": false}` | `{"deleted": false}` |
| `ttl`로 저장한 뒤 `ttl` 없이 덮어쓰면 | 만료 없어짐 (200) | 만료 없어짐 (200) | 만료 없어짐 (200) |
| 만료 확인 방식 | 지연 삭제 | 지연 삭제 | 지연 삭제 |
| lock | 저장소 전체에 하나 | 저장소 전체에 하나 | 저장소 전체에 하나 |
| 8스레드 × 2,000번 동시 저장 후 유실 | 0건 | 0건 | 0건 |

세 구현 모두 "만료 확인 → 삭제"를 lock 하나 안에서 처리합니다. 그래서 그 사이에 다른 요청의 `set`이 끼어들어 새 값이 지워지는 일이 없습니다.

## 4. 입력 검증: 가장 큰 차이

### 같은 요청에 응답이 달랐던 것

| 요청 | hnjee | eungi | somang |
| --- | --- | --- | --- |
| `ttl`이 1 뒤에 0이 400개인 정수 | 400 | **500 서버 오류** | 400 |
| `ttl: 1e300` (약 10의 292제곱 년) | 400 (상한 10년) | 200 | 400 |
| 오타 `"ttI": 5` | 400 (알 수 없는 항목) | **200, 오타가 무시되어 만료 없이 저장됨** | 400 |
| `Content-Type` 헤더 없이 보낸 JSON | 400 | 200 (`force=True`로 받아 줌) | 400 |
| `value` 항목이 아예 없음 | 400 "key와 value가 필요합니다" | 400 "value is required and cannot be null" (null과 같은 문장) | 400 "key와 value가 필요합니다" |
| 없는 주소 (`GET /nope`) | **404 HTML** | 404 JSON | 404 JSON |
| 메서드가 틀림 (`GET /set`) | **405 HTML** | 405 JSON | 405 JSON |
| 오류 문장 | 한국어 | 영어 | 한국어 |

### 세 구현에서 같았던 것

빈 키, 숫자 키, `value: null`, `ttl`이 `0`, `true`, `"5"`, `Infinity`, 본문이 배열, `/get`에 `key` 없음은 셋 다 400입니다. 없는 키를 삭제하면 셋 다 200 `{"deleted": false}`입니다.

### 무엇이 문제인가

**큰 정수 `ttl`에서 500 (eungi)**

```python
# eungi mini_redis/server.py _is_valid_ttl
return math.isfinite(ttl) and ttl > 0
```

`math.isfinite()`는 정수를 소수로 바꿔 검사하는데, 아주 큰 정수는 소수로 바꿀 수 없어 `OverflowError`가 납니다. 검증 코드가 오히려 서버를 터뜨립니다. hnjee와 somang은 `0 < ttl <= MAX_TTL` 범위 비교만 해서 이 문제가 없습니다. 파이썬은 정수와 소수를 비교할 때 소수로 바꾸지 않습니다.

**오타가 무시됨 (eungi)**

사용자는 `"ttl": 5`로 보낸 줄 알지만 실제로는 `"ttI"`(대문자 I)를 보냈습니다. 서버는 200으로 응답하고, 5초 뒤 사라질 줄 알았던 값은 **영원히 남습니다.** 캐시라면 원본이 바뀌어도 옛 값을 계속 돌려주게 됩니다.

**404, 405가 HTML (hnjee)**

API를 쓰는 쪽은 응답을 JSON으로 읽습니다. 주소를 잘못 쓰면 HTML이 와서 JSON 해석부터 실패하고, 무엇이 잘못됐는지 알기 어렵습니다. Flask의 `@app.errorhandler(404)`, `@app.errorhandler(405)` 두 개로 해결됩니다.

### somang의 검증

somang의 `server.py` 주석에 적혀 있듯이, 검증 함수(`check_key`, `check_ttl`, `check_set_body`)는 hnjee 방식을, 404/405 JSON 응답은 eungi 방식을 가져왔습니다. 그래서 위 표에서 빈틈이 없습니다.

## 질문과 정리

| 질문 | 정리 |
| --- | --- |
| eungi는 왜 브랜치 끝이 아니라 `e2831c0`을 기준으로 하는가 | 브랜치 끝에는 13단계 기능이 들어 있음. 세 사람이 같은 범위(0~6단계)를 만든 상태에서 비교해야 공정함 |

| 내장 `hash()`를 쓰면 안 되는가 | 동작은 정상. 다만 실행마다 칸 배치가 달라 충돌 장면을 재현할 수 없고, "직접 구현" 요구사항에서 질문받을 수 있음 |
| 체인을 리스트로 할지 연결 리스트로 할지 | 찾는 속도는 같음. 리스트는 코드가 짧고, 연결 리스트는 체이닝을 그대로 보여 줌 |
