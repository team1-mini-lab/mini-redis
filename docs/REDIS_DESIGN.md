# 미니 레디스 설계 문서

상태: 초안 (11/12 목요일 오전 합의 후 확정)

개념 설명은 [REDIS_OVERVIEW.md](./REDIS_OVERVIEW.md)에 있습니다. 이 문서는 범위, 모듈 간 접점, 역할, 결정만 다룹니다.
각 모듈의 내부 구현 방법은 담당자가 구현하면서 정하고, 정한 내용을 4번 결정 기록에 남깁니다.

## 1. 범위

### 할 것 (과제 요구사항)

- [ ] 해시 테이블 직접 구현 (파이썬 `dict`를 저장소로 쓰지 않음)
  - [ ] 저장, 조회, 삭제
  - [ ] 충돌 처리 (체이닝)
  - [ ] 칸 수 확장과 재배치
- [ ] 만료: 저장할 때 보관 기간을 지정하고, 만료된 값은 조회되지 않음 (지연 삭제)
- [ ] 동시성: 저장소 lock으로 저장, 조회, 삭제를 안전하게 처리
- [ ] 외부에서 호출하는 API 서버 (저장, 조회, 삭제)
- [ ] 무효화: 삭제 API로 저장된 값을 지움
- [ ] 데모 API: 느린 조회 결과를 미니 레디스에 저장해 활용하고, 원본 수정 시 무효화
- [ ] 성능 비교: 미니 레디스를 쓸 때와 쓰지 않을 때의 응답 시간
- [ ] 단위 테스트: 저장, 조회, 삭제, 충돌, 확장, 만료
- [ ] 기능 테스트: API를 통한 저장, 조회, 삭제, 만료, 동시 요청
- [ ] 엣지 케이스 (2번의 동작 규칙 참고)

### 시간이 남으면 할 것 (우선순위 순)

- [ ] 증가 명령과 동시 요청 테스트 (동시에 100번 증가시키면 정확히 100이 되는지)
- [ ] 주기적 정리: 조회되지 않는 만료 키를 일정 간격으로 삭제
- [ ] 서버가 꺼져도 데이터 유지 (과제의 선택 항목)

### 하지 않을 것

- 실제 레디스의 다른 자료형(리스트, 집합 등)과 그 외 명령어: 과제 요구는 키-값 저장소입니다.
- 실제 레디스 클라이언트와의 호환: 자체 API로 충분합니다.
- 여러 서버로의 분산, 복제: 범위를 크게 벗어납니다.
- 사용자 인증: 과제 요구사항이 아닙니다.

## 2. 구조와 접점

### 전체 흐름

```
데모 API (활용 모듈)
   │ HTTP 요청
   ▼
서버 모듈: 요청 해석 → 저장소 함수 호출 → 응답
   │ 함수 호출
   ▼
저장소 모듈: lock → 해시 테이블 (체이닝, 확장, 만료 확인)
```

### 모듈

| 모듈 | 책임 | 담당 |
| --- | --- | --- |
| 저장소 | 해시 테이블, 충돌 처리, 칸 수 확장, 만료 시점 저장과 확인, lock | 미정 |
| 서버 | API 요청 해석, 입력 검증, 저장소 호출, 응답 형식 | 미정 |
| 활용 | 데모 API, 무효화 흐름, 성능 비교, 기능 테스트 | 미정 |

### 접점 1: 저장소 함수 (저장소 모듈이 제공, 서버 모듈이 사용)

| 함수 | 받는 것 | 돌려주는 것 |
| --- | --- | --- |
| `set(key, value, ttl=None)` | 키(문자열), 값, 보관 기간(초, 생략하면 만료 없음) | 없음 |
| `get(key)` | 키 | 값. 키가 없거나 만료되었으면 `None` |
| `delete(key)` | 키 | 지웠으면 `True`, 지울 키가 없었으면 `False` |

시간이 남으면 추가: `incr(key, amount=1)` → 증가된 뒤의 값

동작 규칙 (두 모듈이 같은 기준으로 구현하고 테스트합니다)

- 만료된 키는 "없는 키"와 똑같이 취급합니다. `get`은 `None`을, `delete`는 `False`를 돌려줍니다.
- 이미 있는 키에 `set`을 하면 값을 덮어쓰고, 만료 시점도 새로 정합니다. `ttl`을 생략하면 만료가 없어집니다.
- 값으로 `None`은 저장할 수 없습니다. `get`이 돌려주는 `None`은 항상 "없음"을 뜻합니다.
- 키는 비어 있지 않은 문자열입니다. 값은 JSON으로 표현할 수 있는 값(문자열, 숫자, 리스트, 딕셔너리)입니다.
- `ttl`은 0보다 큰 숫자입니다.
- 위 조건을 어긴 입력은 서버 모듈이 걸러서 오류로 응답합니다. 저장소 함수에는 올바른 입력만 전달됩니다.
- 저장소 함수는 여러 스레드에서 동시에 호출해도 안전해야 합니다. lock은 저장소 모듈 안에서 처리하고, 서버 모듈은 신경 쓰지 않습니다.

### 접점 2: API 형식 (서버 모듈이 제공, 활용 모듈이 사용)

HTTP API를 쓰는 안입니다. 형식은 목요일 오전에 확정합니다.

| 동작 | 요청 | 성공 응답 | 실패 응답 |
| --- | --- | --- | --- |
| 저장 | `POST /set` 본문 `{"key": "name", "value": "현지", "ttl": 600}` (`ttl`은 선택) | 200 `{"ok": true}` | 400 (잘못된 입력) |
| 조회 | `GET /get?key=name` | 200 `{"key": "name", "value": "현지"}` | 404 (없거나 만료됨), 400 |
| 삭제 | `DELETE /delete?key=name` | 200 `{"deleted": true}` 또는 `{"deleted": false}` | 400 |

## 3. 역할과 일정

| 날짜 | 목표 | 하루가 끝났을 때의 상태 |
| --- | --- | --- |
| 11/12 (목) 오전 | 전체 그림 공유, 범위와 접점 확정, 담당자 결정, 이슈 등록 | 이 문서가 확정됨 |
| 11/12 (목) 오후 | 뼈대 위에서 각자 구현 시작 | 저장과 조회가 API로 동작. 저녁에 통합 확인 |
| 11/13 (금) 오전 | 만료, lock, 무효화 흐름 마무리 | "할 것"의 기능이 모두 동작 |
| 11/13 (금) 오후 | 새 기능 중단. 데모 API, 성능 비교, 테스트, 문서 정리 | 과제 요구사항 충족 |

뼈대: 접점 1의 함수 세 개를 가장 단순하게 구현한 저장소와, 그것을 호출하는 접점 2의 API. 뼈대가 동작하면 각 담당자가 자기 모듈의 내부를 채웁니다.

## 4. 결정 기록

상태가 "제안"인 항목은 관례를 따른 초안이고, "미정"인 항목은 팀이 선택합니다. 목요일 오전에 모두 "확정"으로 바꿉니다.

| 날짜 | 결정 | 이유 | 상태 |
| --- | --- | --- | --- |
| 11/11 | 충돌 처리는 체이닝 | 구현과 설명이 단순하고 널리 쓰이는 방식 | 제안 |
| 11/11 | 항목에 만료 "시점"을 저장 | 조회할 때 현재 시각과 비교만 하면 됨 | 제안 |
| 11/11 | 만료 확인은 지연 삭제를 기본으로 함 | 과제 요구("만료된 값을 요청받았을 때")에 해당하고 비용이 작음 | 제안 |
| 11/11 | 만료된 키는 없는 키와 같게 응답 | 사용하는 쪽에서 구분할 필요가 없고, 값이 특정 문자열과 겹치는 문제가 없음 | 제안 |
| 11/11 | 사용 언어는 파이썬 | 팀 전체가 익숙하고 DBMS에서도 같은 언어를 사용 | 미정 |
| 11/11 | API 형식은 HTTP | 구현, 테스트, 시연이 쉬움 | 미정 |
| 11/11 | 동시성 구조는 저장소 전체에 lock 하나 | 단순하고 DBMS Phase 3에서 같은 방식을 다시 사용 | 미정 |
| 11/11 | 주기적 정리와 증가 명령은 "시간이 남으면" | 필수 요구사항을 먼저 완성 | 미정 |
