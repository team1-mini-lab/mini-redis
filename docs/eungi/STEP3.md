## 구현: `mini_redis/store.py`

`set` 끝에 검사 두 줄, 그리고 `_resize` 메서드 하나를 추가함.

```python
def set(self, key, value, ttl=None):
    ...                                        # 2단계 그대로
    self.buckets[index] = Node(key, value, head)
    self.size += 1
    if self.size / self.capacity > 0.75:       # 부하율 검사
        self._resize()

def _resize(self):
    old_buckets = self.buckets                 # 1. 옛 칸 보관
    self.capacity = self.capacity * 2          # 2. 칸 수 2배
    self.buckets = [None] * self.capacity      #    빈 새 칸

    for old_head in old_buckets:               # 3. 옛 칸의 노드를 하나씩 옮김
        current = old_head
        while current is not None:
            next_node = current.next                       # 옛 체인의 다음을 메모
            index = self._get_bucket_index(current.key)    # 새 칸 번호 (어디로)
            new_head = self.buckets[index]                 # 새 칸의 맨 앞 (누구 앞에)
            current.next = new_head                        # ① 내가 맨 앞을 붙잡고
            self.buckets[index] = current                  # ② 칸이 나를 가리킴
            current = next_node                            # 메모해 둔 다음으로
```

옮기는 과정 (옛 1번 칸의 a, e, i → 새 5, 1, 5번 칸):

```
옛[1] → (a) → (e) → (i)

a 옮김:  새[5] → (a)
e 옮김:  새[1] → (e)
i 옮김:  새[5] → (i) → (a)      ← i가 a를 먼저 붙잡고, 칸이 i를 가리킴
```

## 짜면서 막혔던 것

### 빈칸 채우기

- `self.capacity = capacity * 2` → `_resize`는 인자로 `capacity`를 안 받음 → `self.capacity * 2`
- `index = self.buckets[index]` → `self.buckets[index]`는 칸 안의 **노드**지 칸 **번호**가 아님. 그리고 오른쪽 `index`는 아직 없음 → `self._get_bucket_index(current.key)`
- `current.next = head`, `self.buckets[index] = head` → `head`는 **옛 칸**의 첫 노드. 붙여야 하는 건 **새 칸**의 맨 앞 → `current.next = self.buckets[index]`, `self.buckets[index] = current`
- `current = current.next` → 바로 위에서 `current.next`를 새 칸 쪽으로 바꿨으니 옛 체인을 잃어버림 → 미리 메모해 둔 `next_node`로 이동

### head가 두 개라 헷갈림

- 새 칸의 맨 앞도 head인데, 코드에는 옛 칸의 head(`for head in ...`)만 이름이 있었음
- → `old_head`, `new_head`로 이름을 나눠서 어느 칸의 head인지 드러나게 함

### `current.next = self.buckets[index]`는 뭘 구하는 건가?

- 구하는 게 아니라 **연결**하는 것. `=`는 오른쪽을 왼쪽에 넣음
- `self.buckets[index]`가 오른쪽이면 "칸에 지금 뭐가 있지?"(읽기), 왼쪽이면 "칸에 이걸 넣어"(쓰기)
- `index`와 `new_head`는 줄 서기로 생각하면 됨 → "몇 번 줄?"(`index`) + "그 줄 맨 앞이 누구?"(`new_head`)

### ①, ② 순서

- ②를 먼저 하면 칸이 `current`로 바뀌어서 원래 맨 앞 노드를 가리키는 게 없어짐 → 그 노드를 잃어버림
- 2단계 `set`의 `Node(key, value, head)`와 같은 원리: 새 노드가 기존 head를 잡고 → 칸이 새 노드를 가리킴

## 내가 이해한 것

- **부하율**(적재율, load factor) = `size / capacity`. 칸당 평균 몇 개인지. 0.75가 모든 칸에 0.75개씩이라는 뜻은 아님
- **재해싱이 필요한 이유**: 칸 번호가 `hash(key) % capacity`라서 칸 수가 바뀌면 번호도 바뀜. 통째로 복사하면 `get`이 엉뚱한 칸을 봐서 못 찾음
- **`capacity`를 먼저 바꾸는 이유**: `_get_bucket_index`가 `self.capacity`를 쓰니까 새 칸 번호를 계산하기 전에 바뀌어 있어야 함
- **`set`을 다시 부르지 않는 이유**: `size`가 두 번 세지고, `set` 안에서 또 `_resize`가 불릴 수 있음. 노드도 새로 만들 필요 없이 있던 걸 옮기면 됨 (`size`도 그대로)
- **2배로 늘리는 이유**: 1칸씩 늘리면 거의 매번 재해싱. 2배씩이면 가끔만 해서 평균 비용이 거의 일정함
- **검사 위치**: 항목 수가 늘어나는 곳은 `set`의 새 키 추가뿐. 덮어쓰기는 개수가 그대로라 검사 안 함
- 키 100개면 4 → 8 → 16 → 32 → 64 → 128 → 256 (97번째 키에서 97 / 128 ≈ 0.76이 돼서 한 번 더 늘어남)

## 회의 때 공유한 내용

- 체이닝: 서로 다른 키가 같은 칸 번호를 받는 충돌을 해결하는 대표 방법. 칸마다 데이터 하나가 아니라 연결 리스트, 동적 배열, 트리 같은 자료구조를 둠
  - 우리는 **연결 리스트**. `Node.next`로 잇는 게 Pintos의 `list_elem`으로 잇는 것과 같은 발상
- 칸에는 (키, 값, 만료 시점)을 함께 저장해야 함 → 지금 `Node`는 `key`, `value`, `next`. 만료 시점은 4단계에서 `Node`에 추가할 예정
- 체인이 길어지면 칸 수를 확장해야 함 → 언제 늘릴지는 부하율로 계산
- 칸 수를 너무 크게 늘리면 오히려 비효율 → 빈 칸이 많아져 메모리 낭비, 재해싱도 비쌈 → 그래서 2배씩

## 더 공부한 것 (Q&A)

### 왜 부하율(키 수 ÷ 칸 수)을 기준으로 하나?

- `get`이 느려지는 원인은 체인 길이. 부하율이 곧 칸당 평균 체인 길이라서 "지금 느려지는 중"을 그대로 보여 줌
- 키 개수로 정하면 칸 수에 따라 의미가 달라짐 (칸 4개에 키 100개는 붐빔, 칸 1000개에 키 100개는 텅 빔). 비율이라 칸 수와 상관없이 같은 기준
- `size`, `capacity`는 이미 있는 값이라 나눗셈 한 번이면 됨 → 2단계에서 `size`를 세어 둔 게 여기서 쓰임
- 주의: 평균일 뿐. 해시 함수가 나빠 한 칸에 몰리면 부하율이 낮아도 그 칸은 느림

### 왜 "특정 칸의 체인 길이 ≥ n"을 기준으로 하지 않나?

- 비용 문제는 아님. `set`이 어차피 그 체인을 따라가니까 길이는 거의 공짜로 셀 수 있음
- **칸을 늘려도 안 짧아질 수 있음**: 해시값이 똑같은 키들은 칸 수를 몇 배로 늘려도 계속 같은 칸에 모임 (`12 % 4 = 0`, `12 % 8 = 4`, `12 % 16 = 12`) → 길이 기준이면 칸을 끝없이 늘림. 일부러 이런 키를 보내는 공격(해시 플러딩)도 있음
- **운 나쁜 칸 하나 때문에 전체를 옮기게 됨**: 해시가 좋아도 우연히 몇 개가 몰릴 수 있음. 재해싱은 전체 노드를 옮기는 비싼 작업
- 부하율만 지키면 해시가 고를 때 긴 체인은 드묾
- 실제로 체인 길이를 쓰는 경우: Java 8 이후 HashMap은 한 칸의 체인이 8개 이상이면 **그 칸만** 트리(레드-블랙 트리)로 바꿈 (전체 칸 64개 이상일 때)

| 문제 | 해결 | 기준 |
| --- | --- | --- |
| 전체가 붐빔 | 칸 수 확장 (재해싱) | 부하율 > 0.75 |
| 특정 칸만 길어짐 | 그 칸만 트리로 변환 | 체인 길이 ≥ 8 |

- 좋은 해시 함수가 1차 방어(긴 체인이 드물어짐), 트리 변환은 그래도 생기는 최악의 경우를 위한 안전장치. 우리는 트리 변환은 구현하지 않음
- 좋은 해시도 ① 해시 충돌을 완전히 없앨 수는 없음. 예: `h * 31 + ord(ch)` 방식이면 `"Aa"`와 `"BB"`가 둘 다 2112 (Java `String.hashCode`도 같은 방식이라 실제로 충돌함)

### 충돌은 두 가지 (둘 다 "다른 키"일 때)

같은 키는 항상 같은 해시값이라 "해시값이 다른데 키가 같은" 경우는 없음. 같은 키를 다시 넣는 건 충돌이 아니라 덮어쓰기.

| | 해시값 | 칸 번호 | 예 | 칸 수를 늘리면 |
| --- | --- | --- | --- | --- |
| ① 해시 충돌 | **같음** | 같음 | `"x"`, `"y"` 둘 다 12 | 안 풀림 (`12 % 4`, `12 % 8`, `12 % 16` 모두 같은 칸) |
| ② 칸 충돌 | **다름** | 같음 | `"a"`=13, `"e"`=21 → `% 4`가 둘 다 1 | 풀릴 수 있음 (`% 8`이면 5, 5 / `% 16`이면 13, 5) |

- 대부분의 충돌은 ②. 칸 수가 해시값 범위보다 훨씬 작아서 생김 → 칸 수 확장으로 체인이 짧아지는 이유
- ①은 해시 함수가 나쁘거나 일부러 같은 해시값을 만든 경우 → 확장으로는 해결 안 됨. 그래서 체인 길이를 확장 기준으로 쓰면 칸을 끝없이 늘리게 됨
- 체이닝은 두 경우 모두 같은 칸에 이어 붙이고 **원래 키로 비교**해서 구분함 (노드에 해시값이 아니라 키를 저장하는 이유)

### 0.75, 2배, 4칸은 어떻게 정했나?

- **0.75**: Java HashMap의 기본값을 따름 (Java는 시작 칸 16개). 낮으면 메모리 낭비·잦은 재해싱, 높으면 체인이 길어져 느림. 파이썬 dict는 약 0.66
- **2배**: 1칸씩이면 거의 매번 재해싱. 2배씩이면 가끔만 해서 평균 비용이 거의 일정. 키 100개면 6번만 늘어남
- **4칸**: 깊은 이유는 없고 2단계 예제(`range(4)`)부터 쓰던 값. 키 몇 개만 넣어도 확장이 일어나서 동작 확인하기 좋음 (참고: Java 16, 파이썬 dict 8, STEP2 처음 계획 8)
- 셋 다 7단계에서 다른 값과 비교해 볼 거리

## 남은 것 / 미결정

- **해시 함수 직접 만들기**: 지금은 내장 `hash()`. 직접 만들면 실행할 때마다 값이 같아서 디버깅이 쉽고, 해시 플러딩 같은 상황도 실험해 볼 수 있음
- 지우다 보면 부하율이 아주 낮아질 수 있음. 줄이는 건 이번에 안 함 (선택)
- 확장할 때 이미 만료된 항목을 옮길지 버릴지 → 4단계 만료를 만든 뒤에 정함
