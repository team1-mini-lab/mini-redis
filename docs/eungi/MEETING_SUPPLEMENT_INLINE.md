## 1. 코치 피드백 복기: Redis는 어떤 문제를 풀려고 나왔나

### 1-1. 김은기 발표: 로컬 캐시가 망가지는 다섯 장면

로컬 캐시(서버 자기 메모리에 저장)는 네트워크도 안 타고 빠르다. 서버가 한 대라면 여기서 끝. 하지만 사용자가 늘어 서버가 여러 대가 되고 로드 밸런서가 트래픽을 나눠 주면, 서버마다 별도의 메모리를 갖게 된다.

| # | 겪는 사람 | 장면 | 원인 |
|---|---|---|---|
| 1 | 사용자 | 가격이 왔다 갔다 — 관리자가 5만 원 → 4만 원으로 바꾸면 요청받은 서버 A만 고쳐짐. B·C는 다른 프로세스의 메모리라 고칠 방법이 없어 여전히 5만 원 | 원본이 바뀐 것이 다른 서버에 반영되지 않음 |
| 2 | 사용자 | 로그인이 풀림 — 서버 A 메모리에 세션을 만들었는데, 마이페이지 요청이 서버 B로 가면 B에는 세션이 없음 | 세션이 한 서버 메모리에만 있음 |
| 3 | 운영자 | 배포하면 DB가 몰림 — 배포 때 서버가 모두 재시작되며 캐시가 전부 사라지고, 모든 요청이 DB로 감 | 캐시가 서버와 함께 사라짐 |
| 4 | 운영자 | 같은 데이터를 서버 수만큼 저장 — 인기 상품 1,000개를 A·B·C에 모두 올려야 함. 서버를 늘리면 사본도 늘어 비용 증가 | 공유 저장소가 없음 |
| 5 | 사용자 | 함께 세야 하는 값이 틀림 — 운동화 재고 1개를 서버 A와 B에서 동시에 주문해 두 번 팔림 | 각자 자기 값만 보고 다른 서버가 쓴 것을 모름 |

> **김은기 보충**
>
> 위 표의 "겪는 사람"과 "원인"을 다음과 같이 정정합니다.
>
> | # | 회의록 | 정정 |
> |---|---|---|
> | 3 | 운영자 | 운영자 **+ DB**, 심하면 사용자도 (DB가 느려지면 화면도 느려짐) |
> | 4 | 운영자 / 공유 저장소가 없음 | **회사** / **어긋나지 않아도, 같은 사본을 서버마다 따로 들고 있음** |
> | 5 | 사용자 | **개발자 → 회사·고객** (애초에 기능을 못 만드는 문제. 억지로 만들면 초과 판매) |
>
> 4번의 원인으로 적은 "공유 저장소가 없음"은 다섯 장면 **전체**의 원인이라 4번만의 원인으로 적기엔 부정확합니다. 4번의 고유한 원인은 "같은 사본을 서버마다 따로 들고 있음"입니다.
>
> 다섯 장면을 하나의 표로 정리하면:
>
> | 장면 | 실제로 일어난 일 |
> |---|---|
> | ① 가격이 바뀜 | 서버마다 따로 든 `cache` 사본이 **서로 어긋남** |
> | ② 로그아웃 | `sessions`가 로그인을 받은 서버에만 있음 |
> | ③ 배포 때 DB 폭주 | 서버가 재시작되면서 들고 있던 상태가 같이 사라짐 |
> | ④ 중복 | **어긋나지 않아도**, 같은 사본을 서버마다 따로 들고 있음 |
> | ⑤ 재고, 쿠폰 | 모두가 함께 봐야 할 상태를 **둘 곳이 없음** |
>
> 특히 ④번은 ①②를 해결하려다 나온 문제가 아닙니다. ①②는 값이 **서로 달라서** 생기는 문제이고, ④는 값이 **같아도** 생기는 별개의 낭비 문제입니다. 다섯 장면 모두 서버를 세 대로 늘린 구조 그대로, 아무것도 고치지 않은 상태에서 벌어집니다.
>
> 성격을 나누면 **①②는 고객이 바로 보는 문제, ③④는 고객 눈엔 안 보이는 운영·비용 문제, ⑤는 기능 자체를 못 만드는 문제**입니다.
>
> 1번 vs 5번 차이도 보충하면: 1번은 관리자가 바꾼 **원본이 다른 서버에 전파 안 되는** 문제고, 5번은 여러 서버가 같은 값을 **동시에 읽고 각자 판단해서** 생기는 문제입니다. 뮤텍스 없이 공유 변수를 여럿이 동시에 읽고 쓰면 값이 깨지는 것과 같은 원리입니다.

이현지 보충  
3번: DB는 캐시가 있다는 가정으로 규모를 잡았을 텐데, 캐시가 다 지워지면 DB가 다운될 수도 있음. 그렇다고 DB를 크게 지으면 비용이 너무 큼.  
4번: 1·2번 문제를 막으려고 "모든 서버에 다 저장하자"고 하면 생기는 문제.  
1번 vs 5번: 1번은 관리자가 바꾼 원본이 반영 안 되는 문제, 5번은 한 서버가 쓴 것을 다른 서버가 모르는 문제(락 없이 값을 바꾸는 동기화 문제와 비슷).

### 1-2. 원인과 해결: 상태를 서버 밖으로

공통 원인: 상태(state)가 각 서버의 메모리에 묶여 있다.  
상태 = 같은 요청에도 답을 다르게 만드는, 서버가 기억하고 있는 바뀔 수 있는 데이터.  
stateful = 서버가 자기만 아는 상태를 들고 있음. stateless = 서버가 상태를 들고 있지 않음 (서버를 "기억 상실"로 만듦).  
Redis 이전의 시도: 캐시 유지 시간을 짧게, 오래된 키를 지워 메모리 절약, 같은 사용자는 같은 서버로만 보내기 (→ 그 서버가 죽으면 세션이 사라지고 부하가 한쪽으로 몰림).  
증상을 막아서는 근본 해결이 안 됨 → 상태를 서버에서 떼어내 한 곳(공유 저장소)으로 빼자. DB는 너무 느리므로 DB 앞에 메모리 기반의 별도 서버 → Redis.  
Redis 직전에는 Memcached가 있었음. 공유는 되지만 값을 문자열로만 저장하고, 재시작하면 사라지고, 값을 고치려면 꺼내서 고치고 정렬하고 다시 넣어야 했음. Redis는 공유 + 자료구조 + 운영 기능까지 제공 (김은기가 직접 설치해 보니 명령어 하나로 정렬까지 처리됨).  
김은기의 비유 "React가 상태와 화면을 분리했듯이"에 대해 이현지: React는 상태를 바꾸면 화면이 알아서 반영되게 둘을 하나로 묶는 쪽에 가까움. 개발자 입장에서 상태만 신경 쓰게 해 준다는 의미로 정리.

> **김은기 보충**
>
> stateless를 "기억 상실"로 표현했는데, 정확하게는 **기억을 서버 밖에 맡긴 것**입니다. 기억 자체가 없어지는 게 아니라, 기억을 레디스(공용 저장소)가 대신 들고 있고 앱 서버는 필요할 때 거기서 꺼내 씁니다. 창구 직원이 수첩을 버린 게 아니라, 모든 직원이 같은 중앙 서랍에 기록을 보관하는 것입니다.
>
> React 비유도 끝까지 말하면: React가 **상태와 화면을 분리**했듯이, Redis는 **상태와 서버를 분리**합니다.
>
> | | React | Redis |
> |---|---|---|
> | 고통 | DOM을 직접 고치니 화면과 데이터가 어긋남 | 서버 메모리에 캐시·세션을 두니 서버끼리 어긋남 |
> | 뿌리 | 상태가 화면 곳곳에 흩어져 있음 | 상태가 각 서버에 묶여 있음 |
> | 해결 | 상태를 한 곳에 두고 `UI = f(state)` | 상태를 서버 밖 한 곳에 두고 서버는 읽고 쓰기만 |
> | 결과 | **상태 ↔ 화면** 분리 | **상태 ↔ 서버** 분리 |
>
> "명령어 하나로 정렬까지 처리됨"이라고 말한 부분은 **Sorted Set**의 `ZINCRBY` / `ZRANGE`입니다. (기록 메모의 `ZADD`/`ZRANGE` 계열 추측이 맞습니다.)
>
> ```
> ZINCRBY best 1 키보드     # 키보드 점수 +1 — 순위는 Redis가 알아서 유지
> ZRANGE best 0 9 REV      # 상위 10개 꺼내기
> ```
>
> Memcached였다면 랭킹 전체를 `GET`으로 꺼내 앱에서 수정·정렬하고 `SET`으로 통째로 저장해야 했습니다. 데이터가 크면 매번 전부 주고받는 비용이 들고, `GET`과 `SET` 사이에 다른 서버가 끼어들면 그 사이의 변경이 사라집니다. Redis는 `ZINCRBY` 한 명령으로 끝나니 주고받는 데이터도 작고, 끼어들 틈도 없습니다. **공유를 얻는 대신 자료구조를 잃었던 것을 되찾은 것**이 Redis의 핵심입니다.

### 1-3. Redis를 "쓴다"는 것은 무엇인가

이현지의 질문: DBMS를 쓴다는 건 알겠는데, Redis를 쓴다는 건 뭘까?  
정리: 어떤 데이터를 캐시에 넣을지 개발자가 결정하고, 애플리케이션 코드에서 Redis에 get / set을 직접 호출하는 것. (인기 상품을 자동으로 캐싱해 주지 않음)  
김소망: 개발자가 체감하는 장점은 서버 대수를 신경 쓰지 않아도 된다는 것. 웹 서버를 3대에서 10대로 늘려도 모두 같은 Redis를 보므로 캐시 코드가 그대로, 가격을 바꾸면 모든 서버에 반영.  
김은기: 궁극적인 의미는 서버들이 하나의 저장소를 바라보게 만드는 것.

> **김은기 보충**
>
> "개발자가 직접 `get` / `set`을 호출한다"는 정리는 맞습니다. Redis는 자동 캐싱 레이어가 아니라 저장소라서, 무엇을 캐시할지·언제 지울지 전부 앱 코드가 결정합니다(Cache-Aside).
>
> 다만 "Redis가 자동으로 해 주는 것은 없다"로 읽히면 과한 표현입니다. **TTL 만료는 Redis가 알아서 합니다.** 앱은 저장할 때 `ex=60`처럼 기간만 정하고, 그 뒤 지우는 일은 Redis 몫입니다. 2-4의 구분과 같은 얘기입니다.
>
> | | 누가 하나 |
> |---|---|
> | 무효화 (어떤 키를 언제 지울지) | **앱** 책임 |
> | 만료 (TTL 지난 키 삭제) | **Redis** 책임 |
>
> Redis라는 이름 자체가 "서버들이 하나의 저장소를 바라보게 만드는 것"을 설명합니다. **Redis = Remote Dictionary Server**
>
> - **Remote (원격)**: 앱 서버 안이 아니라 **밖에 따로 있어서** 네트워크로 접근합니다. "상태를 서버 밖으로 뺀다"는 해결책 그 자체가 이름에 담겨 있습니다.
> - **Dictionary (사전)**: 키로 값을 찾는 구조입니다. 파이썬의 `dict`이자 우리가 만드는 해시 테이블입니다.
> - **Server (서버)**: 라이브러리가 아니라 따로 돌아가는 프로그램입니다. **그래서 앱을 배포·재시작해도 같이 꺼지지 않습니다.** ③번(배포 때 DB 폭주)이 해결되는 직접적인 이유입니다.
>
> 코드로 보면, 서버 메모리의 딕셔너리를 읽고 쓰던 부분을 Redis 명령으로 바꾸는 것뿐입니다.
>
> ```python
> # 로컬 캐시 (기존)
> cache["keyboard"] = 40000
>
> # Redis (변경 후) — A, B, C 모두 같은 Redis에 접속
> r = redis.Redis(host="레디스서버주소", port=6379)
> r.set("product:keyboard", 40000, ex=60)   # 60초 TTL
> ```
>
> 앱 코드가 가리키는 주소만 바뀌는 겁니다. A, B, C 모두 같은 Redis 주소를 가리키니 자연스럽게 공유됩니다.
>
> 그리고 "가격을 바꾸면 모든 서버에 반영된다"는 표현을 보충하면, Redis가 모든 서버에 새 값을 **밀어넣는** 게 아닙니다. 쓸 때 Redis 키를 **지우면**, 다음 조회 때 각 서버가 알아서 DB에서 새 값을 가져오는 방식입니다(Cache-Aside). 이를 **무효화(invalidation)**라고 합니다.
>
> ```python
> def update_price(pid, price):
>     db.update(pid, price)       # 원본 수정
>     r.delete(f"product:{pid}") # 키 하나만 지우면 A, B, C 모두 해결
> ```

### 1-4. stateless와 HTTP, 세션과 토큰 (이현지)

HTTP도 stateless가 핵심 특성. 요청·응답마다 이전 약속을 가정하지 않고, 메시지에 담긴 것만으로 통신함.  
세션은 서버가 들고 있는 값이라 서버가 여러 대면 불안정 → 이 문제를 풀려는 맥락에서 JWT 토큰이 나옴. 세션 하나 때문에 Redis를 들이기는 과하니 토큰으로 풀기도 하고, Redis를 쓴다면 세션도 Redis로 해결.

### 1-5. 우리 흐름에서 어디를 건너뛰었나 (이현지 정리)

| 단계 | 문제 | 해결 시도 | 우리가 다룬 것 |
|---|---|---|---|
| 1 | 캐시 없이 매번 DB 조회 → 같은 계산 반복, 느리고 DB 부하 (인기 상품 API 3초) | 한 번 계산한 결과를 저장 | ✅ 출발점 |
| 2 | 웹 서버 프로그램 안 변수에 저장 → 한 대일 땐 행복. 사용자가 늘어 서버가 여러 대가 되면 위의 다섯 장면 | 상태를 별도 서버로 분리 | ❌ 건너뜀 (코치님 지적) |
| 3 | 별도 서버 메모리에 계속 저장 → 안 쓰는 값이 쌓여 메모리가 참, 원본이 바뀌어도 낡은 값이 남음 | 만료 · 무효화 | ✅ 4단계 |
| 4 | 여러 서버가 동시에 요청 → 처리 도중 다른 요청이 끼어듦 | 단일 스레드 등 | ✅ 동시성 단계 |
| 5 | 메모리에만 있어 재시작하면 휘발 → 다시 DB로 몰림 | 끄기 전 파일에 기록하고 복원 | ✅ 영속성 |

우리는 1에서 3으로 바로 갔다. 요구사항의 **"외부에서 사용할 수 있어야 한다"**를 "API가 외부에 있으면 되겠지"로 당연하게 넘긴 것이 이 지점.  
김은기·이현지: 공부 방향이 틀렸던 것은 아님. 이 부분도 짚었으면 좋겠다는 코치님의 말씀.

## 2. 4단계: 만료(TTL)

### 2-1. 김소망 구현

store.py가 해시 테이블에 (값, 만료 시점) 튜플을 값으로 넣음. 해시 테이블 코드는 바꾸지 않음 (해시 테이블은 그냥 자료구조. 만료나 락을 알 필요가 없음).  
덮어쓰거나 칸 수 확장으로 노드를 옮길 때 만료 시점이 값과 한 묶음이라 같이 따라감.  
지연 삭제: 만료되어도 바로 지우지 않고, 누군가 그 키를 get / delete할 때 시간을 확인해 지났으면 그때 지움.  
지금 시각 ≥ 만료 시점이면 만료로 판단.  
만료된 키를 delete하면 1단계 규칙 그대로 200 + deleted: false (없는 키 삭제와 동일).  
김은기: expire_at 하나를 추가해 구현.

### 2-2. 어떤 시계를 쓸까: time.time() vs time.monotonic()

| | time.time() (달력 시간) | time.monotonic() |
|---|---|---|
| 기준 | OS가 가진 실제 시각 | 프로그램이 정한 기준점에서 흐른 시간 |
| 장점 | 재시작해도 의미가 유지되어 파일 저장에 유리 | 시간이 뒤로 가지 않아 만료가 정확 |
| 약점 | OS 시계가 인터넷 시간에 맞춰지는 등 바뀔 수 있음 → 만료가 갑자기 늦어지거나 빨라짐 | 재시작하면 기준점이 바뀌어 저장해 둔 만료 시점이 의미 없어짐 |

김소망은 time.monotonic() 선택. 지금은 파일에 저장하지 않아 서버를 끄면 해시 테이블도 사라지므로 문제없음. 나중에 영속성을 붙이면 문제가 될 수 있음.  
이현지 제안: 파일에 저장할 때 만료 시점 대신 남은 초를 저장하고, 다시 켰을 때 새 기준점에 남은 초를 더해 복원.  
실제 Redis는 파일 저장이 기본이라 달력 시간을 쓰고, 시계가 바뀌는 위험을 감수한다고 함 (이현지 조사). 서버 시계가 바뀌지 않도록 운영 쪽에서 관리할 것으로 추측.

### 2-3. 만료의 목표와 세 가지 결정 (이현지 정리)

목표: 값을 저장할 때 보관 기간을 함께 받고, 기간이 지난 값은 없는 키와 똑같이 다룬다.  
완료 기준: TTL을 주면 바로 조회되고 5초 뒤에는 404. TTL 없이 저장한 값은 계속 조회됨 (TTL은 선택).

| 질문 | 세 명의 공통 답 |
|---|---|
| 무엇을 저장하나 | "5초"라는 기간이 아니라 지금 + 5초 = 만료 시점 |
| 어디에 저장하나 | 값 자리에 (값, 만료 시점) 튜플 → 해시 테이블을 고칠 필요 없음 |
| 누가 언제 판단해 지우나 | 조회될 때 확인해 그 자리에서 지움 (지연 삭제) |

### 2-4. 만료와 무효화는 다르다

무효화: 원본과 캐시가 어긋나는 순간(원본 DB가 바뀜) 캐시를 즉시 지우는 것.  
누구 책임? → 원본을 수정한 애플리케이션. Redis는 원본이 있는지조차 모름. Redis가 DB를 계속 폴링하며 "바뀌었니?" 묻는 것은 말이 안 됨.  
흐름 (김소망·김은기 정리): 읽을 때 Redis에 있으면 바로 반환 → 없으면(캐시 미스) DB 조회 후 Redis에 저장하고 반환. 쓸 때 DB를 수정하고 Redis 키를 삭제 → 다음 읽기 때 새 값으로 채워짐.  
8단계 데모 API가 바로 이 "Redis를 사용하는 애플리케이션 코드"에 해당.  
만료: "인기 상품은 10초만 유효"처럼 정해 둔 기간이 지나면 없는 키로 취급.  
김소망: TTL은 안전망. 개발자가 무효화를 깜빡해도 TTL이 지나면 사라져 잘못된 상태가 오래가지 않음.

> **김은기 보충**
>
> 만료와 무효화를 나란히 비교하면:
>
> | | 만료 (expiration) | 무효화 (invalidation) |
> |---|---|---|
> | 무엇을 | TTL이 붙은 키 | 원본(DB)이 바뀐 데이터의 캐시 키 |
> | 언제 | 정해 둔 시간이 지나면 | 원본을 고친 직후 |
> | 누가 지우나 | 저장소(Redis). 앱은 TTL만 정함 | 앱이 직접 삭제 (`DEL`) |
> | 놓치면 | 조회 안 되는 만료 키가 메모리에 남음 | 옛 값이 TTL이 끝날 때까지 보임 |
>
> 보통 둘을 함께 씁니다. 무효화가 놓친 경우를 TTL이 안전망으로 잡아줍니다.

### 2-5. 지연 삭제의 약점과 주기적 정리

1초마다 100만 개를 모두 확인하는 방식은 확인하다 1초가 지나고 CPU를 다 씀 → 불가능.  
그래서 지연 삭제: 요청이 왔을 때만 판단.  
약점: 아무도 조회하지 않는 만료 키는 영원히 남음. 예: 크리스마스 트리 가격을 넣어 두면 다음 크리스마스까지 남아 있음.  
쓰지 않는 키가 적재율에 포함되어, 비어도 될 테이블을 계속 늘리게 만듦.  
해결: 일정 간격으로 훑으며 지우는 주기적 정리를 함께 씀 → 다음 단계.  
김소망이 짚은 동시성 문제: get이 "만료 확인 → 삭제"를 두 번에 나눠 하는 사이에 다른 요청이 같은 키를 set하면, 방금 들어온 새 값을 지워 버림 → 락이 필요한 지점 (동시성 단계로 이어짐).

## 3. 미해결: 칸 수 확장 때 만료 정보가 사라지는 문제 (김소망)

김소망 코드  
put(key, value): 새 키·값이 들어오면 새 노드를 만들어 넣음.  
resize: 칸을 늘릴 때 노드를 새로 만들지 않고 기존 노드를 떼어 새 칸에 붙임.  
고민: 확장할 때 resize 대신 put으로 다시 넣으면, put의 인자가 키·값뿐이라 만료 시점이 사라짐. 만료가 없던 키는 괜찮지만 만료가 있던 키는 만료가 없어짐. 고치려니 해시 테이블 코드 전체를 바꿔야 할 수준 → 기존 resize(노드 재사용)를 쓰면 안전하다고 판단.  
이현지 의문: 값 자리에 (값, 만료 시점) 튜플 하나를 넣는다면, Python 입장에서 튜플은 값 하나이므로 put(key, (값, 만료 시점))으로 넣어도 만료가 사라지지 않아야 함. 김소망의 다이어그램에는 set에 키·값·TTL 세 개를 따로 넣는 것처럼 보이는데 어떤 의미인지?  
결론 없음. 김소망이 원인을 다시 확인하기로 함.
