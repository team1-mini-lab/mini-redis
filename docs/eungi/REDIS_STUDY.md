## 1. 헷갈렸던 질문들

### Q. 레디스는 HTTP로 안 한다는 게 무슨 뜻?

- 네트워크로 통신하지만 HTTP가 아니라 **자체 프로토콜(RESP)을 TCP 위에서 직접** 씀

```
웹 API:  HTTP → TCP → IP
레디스:  RESP → TCP → IP

# RESP로 GET user:1 을 보내면 이게 전부
*2\r\n$3\r\nGET\r\n$6\r\nuser:1\r\n
```

- 이유: 캐시는 빨라야 함. 헤더 오버헤드 없음, 커넥션을 열어두고 재사용, 파이프라이닝, 파싱이 단순
- 그래서 curl이 아니라 `redis-cli`나 클라이언트 라이브러리(redis-py 등)로 접속
- 우리 미니 레디스는 구현·테스트·시연이 쉬워서 HTTP를 고름 (DESIGN.md 1단계 결정)

### Q. "API 형태의 구조"가 무슨 뜻?

- 로컬 캐시: 내 메모리의 객체 → `cache.get("key")`로 바로 접근
- 레디스: 다른 서버 → 정해진 명령으로 **요청/응답**, 실패·타임아웃 처리, 객체를 JSON 등으로 **직렬화**해야 함
- 통신은 HTTP가 아니어도 쓰는 모양은 API 호출과 같음

### Q. 캐시가 DP를 쓴다는 건?

- DP의 **메모이제이션**과 같은 아이디어: "한 번 계산한 건 저장해두고 다시 쓴다"
- `memo` 딕셔너리 = 캐시 저장소, 이미 계산한 값 재사용 = 캐시 히트
- 차이: DP의 답은 안 바뀜. 캐시는 원본(DB)이 바뀔 수 있어서 TTL, 무효화, 일관성 문제가 생김

### Q. 원자적 명령 = 점진적 재해싱?

아님. 둘 다 "레디스가 싱글 스레드"라서 나왔을 뿐 다른 개념.

| | 원자적 명령 | 점진적 재해싱 |
| --- | --- | --- |
| 무엇 | 명령 하나가 끼어들 틈 없이 한 번에 실행 | 해시 테이블을 키울 때 조금씩 나눠 옮기는 내부 방식 |
| 관점 | 사용하는 사람이 받는 보장 | 레디스 내부 구현 |
| 싱글 스레드와 관계 | 하나씩 처리하니 자연스럽게 원자성이 생김 | 한 번에 다 옮기면 그동안 모든 요청이 멈추니 나눠서 옮김 |

### Q. 싱글 스레드인데 왜 빠르지?

- 데이터가 RAM에 있어서 명령 하나가 아주 빨리 끝남
- 스레드가 하나라 락이 필요 없음
- 연결 여러 개를 한 스레드가 번갈아 처리 (I/O 멀티플렉싱)
- 대신 오래 걸리는 작업 하나가 전체를 멈추게 함 → 그래서 점진적 재해싱, 만료 키 샘플링 삭제처럼 **일을 쪼갬**

### Q. 동시성 문제는 여러 서버 문제만?

- 여러 **주체**가 같은 데이터를 동시에 읽고 고칠 때의 문제
- 여러 서버뿐 아니라 **한 서버 안의 여러 스레드**에서도 생김 (웹 서버는 요청마다 스레드가 따로 돎)
- 그래서 우리 5단계에서 저장소를 lock으로 감쌈

### Q. 상태 = 자료구조?

- 상태: 시스템이 **기억해서 다음 동작에 영향을 주는 데이터** (무엇을)
- 자료구조: 그걸 **어떤 모양으로 담나** (어떻게)
- 리액트로 치면 `count = 3`이 상태, 숫자로 담을지 배열로 담을지는 자료구조 선택

### Q. 레디스 타입마다 내부 구현이 다르다?

- 타입에 따라, 그리고 **데이터 크기에 따라** 달라짐
- 작을 때는 메모리를 아끼려고 압축 배열(listpack), 커지면 아래 구조로 바뀜

| 타입 | 클 때 내부 구현 |
| --- | --- |
| Hash, Set | 해시 테이블 |
| Sorted Set | 스킵 리스트 + 해시 테이블 |
| List | quicklist (연결 리스트 + 압축 배열) |

- `OBJECT ENCODING 키`로 확인 가능

## 2. 우리 구현과 실제 레디스 비교

| 항목 | 우리 미니 레디스 | 실제 레디스 |
| --- | --- | --- |
| 충돌 해결 | 체이닝 (연결 리스트) | 체이닝 |
| 새 노드 위치 | 체인 맨 앞 | 맨 앞 |
| 확장 기준 | 부하율 0.75 초과 | 부하율 1.0 기준 (메모리 절약 쪽) |
| 확장 배수 | 2배 | 2배 |
| 재배치 | 한 번에 전부 | 점진적 재해싱 (테이블 2개, 요청마다 조금씩) |
| 통신 | HTTP | RESP over TCP |
| 동시성 | lock (5단계) | 싱글 스레드 |
| 만료 | 지연 삭제 (4단계) | 지연 삭제 + 주기적 샘플링 삭제 |

### 왜 레디스는 개방 주소법이 아니라 체이닝?

- 개방 주소법은 칸 수보다 많이 못 담고, 차면 급격히 느려짐 → 무조건 늘려야 함
- 체이닝은 칸 수보다 많이 담을 수 있고 조금씩 느려짐
- 레디스는 거대한 테이블 하나를 **멈추지 않고** 운영해야 하고 삭제가 많음 → 체이닝 + 점진적 재해싱이 안정적

### 다항식 해시 (해시 함수를 직접 만들 때)

```python
def poly_hash(key):
    h = 0
    for ch in key:
        h = h * 31 + ord(ch)    # 자리마다 31을 곱하고 다음 글자를 더함
    return h
```

- 글자를 그냥 더하면 `"ab"`와 `"ba"`가 같은 값 → 자리마다 가중치를 곱해 순서가 다르면 값도 다르게
- Java `String.hashCode()`가 이 방식
- 파이썬 `hash()`는 문자열에 대해 실행마다 seed가 바뀜 (SipHash + 랜덤 seed, 해시 충돌 공격 방지) → 매번 같은 칸 배치를 보여주려면 직접 만든 해시가 유리

### `None` 값 저장 금지 규칙 (1단계 결정)

- `get`이 `None`을 돌려주면 "키가 없다" 하나로만 해석되게 하려는 것
- `None`을 저장할 수 있으면 "키는 있는데 값이 None"과 "키가 없음"을 구분할 수 없음

## 3. redis-cli 실습 기록

```bash
brew install redis
brew services start redis
redis-cli ping     # PONG
```

- `brew services start`가 성공이라고 해도 바로 접속하면 `Connection refused`가 날 수 있음. 잠깐 뒤 `ping`
- `redis-cli`는 `#` 주석을 지원하지 않음. 명령만 입력

| 개념 | 명령 | 확인한 것 |
| --- | --- | --- |
| TTL | `SET code 1234 EX 10` → `TTL code` → `GET code` | 10초 뒤 `(nil)` |
| 원자적 명령 | 터미널 2개에서 `INCR views` | 동시에 눌러도 정확히 올라감 |
| Sorted Set | `ZADD ranking 100 kim 300 lee 200 park` → `ZREVRANGE ranking 0 -1 WITHSCORES` → `ZINCRBY ranking 250 kim` | 정렬 명령 없이도 kim이 1등으로 바뀜 |
| Hash | `HSET user:1 name kim age 20` → `HINCRBY user:1 age 1` → `HGETALL user:1` | 필드 단위로 수정 |
| Pub/Sub | 터미널1 `SUBSCRIBE chat` / 터미널2 `PUBLISH chat "hello"` | 구독 중인 쪽이 바로 받음 |
| 영속성 | 값 저장 → 재시작 → `GET` | 서버 로그의 `Loading RDB ... keys loaded`가 디스크 백업을 다시 올리는 과정 |

### 출력 읽는 법

- `ZADD`의 `(integer) 0` = 새로 추가된 멤버 수. 이미 있으면 0이고 점수만 덮어씀
- `WITHSCORES` 결과는 두 줄씩 한 쌍. 홀수 줄 이름, 짝수 줄 점수 (번호는 순위가 아님)
- 핵심: `ZINCRBY`로 점수만 바꿨는데 꺼내보니 이미 정렬돼 있음 → Memcached였다면 꺼내서 정렬하고 통째로 다시 저장해야 했던 일
