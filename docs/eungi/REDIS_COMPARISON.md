# 실제 레디스 vs 우리 구현

기준 코드: `somang` 브랜치 36b80f2 (0~6단계) + `feat/8-demo` (8·9단계)

이 표는 "레디스의 기능 → 우리 코드"로 바로 건너뛰지 않고, 그 사이에 **실제 레디스는 어떻게 했는지**를 넣었습니다. 우리가 레디스와 다르게 한 곳마다 "왜 다르게 했나"를 적어 두면, 그게 곧 우리가 내린 결정입니다.

---

## 1. 한눈에 보기

| 레디스의 기능 | 실제 레디스 | 우리 구현 | 왜 다르게 했나 | 단계 · 상태 |
|---|---|---|---|---|
| 키로 값 찾기 | 해시 테이블, 체이닝 | 해시 테이블, 체이닝 (`hashtable.py`) | 같음 | 2 · 완료 |
| 해시 함수 | SipHash, **프로세스마다 무작위 시드** | FNV-1a, 고정 시작값 | 시드는 공격 방어용. 과제 범위 밖이고, 고정이면 테스트에서 칸 번호를 예측할 수 있음 | 2 · 완료 |
| 칸 수 늘리기 | 부하율 **1**에서 확장, **점진적 재해싱** (두 테이블을 두고 조금씩 옮김) | 부하율 **0.75** 넘으면 2배, **한 번에** 전부 옮김 | 한 번에 옮기는 쪽이 구현·설명이 단순. 우리 규모에선 멈춤이 체감되지 않음 | 3 · 완료 |
| 칸 수 줄이기 | 10% 미만으로 차면 축소 | 없음 | 과제 요구에 없음 | 하지 않음 |
| 만료 시점 저장 | 값과 **따로**, 별도 사전(`expires`)에 키 → 만료 시각 | 값 자리에 `(값, 만료 시점)` **튜플로 함께** | 해시 테이블을 고치지 않고 Store에서 처리 가능. 해시 테이블은 만료를 모름 | 4 · 완료 |
| 만료 시계 | 달력 시간 (Unix ms) | `time.monotonic()` | 우린 파일 저장이 없어 재시작 후 의미가 없어도 됨. 시계 보정에 흔들리지 않는 쪽을 택함 | 4 · 완료 |
| 지연 삭제 | 키에 접근할 때 확인 후 삭제 | `get`·`delete`에서 확인 후 삭제 | 같음 | 4 · 완료 |
| 주기적 삭제 | 1초에 10번, 만료 키 20개를 무작위로 뽑아 지우고, 25% 넘게 만료돼 있으면 반복 | 없음 | 과제 요구가 "만료된 값을 요청받았을 때" 처리라 지연 삭제로 충족 | 13 · 선택 |
| 동시 접근 | **싱글 스레드**로 명령을 하나씩 실행. lock 없음 | Flask 멀티스레드 + `Store`에 **lock 하나** | 파이썬 Flask는 요청을 스레드로 받음. lock으로 "한 번에 하나씩"이라는 같은 효과를 냄 | 5 · 완료 |
| 프로토콜 | RESP (TCP 위 자체 텍스트 프로토콜) | HTTP + JSON | 과제 R8 "외부에서 사용". HTTP는 curl·브라우저로 바로 확인 가능 | 1 · 완료 |
| 빈 키 `""` | **허용** | 400 거절 | 실수로 빈 키를 보내는 경우를 막으려고. 레디스보다 엄격함 | 6 · 완료 |
| 값의 종류 | 바이너리 문자열 (String 자료형) | JSON 값 그대로 (숫자·리스트·객체도 가능) | HTTP+JSON이라 자연스럽게 됨. 대신 리스트 일부만 고치는 명령은 없음 | 1 · 완료 |
| 값 `null` | 개념 없음 (값은 항상 문자열) | 400 거절 | `get`의 "없음"(404)과 구분할 수 없어서 | 6 · 완료 |
| TTL 0 이하 | `SET ... EX 0`은 오류, `EXPIRE key -1`은 **키를 즉시 삭제** | 400 거절 | 명령 하나(`/set`)뿐이라 "즉시 삭제" 의미를 줄 이유가 없음 | 6 · 완료 |
| 만료된 키 삭제 | `DEL` 결과 0 (없는 키와 같음) | `deleted: false` (없는 키와 같음) | 같음 | 4 · 완료 |
| 원자적 증가 | `INCR` | 없음 | 시간이 남으면. 동시성(R4)을 보여 주기 가장 좋은 기능 | 12 · 미정 |
| 데이터 유지 | RDB(스냅샷) / AOF(명령 기록) | 없음 | 과제에서 선택(R11) | 14 · 미정 |
| 메모리 한도 | `maxmemory` + 삭제 정책 (LRU/LFU 근사) | 없음. 계속 늘어남 | 과제 범위 밖. 대신 TTL로 캐시 키가 사라지게 함 | 하지 않음 |
| DB 앞의 캐시 | 레디스가 해 주지 않음. **앱이** Cache-Aside를 짬 | `demo/app.py`가 Cache-Aside를 짬 | 같음 (이게 "레디스를 쓴다"의 실제 모습) | 8 · 완료 |
| 원본 변경 시 무효화 | 레디스가 해 주지 않음. **앱이** `DEL` | `demo/app.py`가 DB 수정 후 `DELETE /delete` | 같음 | 8 · 완료 |
| Sorted Set, List, Replication, Cluster | 있음 | 없음 | 해시 테이블 위에 얹는 기능이라 범위 밖 (DESIGN.md "하지 않을 것") | 하지 않음 |

## 2. 같은 것 / 다른 것으로 나누면

**레디스와 같게 한 것**: 체이닝, 지연 삭제, 만료된 키 삭제 결과, Cache-Aside와 무효화를 앱이 책임지는 구조.

**단순하게 바꾼 것**: 해시 시드 없음, 한 번에 재해싱, 만료를 값과 함께 저장, lock으로 동시성 처리. 모두 "같은 효과를 더 단순한 방법으로" 낸 것입니다.

**더 엄격하게 한 것**: 빈 키, `null` 값, 0 이하 TTL을 거절. 레디스는 명령이 많아서 각 입력에 의미를 주지만, 우리는 명령이 셋뿐이라 애매한 입력은 거절하는 쪽이 안전했습니다.

**하지 않은 것**: 주기적 삭제, 축소, 메모리 한도, 영속성, 다른 자료형.

## 3. 발표 때 나올 만한 질문

**Q. 레디스는 싱글 스레드인데 우리는 왜 lock을 쓰나요?**
Flask가 요청을 여러 스레드로 받기 때문입니다. 레디스는 명령을 하나씩 순서대로 실행해서 끼어들 틈이 없고, 우리는 lock으로 같은 효과를 냅니다. 지연 삭제 때문에 `get`도 지우기를 할 수 있어서 조회에도 lock을 겁니다.

**Q. 재해싱을 한 번에 하면 그동안 멈추지 않나요?**
멈춥니다. 레디스는 키가 수백만 개라 그 멈춤이 문제가 되어 두 테이블을 두고 조금씩 옮기는 점진적 재해싱을 씁니다. 우리 규모에서는 체감되지 않아 단순한 쪽을 택했습니다.

**Q. 왜 레디스는 해시에 무작위 시드를 쓰나요?**
시드가 고정이면 공격자가 같은 칸에 몰리는 키를 미리 계산해 보낼 수 있습니다. 그러면 체인이 길어져 조회가 O(1)에서 O(N)으로 느려집니다(해시 플러딩). 우리 과제는 외부 공격을 다루지 않아 고정값을 썼습니다.

**Q. 레디스가 캐시를 알아서 채워 주나요?**
아닙니다. 무엇을 캐시할지, 언제 지울지는 앱이 정합니다. 8단계 데모 API가 바로 그 앱 코드입니다. 레디스가 알아서 하는 건 TTL이 지난 키를 지우는 것뿐입니다.
