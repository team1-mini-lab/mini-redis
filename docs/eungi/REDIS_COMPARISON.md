# 실제 레디스 vs 우리 구현

기준 코드: `somang` 브랜치 36b80f2 (0~6단계) + `feat/8-demo` (8·9단계)

레디스는 로컬 캐시가 일으키는 다섯 가지 문제를 풀려고 나왔습니다 ([WHY_REDIS_GUIDE.md](../study/WHY_REDIS_GUIDE.md) 3장). 그래서 이 문서는 기능을 하나씩 나열하지 않고, **다섯 문제마다 레디스가 무엇으로 풀었고, 우리는 어디까지 구현했는지**를 비교합니다.

---

## 1. 다섯 문제로 보는 비교

| 문제 (로컬 캐시) | 레디스는 무엇으로 푸나 | 우리 구현 | 상태 |
|---|---|---|---|
| **① 가격이 왔다 갔다**<br>서버마다 든 캐시 사본이 서로 어긋남 | 캐시를 서버 밖 **한 곳**에 둠. 원본이 바뀌면 앱이 `DEL`로 키 하나를 지움(무효화). `EXPIRE`(TTL)는 무효화를 깜빡했을 때의 안전망 | mini-redis를 별도 서버로 띄우고 HTTP로 사용 (1단계). `DELETE /delete`로 무효화, `ttl`로 만료 (1·4단계). 데모 API가 가격 수정 시 캐시 삭제 (8단계) | ✅ 시연으로 확인: 서버 A에서 할인하면 서버 B도 새 가격 |
| **② 로그인이 풀림**<br>세션이 로그인을 받은 서버에만 있음 | 세션을 키로 저장 (`SET session:abc kim EX 1800`). 어느 서버든 같은 곳에서 꺼냄 | 같은 `set` / `get` / `ttl`로 저장 가능. 세션도 키-값이라 따로 만들 기능이 없음 | △ 기능은 있음, 세션 데모는 만들지 않음 |
| **③ 배포하면 DB가 몰림**<br>캐시가 서버와 함께 사라짐 | 레디스는 앱과 **다른 프로세스**라 앱을 재시작해도 캐시가 남음. 레디스 자신이 꺼질 때를 대비해 RDB·AOF(파일 저장), Replication(복제) | mini-redis가 별도 프로세스 → 앱 재시작해도 캐시 유지. mini-redis 자신을 재시작하면 사라짐 (14단계 데이터 유지는 선택) | ✅ 앱 재시작 시연으로 확인<br>△ mini-redis 재시작은 미구현 |
| **④ 같은 데이터를 서버 수만큼 저장**<br>같은 사본을 서버마다 따로 저장하고 따로 조회 | 한 곳에만 저장. 메모리가 차면 `maxmemory` + 삭제 정책(LRU 등), 커지면 Cluster로 나눠 담음 | 한 곳에만 저장 → 서버 B는 A가 채운 캐시를 그대로 씀. 메모리 한도 없음, 만료 키는 조회될 때만 지움 (13단계 주기적 정리는 선택) | ✅ 시연으로 확인: DB 조회 4번 → 2번<br>△ 메모리 관리 없음 |
| **⑤ 함께 세야 하는 값이 틀림**<br>여러 서버가 같은 값을 동시에 읽고 고쳐 재고 1개가 두 번 팔림 | 명령을 **싱글 스레드**로 하나씩 실행. `INCR` / `DECR`처럼 "읽기+고치기+쓰기"를 한 명령으로 끝내 끼어들 틈이 없음(원자적). `SET NX`로 분산 락 | `set` / `get` / `delete` 하나하나는 lock으로 안전 (5단계). 하지만 재고를 "읽고 → 앱에서 빼고 → 다시 저장"하면 그 사이에 끼어들 수 있음 → 한 번에 끝내는 증가 명령이 필요 (12단계는 선택) | △ 저장소 안전은 됨<br>❌ 원자적 증가는 미구현 |

**다섯 문제의 공통 해결은 "상태를 서버 밖 한 곳으로 뺀다"**이고, 그 한 곳에서 키로 값을 찾는 입구가 **해시 테이블**입니다. 우리 과제의 핵심(2·3단계)이 여기에 해당합니다.

## 2. 정리

| 상태 | 문제 |
|---|---|
| 구현하고 시연으로 확인 | ① 가격이 왔다 갔다, ③ 배포하면 DB가 몰림(앱 서버 재시작), ④ 같은 데이터를 서버 수만큼 저장 |
| 기능은 있지만 데모 없음 | ② 로그인이 풀림 (세션을 mini-redis에 저장하면 됨) |
| 일부만 | ③ 중 mini-redis 자신이 재시작될 때 (14단계), ④ 중 메모리 관리 (13단계) |
| 아직 없음 | ⑤ 함께 세야 하는 값이 틀림 — 원자적 증가 명령 (12단계) |

⑤는 DESIGN.md "시간이 남으면" 1순위인 12단계(증가 명령)로 풀 수 있습니다. 완료 기준이 "동시에 100번 증가시키면 정확히 100"이라, 끝내면 다섯 문제를 모두 다룬 셈이 됩니다.

## 3. 시연과의 연결

`python -m demo.scenario`가 같은 데모 API를 두 대씩 띄워 ①③④를 로컬 캐시와 mini-redis로 나란히 보여 줍니다.

| 시연 단계 | 보여 주는 문제 | 로컬 캐시 | mini-redis |
|---|---|---|---|
| ② 서버 B로 첫 조회 | ④ 같은 데이터를 서버 수만큼 저장 | DB에 또 감 | 캐시에서 |
| ④ 할인 후 서버 B 조회 | ① 가격이 왔다 갔다 | 50,000원 (옛 가격) | 40,000원 |
| ⑤ 서버 A 재시작 후 조회 | ③ 배포하면 DB가 몰림 | DB에서 | 캐시에서 |

## 부록. 세부 구현 비교 (발표 질문 대비)

해시 테이블과 저장소를 어떻게 만들었는지, 실제 레디스와 어디가 다른지입니다.

| 항목 | 실제 레디스 | 우리 구현 | 왜 다르게 했나 |
|---|---|---|---|
| 충돌 처리 | 체이닝 | 체이닝 | 같음 |
| 해시 함수 | SipHash, 프로세스마다 무작위 시드 | FNV-1a, 고정 시작값 | 시드는 공격 방어용(해시 플러딩). 과제 범위 밖이고, 고정이면 충돌 장면을 매번 같게 보여 줄 수 있음 |
| 칸 수 늘리기 | 부하율 1에서 확장, 두 테이블을 두고 조금씩 옮김(점진적 재해싱) | 부하율 0.75 넘으면 2배, 한 번에 옮김 | 구현과 설명이 단순. 우리 규모에선 멈춤이 체감되지 않음 |
| 만료 저장 | 값과 따로, 별도 사전에 만료 시각 | 값 자리에 `(값, 만료 시점)` 튜플 | 해시 테이블은 만료를 모르게 하고 저장소가 처리. 가짜 시계로 테스트 가능 |
| 만료 시계 | 달력 시간 (Unix ms) | `time.monotonic()` | 파일 저장이 없어 재시작 후 의미가 없어도 됨. 시계 보정에 흔들리지 않음 |
| 만료 삭제 | 지연 삭제 + 1초에 10번 20개씩 무작위 검사 | 지연 삭제만 | 과제 요구가 "만료된 값을 요청받았을 때"라 지연 삭제로 충족 |
| 동시성 | 싱글 스레드, lock 없음 | Flask 멀티스레드 + 저장소에 lock 하나 | Flask가 요청을 스레드로 받음. lock으로 같은 효과 |
| 통신 | RESP (TCP 자체 프로토콜) | HTTP + JSON | 과제 R3·R8 "외부에서 사용". curl로 바로 확인 가능 |
| 빈 키 `""` | 허용 | 400 거절 | 실수 방지. 레디스보다 엄격 |
| TTL 0 이하 | `EX 0`은 오류, `EXPIRE -1`은 즉시 삭제 | 400 거절 | 명령이 셋뿐이라 애매한 입력은 거절 |
| 만료된 키 삭제 | 결과 0 (없는 키와 같음) | `deleted: false` | 같음 |

### 예상 질문

**Q. 레디스는 싱글 스레드인데 우리는 왜 lock을 쓰나요?**
Flask가 요청을 여러 스레드로 받기 때문입니다. 레디스는 명령을 하나씩 순서대로 실행해서 끼어들 틈이 없고, 우리는 lock으로 같은 효과를 냅니다.

**Q. lock이 있는데 왜 ⑤가 안 풀리나요?**
lock은 `set` 하나, `get` 하나를 안전하게 만듭니다. 재고 차감은 "get으로 읽고 → 앱에서 1 빼고 → set으로 저장"이라 명령이 두 번이고, 그 사이에 다른 서버가 끼어들 수 있습니다. 레디스는 `DECR` 한 명령으로 끝내서 이 틈이 없습니다. 12단계 증가 명령이 이걸 풉니다.

**Q. 레디스가 캐시를 알아서 채워 주나요?**
아닙니다. 무엇을 캐시할지, 언제 지울지는 앱이 정합니다. 8단계 데모 API가 그 앱 코드입니다. 레디스가 알아서 하는 건 TTL이 지난 키를 지우는 것뿐입니다.
