# 회의록 보충 — 김은기

> GitHub Discussions #32 회의록에서 잘못 설명했거나 미흡한 부분을 WHY_REDIS 자료를 근거로 정정·보완합니다.

---

## 1. ④번이 ①②를 해결하려다 나온 게 아님

①②는 서버마다 든 값이 **서로 달라서** 생기는 문제입니다. ④는 그것과 완전히 다른, **값이 같아도 생기는** 별개의 문제입니다.

| 장면 | 실제로 일어난 일 |
|---|---|
| ① 가격이 바뀜 | 서버마다 따로 든 `cache` 사본이 **서로 어긋남** |
| ② 로그아웃 | `sessions`가 로그인을 받은 서버에만 있음 |
| ③ 배포 때 DB 폭주 | 서버가 재시작되면서 들고 있던 상태가 같이 사라짐 |
| ④ 중복 | **어긋나지 않아도**, 같은 사본을 서버마다 따로 들고 있음 |
| ⑤ 재고, 쿠폰 | 모두가 함께 봐야 할 상태를 **둘 곳이 없음** |

다섯 장면은 서버를 세 대로 늘린 구조 그대로, 아무것도 고치지 않은 상태에서 벌어집니다. ④는 ①②를 고치려다 생긴 게 아니라, 처음부터 그 구조에 내재된 별개의 낭비 문제입니다.

---

## 2. stateless = "기억 상실"이 아니라 "기억을 맡긴 것"

"기억 상실"이라고 하면 기억 자체가 사라진다는 오해를 줍니다. 정확하게는 **기억을 서버 밖에 맡긴 것**입니다.

- **stateful 서버**: 자기만 아는 상태를 들고 있음 → 요청이 "그 서버"로 가야만 처리됨
- **stateless 서버**: 상태를 서버 밖에 맡기고 자기는 들고 있지 않음 → 어느 서버로 가도 같은 답

기억 자체가 없어지는 게 아니라, 기억을 레디스(공용 저장소)가 대신 들고 있는 겁니다. 앱 서버는 필요할 때 거기서 꺼내 쓰면 됩니다. 창구 직원이 수첩을 버린 게 아니라, 모든 직원이 같은 중앙 서랍에 기록을 보관하는 것입니다.

---

## 3. "React가 상태와 화면을 분리했듯이" — 끝까지 말하면

React가 상태와 화면을 분리했듯이, **Redis는 상태와 서버를 분리**합니다.

| | React | Redis |
|---|---|---|
| 고통 | DOM을 직접 고치니 화면과 데이터가 어긋남 | 서버 메모리에 캐시·세션을 두니 서버끼리 어긋남 |
| 뿌리 | 상태가 화면 곳곳에 흩어져 있음 | 상태가 각 서버에 묶여 있음 |
| 해결 | 상태를 한 곳에 두고 `UI = f(state)` | 상태를 서버 밖 한 곳에 두고 서버는 읽고 쓰기만 |
| 결과 | **상태 ↔ 화면** 분리 | **상태 ↔ 서버** 분리 |

## 4. Redis를 "쓴다"는 것이 무엇인가

Redis는 라이브러리가 아니라 **따로 돌아가는 서버 프로그램**입니다. 풀네임이 그걸 그대로 설명합니다.

> **Redis = Remote Dictionary Server**

- **Remote (원격)**: 앱 서버 안이 아니라 **밖에 따로 있어서** 네트워크로 접근합니다. "상태를 서버 밖으로 뺀다"는 해결책 그 자체가 이름에 담겨 있습니다.
- **Dictionary (사전)**: 키로 값을 찾는 구조입니다. 파이썬의 `dict`이자 우리가 만드는 해시 테이블입니다. 레디스의 바깥 층 — "키 → 값 해시 테이블 하나" — 과 같은 말입니다.
- **Server (서버)**: 라이브러리가 아니라 따로 돌아가는 프로그램입니다. **그래서 앱을 배포하고 재시작해도 같이 꺼지지 않습니다.** ③번(배포 때 DB 폭주)이 해결되는 직접적인 이유입니다.

코드로 보면, 서버 메모리의 딕셔너리를 읽고 쓰던 부분을 레디스 명령으로 바꾸는 것뿐입니다:

```python
# 로컬 캐시 (기존)
cache["keyboard"] = 40000

# 레디스 (변경 후) — A, B, C 모두 같은 레디스에 접속
r = redis.Redis(host="레디스서버주소", port=6379)
r.set("product:keyboard", 40000, ex=60)   # 60초 TTL
```

앱 코드가 가리키는 주소만 바뀌는 겁니다. A, B, C 모두 같은 레디스 주소를 가리키니 자연스럽게 공유됩니다.

## 5. ①번 — 가격 변경이 B, C에 반영 안 되는 이유

관리자 요청이 로드밸런서를 거쳐 서버 A로 배정됩니다. 서버 A는 DB를 수정하고 **자기 메모리 안의 캐시만** 고칩니다. 서버 B, C는 별도 프로세스라 A의 메모리에 접근할 방법이 없습니다.

```
관리자 → 로드밸런서 → 서버 A
                       ├─ DB 수정 (40,000원)       ← 원본은 고쳐짐
                       └─ 자기 캐시만 갱신          ← B, C에는 여전히 50,000원

고객이 새로고침:
  → 서버 A로 가면 40,000원
  → 서버 B로 가면 50,000원   ← 로드밸런서가 번갈아 보내서
  → 서버 C로 가면 50,000원
```

레디스로 해결할 때는 키를 "밀어넣는" 게 아니라 **지웁니다**:

```python
def update_price(pid, price):
    db.update(pid, price)       # 원본 수정
    r.delete(f"product:{pid}") # 레디스 키 하나만 삭제
```

다음 조회 때 A, B, C 모두 레디스에 없으니 DB에서 새 값을 가져옵니다. 이걸 **무효화(invalidation)**라고 합니다. TTL로 시간이 지나면 자동 삭제되는 **만료(expiration)**와 다른 개념입니다. 보통 둘을 함께 씁니다 — 무효화가 놓친 경우를 TTL이 안전망으로 잡아줍니다.

---

## 6. ①번과 ⑤번의 차이

| | ① 가격 | ⑤ 재고 |
|---|---|---|
| 문제 | 원본이 바뀐 사실이 다른 서버에 **전파 안 됨** | 여러 서버가 같은 값을 **동시에 읽고 각자 판단** |
| 비유 | 한쪽이 고쳤는데 나머지가 모름 | 뮤텍스 없이 공유 변수를 여럿이 동시에 읽고 씀 |
| 레디스 해결 | 쓸 때 키를 삭제 (무효화) | `DECR` 한 명령으로 읽기·빼기·쓰기를 원자적으로 |

레디스는 명령을 한 스레드에서 하나씩 처리하므로 `DECR` 중간에 아무도 끼어들 수 없습니다. 우리 구현에서는 `threading.Lock()`으로 같은 효과를 냅니다.
